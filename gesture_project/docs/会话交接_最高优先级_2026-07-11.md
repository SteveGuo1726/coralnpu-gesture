## 4. 下一轮直接怎么接

下一轮不要再回头重复证明已经通过的东西，直接按下面顺序推进：

1. 不要再重复证明 `cfg9` 能不能出位流、能不能烧录、能不能做 `debug smoke`、能不能做 `rowhandoff` 对账、能不能做 `WIN3` 板测，这些都已经真实通过。
2. 继续沿当前 `DSP_USED=13` 的稳定基线推进 `3x3` 后端，不要散回去扫零碎小 patch。
3. 当前最高价值方向是：
   - 更连续的行缓存和滑窗复用
   - 更少的 AXI-Lite 逐字喂数依赖
   - 把当前窗口级参考核继续推进成更接近整层卷积数据流的后端
4. 只要改了 RTL，就必须继续做到：
   - 真实构建
   - 真实烧录
   - 真实板测
   - 真实结果判断

### 4.1 当前朝“上板算法运行”的推荐目标

当前最推荐的上板算法运行目标，不是一下子追求“整网自主跑完”，而是按下面顺序推进，这样最快也最稳：

1. 先把当前手势识别主算法的第一层真实 `3x3` 卷积做成“整层逐行上板回放”。
   - 不是只算一个窗口，也不是只做 smoke。
   - 目标是把一整层输入特征图按行喂入板上，板上连续输出这一层的完整结果，并与软件 golden 对齐。
2. 再把第二层到第四层按同样方式接成“逐层回放”。
   - 当前更适合先做“逐层 host 驱动 + 板上卷积执行 + host readback 对账”。
   - 还不适合现在就强行追求板上完全 автономous 整网控制。
3. 当前最值得优先实现的板上算法运行形态是：
   - 固定权重和 bias
   - 输入特征图按行或按小块送入
   - 板上连续完成 `3x3` 滑窗卷积
   - 结果回读后与软件逐点对齐
4. 当前不推荐把“第一版上板算法运行目标”定成：
   - 摄像头实时采集
   - PS 端复杂软件栈
   - 完整整网一次性自动调度
   这些会明显拖慢当前主线，不利于先把核心算法跑板上跑稳。

### 5.3 XSDB / 板级调试硬规则

- 不要并发跑两个 `xsdb` 抢同一块板。
- 看到 `DAP (AHB AP transaction error, DAP status 0x30000021)` 时，不一定要立刻手工重启板子。
- 当前已经验证可恢复流程是：
  - 选 `DAP*`
  - 执行 `rst -system`
  - 等约 `1000ms`
  - 再重新枚举目标
- 当前 `cfg9` 板级壳里，核心默认会被 `CoreCSR` 保持在 `reset/cg` 状态。
- 真实板测里必须先处理 `CoreCSR` 控制字：
  - 读 `0x00000000` 会看到 `0x00000003`
  - 再把它清成 `0x00000000`
  - 然后 `DMSTATUS / DATA0` 调试链才会真正通
- 板上对 `0x43C00000` 做寄存器读写时，稳妥方式是：
  - `stop/ps7_init/ps7_post_config` 走 `ARM Cortex-A9 MPCore #0`
  - PL 外设寄存器读写切到 `APU`
  - 显式 `configparams force-mem-accesses 1`

### 5.4 CoreCSR / rowhandoff 当前确认口径

- `0x820 -> {hit, miss, invalidate, produce}`
- `0x830 -> {tail_hit, interior, right_edge, row_last}`
- `0x844 -> state_trace_word`
- `0x840` 是写事件口，不是状态读口
- 当前 `cfg9` 壳里的快捷事件注入口是：
  - `base + 0xB0`
