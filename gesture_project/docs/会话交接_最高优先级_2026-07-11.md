### 3.4 当前最新硬件判断

当前必须保持清醒的判断如下：

1. `cfg9 + CoreCSR + rowhandoff + WIN3` 这一版已经能在 `7Z010` 上稳定收敛到 `25MHz`。
2. `WIN3` 当前已经不是“只功能打通的 LUT 乘法参考核”，而是真正吃进 `DSP48E1` 的板级稳定版。
3. `DSP_USED` 从之前的 `4` 提升到了 `13`。
   - 原先 `4` 个 DSP 来自 `cfg9` 核内既有乘法路径。
   - 新增 `9` 个 DSP 来自 `gesture_conv3x3_win3_lite.sv` 的 9 路 `8x8` 有符号乘法。
4. 但不要误判成“3x3 后端已经优化完成”。
   - 当前 `WIN3` 仍然只是“单次喂入 3 行 5 列，顺序产出 3 个相邻窗口结果”的窗口级参考核。
   - 它已经具备权重锁存、窗口内输入复用、部分和寄存、DSP 乘法映射。
   - 它还没有做到更完整的连续行缓存、流式输入、跨更多输出通道的真实层加速器形态。
5. 当前已经证明：即使板核里还没加片上 requant 尾部，现有 `WIN3` 也已经能在真板上吃进真实量化层张量，并由 host 侧完成跨 `Cin` 累加后对上 raw conv golden。
   - 这说明“真实模型层数据 -> 板上窗口核 -> host readback 对账”这条主链已经成立。
   - 而且这一条主链已经从“3 个相邻窗口片段”推进到了“单输出通道整行回放”。
   - 现在又进一步推进到了“多输出通道整行回放”，只是当前多输出通道仍由 host 逐通道换权重驱动，不是板上并行 `Cout` 阵列。
   - 板上直接读回的仍然是 raw `int32` 卷积和，这是卷积累加器的正常输出，不代表模型本身存的是 `int32`。
   - 当前已经补齐 host 侧真实量化参数换算，所以现在既能对上 raw `int32`，也能进一步对上 `TFLite` 最终 `int8` 输出。
   - 但仍要注意：requant / output zero-point / fused activation 还没有真正下沉进板上 RTL。
6. `coralnpu_lite_cfg9_axi_lite_peripheral.sv` 里此前围绕 `win3_ctrl_clear_write` 的 HDL 解析告警已经收掉。
   - 这次重新完整构建时，不再出现对 `ADDR_WIN3_CTRL` 的那条依赖告警。

### 4.1 当前朝“上板算法运行”的推荐目标

当前最推荐的上板算法运行目标，不是一下子追求“整网自主跑完”，而是按下面顺序推进，这样最快也最稳：

1. 先把当前手势识别主算法的第一层真实 `3x3` 卷积做成“整层逐行上板回放”。
   - 不是只算一个窗口，也不是只做 smoke。
   - 目标是把一整层输入特征图按行喂入板上，板上连续输出这一层的完整结果，并与软件 golden 对齐。
2. 再把第二层到第四层按同样方式接成“逐层回放”。
   - 当前更适合先做“逐层 host 驱动 + 板上卷积执行 + host readback 对账”。
   - 还不适合现在就强行追求板上完全 автономous 整网控制。
3. 当前最值得优先实现的板上算法运行形态是：
   - 固定权重和 bias
   - 输入特征图按行或按小块送入
   - 板上连续完成 `3x3` 滑窗卷积
   - 结果回读后与软件逐点对齐
4. 当前不推荐把“第一版上板算法运行目标”定成：
   - 摄像头实时采集
   - PS 端复杂软件栈
   - 完整整网一次性自动调度
   这些会明显拖慢当前主线，不利于先把核心算法跑板上跑稳。

### 4.2 当前最新阻塞与直接应对

1. 当前最大的速度瓶颈已经不是 `WIN3` 卷积核本身，而是 `XSDB + AXI-Lite` 的逐窗口寄存器交互。
   - 以 `conv2_3x3_b, row=0, oc={0,5,11,17}` 这次多输出通道整行为例，脚本生成了约 `36869` 行 `XSDB` 命令。
   - 慢点主要在 JTAG/调试链，不在板上 `DSP` 乘加。
2. 下一轮加速优先级应当是：
   - 先摸清 `delay_ms` 的稳定下限，减少单次窗口等待。
   - 再把“逐窗口寄存器脚本”推进成“更少主机交互、更多板上连续执行”的回放形态。
3. 在没有完成上面这一步之前，不要误把超长板测耗时当成 `WIN3` 核吞吐本身。
4. `ARM` 板上循环版快速回放已经推进到：
   - 新脚本：`gesture_project/board_validation/zynqmini_7z010/current/scripts/host/run_win3_real_layer_fragment_arm.py`
   - 已确认：生成模型 payload、生成 ARM 裸机二进制、调用 `XSDB` 下载/执行/回读 `mailbox` 这条链基本结构已经打通
   - 新确认：`A9` 目标下对 `0x00000000 / 0x00100000 / 0xFFFC0000` 的普通 `mwr/mrd` 仍会被 MMU 翻译挡住
   - 新确认：`APU` 对 DDR 地址做单次 `mwr/mrd` 或极小 `dow -data` 有时可返回成功，但对较大的程序下载仍会撞到 `AHB AP transaction error, DAP status 0xF0000021`
   - 当前阻塞：稳定的 ARM 程序装载路径还没有收敛，尤其是“如何把可执行程序稳定装入 A9 可运行的内存区”这一点尚未形成正式保底线
   - 结论：它还属于活跃实验线，不能替代现有已通过的 host + `XSDB` 真板回放保底线

### 5.3 XSDB / 板级调试硬规则

- 不要并发跑两个 `xsdb` 抢同一块板。
- 看到 `DAP (AHB AP transaction error, DAP status 0x30000021)` 时，不一定要立刻手工重启板子。
- 当前已经验证可恢复流程是：
  - 选 `DAP*`
  - 执行 `rst -system`
  - 等约 `1000ms`
  - 再重新枚举目标
- 当前 `cfg9` 板级壳里，核心默认会被 `CoreCSR` 保持在 `reset/cg` 状态。
- 真实板测里必须先处理 `CoreCSR` 控制字：
  - 读 `0x00000000` 会看到 `0x00000003`
  - 再把它清成 `0x00000000`
  - 然后 `DMSTATUS / DATA0` 调试链才会真正通
- 板上对 `0x43C00000` 做寄存器读写时，稳妥方式是：
  - `stop/ps7_init/ps7_post_config` 走 `ARM Cortex-A9 MPCore #0`
  - PL 外设寄存器读写切到 `APU`
  - 显式 `configparams force-mem-accesses 1`

### 5.4 CoreCSR / rowhandoff 当前确认口径

- `0x820 -> {hit, miss, invalidate, produce}`
- `0x830 -> {tail_hit, interior, right_edge, row_last}`
- `0x844 -> state_trace_word`
- `0x840` 是写事件口，不是状态读口
- 当前 `cfg9` 壳里的快捷事件注入口是：
  - `base + 0xB0`

  - `Slice LUTs = 37791`
  - `Slice Registers = 6503`
  - `BRAM = 6`
  - `DSP = 4`
  - `WNS = -28.525 ns`

这一阶段的意义：

- 失败不是工具链失败，而是设计资源本身还太大。
- 后续必须优先找真正能大幅降 LUT 的结构性裁剪点，而不是只微调缓存或 TCM。
