## 1. 项目全景：我们到底在做什么

### 1.1 一句话

我们要在 Xilinx Zynq-7020 开发板上，用 FPGA 可编程逻辑（PL）加速一个 18 类
静态手势识别 CNN，使一张 96×96 RGB 测试图从 DDR 读入后，完整跑完卷积、池化、
1×1 头、全局平均池化和全连接分类，并输出预测类别。PS 端（ARM 处理器）只负责
配置硬件和启动任务，真正的计算在 PL 端完成。

当前稳定版本实板结果是：

- 时钟频率：80 MHz。
- 端到端：约 41.9 FPS（DDR 模拟摄像头输入帧 → 整网 → 类别）。
- `FINAL_RESULT = 0x600D600D`，所有层 FNV 校验和 TFLite golden 一致。
- 时序：`WNS=+0.365 ns`、`WHS=+0.022 ns`，无失败路径。

### 1.2 为什么选 Zynq-7020

Zynq-7020 不是普通 FPGA，而是 SoC：它内部同时有：

- **PS**（Processing System）：ARM Cortex-A9 双核，可以跑软件、文件系统、网络、摄像头驱动。
- **PL**（Programmable Logic）：传统 FPGA 可编程逻辑，适合做并行硬件加速器。
- **AXI 总线**：PS 和 PL 之间的高速数据通道。

对“摄像头手势识别”这种任务，我们让 ARM 做“管理员”，FPGA 做“计算工人”：
管理逻辑慢但灵活，计算逻辑固定但极快。软硬件协同设计就是分配好两者职责。

### 1.3 为什么最初参考 CoralNPU，但现在是自己实现

Google Coral Edge TPU 的 RTL 是很好的参考，但它是 Google 官方代码，本项目不能
修改。我们只借鉴它的几个核心思想：

1. **控制与计算解耦**：PS 配置任务，PL 独立执行。
2. **片上数据复用**：尽量让中间结果留在片上，减少 DDR 往返。
3. **权重驻留 / 双 bank**：计算一个权重 bank 时，另一个 bank 可以预载下一层权重。

我们的 GestureFlow-NPU 是独立 SystemVerilog RTL，不是 CoralNPU 移植。所有 RTL
文件都带 `PROJECT_LOCAL_SELF_RESEARCH_NOT_GOOGLE_OFFICIAL` 注释。

### 1.4 当前部署模型

当前上板的静态学生模型是：

```text
96×96×3 RGB
  → conv0: 4×4 SAME, 3→16
  → pool1: 2×2 maxpool
  → conv2a: 4×4 SAME, 16→32
  → conv2b: 4×4 SAME, 32→32
  → pool2: 2×2 maxpool
  → conv3a: 4×4 SAME, 32→48
  → conv3b: 4×4 SAME, 48→48
  → pool3: 2×2 maxpool
  → head: 1×1, 48→64
  → GAP: 全局平均池化
  → FC: 64→18, softmax
```

这里的 `4×4 SAME` 表示卷积核是 4×4，输出尺寸和输入尺寸相同（用 padding 补齐）；
`3→16` 表示输入通道 3、输出通道 16。`1×1` 卷积本质是“对每个像素位置做一次小全
连接”，后面硬件专门有 pointwise 模式复用它。

## 2. 算法与训练：一个 18 类学生模型是怎么炼成的

### 2.1 手势识别任务与数据

本项目使用 HaGRID-v1 的 384p 目标手部版本，18 类手势。训练前按“受试者”
划分 train/val/test，避免同一个人几乎相同的帧同时出现在训练集和测试集，造成
虚高准确率。数据准备脚本在 [`datasets/tools/`](../datasets/tools/)。

标签平滑和 MixUp 都属于“正则化”，目的是防止模型对训练样本太自信，从而提高
泛化和量化后的稳定性。

### 2.2 教师模型：MobileNetV3Large

教师模型不是直接上板，而是用来教学生。训练脚本
[`run_train_hagrid18_teacher.sh`](../algorithms/scripts/run_train_hagrid18_teacher.sh)
的关键参数：

```bash
--arch keras_mobilenet_v3_large
--weights imagenet          # 从 ImageNet 预训练开始，比随机初始化快且稳
--image_size 96
--batch_size 128
--freeze_backbone           # 前 3 轮只训练新分类头
--finetune_epochs 20        # 之后微调整个骨干
--label_smoothing 0.05
--mixup_alpha 0.1
```

为什么先用 ImageNet 预训练？因为卷积网络低层学的是边缘、纹理、形状等通用特征，
这些特征可以迁移到手势任务，避免小数据上从头学。

### 2.3 标签平滑 Label Smoothing

普通 one-hot 标签是 `[0,0,1,0,...]`，告诉模型“正确答案概率是 1，其他是 0”。
标签平滑把 1 稍微分给其他类别，例如 18 类、平滑系数 0.05 时：

```text
正确类 = 1 - 0.05 = 0.95
其他类 = 0.05 / (18 - 1)
```

对应代码在
[`train_static_cnn.py`](../algorithms/static_cnn/train_static_cnn.py#L285) 的
`build_loss()`：`CategoricalCrossentropy(label_smoothing=...)`。

为什么对硬件量化有帮助？如果模型对错误类别输出极端接近 0，训练后权重分布可能
更尖锐；量化到 INT8 后，这种极端分布更容易因舍入而损失信息。标签平滑让输出更
平滑，通常能让量化模型更稳。

### 2.4 MixUp

MixUp 不直接喂原始图，而是把两张图和标签按比例混合：

```text
x_mix = λ x_a + (1-λ) x_b
y_mix = λ y_a + (1-λ) y_b
```

它让模型学会“输入被插值时，输出也应该是插值的”，是一种数据增强和正则化。
代码在 [`train_static_cnn.py`](../algorithms/static_cnn/train_static_cnn.py#L474)
的 `apply_mixup()`。

### 2.5 知识蒸馏 Knowledge Distillation

教师模型大、精度高，但硬件放不下或跑不动；学生模型小、适合 FPGA，但直接训练
精度不够。知识蒸馏让教师模型的“软输出”指导学生：

```text
学生损失 = (1-α) × 真实标签损失 + α × 蒸馏损失
```

软输出不是直接 softmax，而是先除以温度 T 再 softmax：

```text
soft_target = softmax(log(teacher_prob) / T)
```

温度越高，教师输出越“平滑”，类间相似性信息越明显。温度低则接近 one-hot。

学生蒸馏脚本
[`run_train_hagrid18_student_distill.sh`](../algorithms/scripts/run_train_hagrid18_student_distill.sh)
中的关键参数：

```bash
--distill_alpha 0.35        # 蒸馏损失占总损失 35%
--distill_temperature 3.0   # 温度 3
```

蒸馏训练器在
[`train_static_cnn.py`](../algorithms/static_cnn/train_static_cnn.py#L344)
的 `build_distillation_trainer()`。注意这个 wrapper 只用于训练，导出时只保存
`student`，所以蒸馏不会增加部署模型的参数、算力或硬件负担。

### 2.6 学生结构：为什么是 4×4 / 16-32-48 / 1×1 head

当前学生不是“随便一个小 CNN”，而是和 7020 硬件深度耦合的结构：

- 输出通道选 16/32/48，是因为 PL 卷积 tile 一次输出 16 通道，1×1 head 输出
  64 通道也被切成 4 个 16 通道 tile；这样几乎没有浪费。
- 卷积核选 4×4，是 DMP 流引擎目前 `KERNEL_SIZE=4` 的主要路径，后续也兼容 3×3。
- 最后用 1×1 把 48 通道升到 64，再用 GAP+FC 分类。1×1 在硬件上就是 pointwise
  模式，可以复用同一套 MAC 阵列。

学生结构构建入口在
[`train_static_cnn.py`](../algorithms/static_cnn/train_static_cnn.py#L917) 的
`build_model()`。

### 2.7 训练命令与产物

教师和学生的训练脚本入口分别是：

- [`algorithms/scripts/run_train_hagrid18_teacher.sh`](../algorithms/scripts/run_train_hagrid18_teacher.sh)
- [`algorithms/scripts/run_train_hagrid18_student_distill.sh`](../algorithms/scripts/run_train_hagrid18_student_distill.sh)

训练产物保存在 `models/`，不再放在 `/tmp`，避免丢失。

## 3. 量化与导出：从 Keras 浮点模型到 INT8 TFLite

### 3.1 为什么要量化

浮点卷积在 FPGA 上又慢又费资源；本项目的硬件是 INT8 定点乘加。把 Keras 浮点
模型转成 INT8，是为了让软件模型和硬件计算格式一致。

量化就是把浮点值映射成整数：

```text
real_value = scale × (quantized_value - zero_point)
```

其中 `scale` 是步长，`zero_point` 是整数零点。卷积和全连接的量化计算最终会变成
整数乘加，硬件只需要整数乘加器。

### 3.2 训练后量化 Post-Training Quantization

本项目用的是 TFLite 训练后整型量化，入口
[`quantize_tflite.py`](../algorithms/static_cnn/quantize_tflite.py#L52)：

```python
converter.optimizations = [tf.lite.Optimize.DEFAULT]
converter.representative_dataset = ...
converter.target_spec.supported_ops = [tf.lite.OpsSet.TFLITE_BUILTINS_INT8]
converter.inference_input_type = tf.int8
converter.inference_output_type = tf.int8
```

`representative_dataset` 从训练集抽样，让 TFLite 观察每层激活的范围，从而选择
合理的 scale 和 zero_point。代码在
[`quantize_tflite.py`](../algorithms/static_cnn/quantize_tflite.py#L32)。

### 3.3 RepVGG 训练/部署等价导出

训练时为了更好收敛，RepVGG 会同时用 3×3、1×1 和 identity 分支；部署时把这些
分支和 BatchNorm 融合成单个卷积，参数和计算量更小。导出逻辑在
[`export_repvgg_deploy.py`](../algorithms/static_cnn/export_repvgg_deploy.py)。

但当前上板的“学生部署图”用的是 `regularized_plain + 4,4,4`，不是 RepVGG 分支
结构，因此 RepVGG 导出脚本是备选/对照路线。交接文档中“RepVGG 图像参考线”是
更高精度的另一条候选。

### 3.4 TFLite 的 requantize 规则

TFLite 整数推理的卷积层输出在硬件中不是直接截断，而是要按公式：

```text
output = saturating_rounding_doubling_high_mul(
    input × multiplier, right_shift) + output_zero_point
```

这个公式看起来复杂，本质是“先做定点乘法，再做带舍入的右移，再加零点并饱和到
INT8”。硬件必须逐位复现它，否则 FNV 会不一致。对应硬件
[`gestureflow_requant_relu.sv`](../innovation_npu/rtl/gestureflow_requant_relu.sv#L14)
。

## 4. 硬件架构：逐模块讲透

### 4.1 先建立 FPGA 硬件直觉

软件代码是“一条条顺序执行”，SystemVerilog 是“很多电路同时工作”。RTL 里最常
出现两个块：

```systemverilog
always_ff @(posedge clk) begin
  q <= d;   // 每个时钟上升沿，寄存器 q 被 d 更新
end

always_comb begin
  y = a + b; // 组合逻辑，a/b 一变，y 立刻变
end
```

性能不是看“多少行代码”，而是看：

- 每个周期能做多少有效乘加（MAC/cycle）。
- 关键路径多长（决定最高频率）。
- DDR 访存是否成为瓶颈。
- 资源（LUT、FF、BRAM、DSP）是否超限。

### 4.2 顶层：谁负责调度，谁负责计算

硬件顶层
[`gestureflow_layer_chain_dmp_hp0_axil.sv`](../innovation_npu/rtl/gestureflow_layer_chain_dmp_hp0_axil.sv#L12)
是一个大模块，对外有两组 AXI：

1. **S_AXI（AXI-Lite）**：PS 用来读写控制寄存器。
2. **M_AXI（AXI4 HP0）**：PL 主动去 DDR 读写输入/输出张量和权重。

顶层内部实例化了：

- RGB loader / tensor loader：DDR 读输入。
- 行缓存 + 滑窗：把流式像素变成卷积窗口。
- DMP MAC tile：做卷积乘加。
- requant + ReLU：TFLite 量化尾端。
- output bank / writer：把结果写回 DDR。
- GAP/FC：分类尾端。

寄存器表定义在
[`gestureflow_layer_chain_dmp_hp0_axil.sv`](../innovation_npu/rtl/gestureflow_layer_chain_dmp_hp0_axil.sv#L95)
附近。

### 4.3 DMP MAC tile：一次乘加为什么能“一顶二”

普通 INT8 MAC 用 1 个 DSP48E1 做 1 次有符号乘加。DMP（Dual-Multiply Packing）
的核心是把两个输出通道的权重打包到 DSP 的 25-bit A 端口：

```text
A = w_even' + (w_odd' << 16)
B = a'
A × B = w_even'·a' + (w_odd'·a')<<16
```

两个 8×8 无符号乘积最大只有 0xFE01，所以它们可以在 32 位结果里相隔 16 位而不
溢出。这样 1 个 DSP 每周期贡献两个输出通道。对应代码在
[`gestureflow_mac_tile_dmp.sv`](../innovation_npu/rtl/gestureflow_mac_tile_dmp.sv#L21)
，打包乘法在
[`product_comb`](../innovation_npu/rtl/gestureflow_mac_tile_dmp.sv#L150)
附近。

为什么用有符号偏移而不是直接把有符号数乘起来？因为直接有符号 8×8 乘法的硬件
拆包更麻烦；这里把激活和权重都偏移到无符号域，最后再统一减去 `-128 × sum(a)`
的修正项。修正项在
[`gestureflow_mac_tile_dmp.sv`](../innovation_npu/rtl/gestureflow_mac_tile_dmp.sv#L305)
附近的 retire 阶段完成。

### 4.4 为什么 DMP 能省 DSP，而不是省时间？

设普通 tile 是 `16 输出通道 × 4 输入通道`，需要 64 DSP，每周期 64 MAC。
DMP tile 是 `16 输出通道 × 8 输入通道`，仍然 64 DSP，但每周期 128 MAC。

因此 DMP 是在 **DSP 数量不变的情况下，吞吐翻倍**。代价是：

- 权重需要按 pair/tap/group 重新打包；
- 需要额外做有符号偏移修正；
- 加树要同时维护 low 16 bit 和 high 16 bit 两路，组合逻辑略增。

这个 trade-off 对 7020 很合适，因为 7020 DSP 只有 220 个，是稀缺资源；而多一
点 LUT/FF 和寄存器级数通常比多 DSP 更划算。

### 4.5 卷积流引擎：如何把一行行像素变成一个个 4×4 窗口

卷积输入是 NHWC 格式，按像素流送进来。不能等整张图都到了再算，否则要巨大的
片上缓存。硬件用“行缓存 + 滑窗”：

- 行缓存存几行像素；
- 当窗口的右下角像素到达时，把窗口内 16 个位置的像素同时送到 MAC。

窗口模块：

- [`gestureflow_same4x4_cin_window.sv`](../innovation_npu/rtl/gestureflow_same4x4_cin_window.sv#L10)
- [`gestureflow_line_window.sv`](../innovation_npu/rtl/gestureflow_line_window.sv#L8)
- [`gestureflow_line_window_vector.sv`](../innovation_npu/rtl/gestureflow_line_window_vector.sv#L7)

卷积流引擎
[`gestureflow_conv4x4_cin_same_stream_dmp.sv`](../innovation_npu/rtl/gestureflow_conv4x4_cin_same_stream_dmp.sv#L14)
负责：

1. 从窗口模块拿到 `window_valid/window_data`；
2. 把窗口存入 `held_window`，启动 MAC；
3. 依次遍历 tap 和 input group；
4. 每个窗口的最后一次 MAC 才输出一个结果向量。

### 4.6 输入通道分组：为什么 8 通道一组

DMP 每个权重字是 192 bit，覆盖 8 个输入 lane。因此输入通道按 8 个一组处理。
RGB 只有 3 个有效通道，也放在一个 8 通道组内，并用 `input_lane_enable` 屏蔽
高 5 个 lane。这样不需要为 RGB 单独做一套 3 通道硬件。

对应顶层连接：

```systemverilog
.input_group_count(...)
.input_lane_enable(layer_mode == 0 ? 8'b00000111 : 8'hff)
```

位置在
[`gestureflow_layer_chain_dmp_hp0_axil.sv`](../innovation_npu/rtl/gestureflow_layer_chain_dmp_hp0_axil.sv#L614)
附近。

### 4.7 行缓存和 SAME padding

SAME 卷积要求输出尺寸等于输入尺寸，因此在图像边缘补零。本项目 4×4 SAME 的
padding 是 top=1、left=1、bottom=2、right=2；3×3 SAME 是 top=1、left=1、
bottom=1、right=1。窗口模块必须正确处理这些 padding，否则边缘像素的卷积结果
会错。

### 4.8 池化：2×2 maxpool

池化在硬件中不是额外跑一个“网络”，而是融合在输出写回阶段：

- 普通层：requant 结果直接写 output bank；
- 需要池化的层：先用 `gestureflow_stream_pool2x2` 或 output bank 的 pool 模式，
  对 2×2 窗口取最大值，再把缩小后的结果写回 DDR。

相关模块：

- [`gestureflow_stream_pool2x2.sv`](../innovation_npu/rtl/gestureflow_stream_pool2x2.sv#L8)
- [`gestureflow_hp0_tensor_writer.sv`](../innovation_npu/rtl/gestureflow_hp0_tensor_writer.sv#L8)

### 4.9 requant + ReLU：TFLite 位精确的尾端

卷积累加器是 INT32，不能直接写回 INT8。requant 模块做：

```text
psum → 定点乘法 high_mul → 舍入右移 → 加 zero_point → 饱和到 [-128,127]
```

ReLU 被融合进去：如果启用 ReLU，结果小于 zero_point 时直接钳到 zero_point。

为什么当前用 4-lane 时间复用而不是 16-lane 全并行？因为 16 路并行会让 16 个
变量右移和多路选择同时扇出，容易成为关键路径。4 路在“吞吐足够、时序安全”之间
更平衡。模块入口
[`gestureflow_requant_relu.sv`](../innovation_npu/rtl/gestureflow_requant_relu.sv#L14)
，顶层参数 `REQUANT_PARALLEL_LANES` 在
[`gestureflow_layer_chain_dmp_hp0_axil.sv`](../innovation_npu/rtl/gestureflow_layer_chain_dmp_hp0_axil.sv#L20)
附近。

### 4.10 权重 bank 与 ping-pong

权重不是每帧从 DDR 慢慢读，而是存在片上 BRAM。每个输出通道对有一块权重 bank。
顶层还提供双 bank：

- 计算当前层时读 bank A；
- 同时可以把下一层权重 DMA 进 bank B。

这称为 ping-pong / double-buffering。硬件使能条件在 MAC 权重 bank 的写使能：

```systemverilog
.write_enable(weight_write_valid && (weight_write_pair == p) &&
              (!busy || (weight_bank_select != read_bank_select)))
```

对应文件
[`gestureflow_mac_tile_dmp.sv`](../innovation_npu/rtl/gestureflow_mac_tile_dmp.sv#L105)
附近。

注意：当前稳定版软件仍是同步调度，没有真正把“下一层权重 DMA”和“当前层 store”
重叠起来；这部分硬件能力已留好，是下一步软件优化入口。

### 4.11 DDR 读：RGB loader 与 tensor loader

RGB 输入只有 3 通道，但为了统一，顶层把 RGB 当 8 通道处理，用
[`gestureflow_hp0_rgb_loader.sv`](../innovation_npu/rtl/gestureflow_hp0_rgb_loader.sv)
读 DDR。

中间张量是 16/32/48 通道，用
[`gestureflow_hp0_tensor_loader_banked.sv`](../innovation_npu/rtl/gestureflow_hp0_tensor_loader_banked.sv#L10)
。它用 ring buffer 存 AXI 读回的 64-bit beats，等凑齐一个完整像素向量才交给
流引擎。这样避免每次都做宽移位，减少组合逻辑。

### 4.12 DDR 写：tensor writer

输出结果先写 output bank，再由
[`gestureflow_hp0_tensor_writer.sv`](../innovation_npu/rtl/gestureflow_hp0_tensor_writer.sv#L8)
按 AXI4 burst 写回 DDR。它支持：

- 连续向量合并成 burst；
- 2×2 池化后的写回；
- `valid_vector_bytes` 处理尾 tile 的字节掩码；
- stride 写回，让 16 通道物理 tile 能填到更宽的 NHWC 张量里。

### 4.13 GAP + FC：分类尾端

最后的 12×12×64 张量不需要再写回 DDR，而是由
[`gestureflow_hp0_gap_fc.sv`](../innovation_npu/rtl/gestureflow_hp0_gap_fc.sv#L11)
从 DDR 读 head 输出，在片上完成：

```text
全局平均池化 → 64 维向量 → 18 类 FC 点积 → 预测类别
```

GAP/FC 的 bias、requant multiplier、weight 都由 PS 通过寄存器写入。

### 4.14 AXI-Lite 控制寄存器

PS 通过 AXI-Lite 写寄存器配置任务。寄存器地址定义在
[`gestureflow_layer_chain_dmp_hp0_axil.sv`](../innovation_npu/rtl/gestureflow_layer_chain_dmp_hp0_axil.sv#L95)
附近，常用：

- `CONTROL`：bit0 复位，bit1 启动一层。
- `LAYER_MODE`：选择 RGB/16/32/48/pointwise/GAP-FC。
- `DMA_SOURCE/DMA_BYTES/DMA_PIXELS`：输入张量地址和大小。
- `STORE_DESTINATION/STORE_BYTES/STORE_CONTROL`：输出张量地址和写回方式。
- `QCFG`：输入/输出 zero point、requant 使能、ReLU 使能。
- `WEIGHT_DMA_*`：权重 DMA 控制。
- `WEIGHT_BANK_SELECT / PARAM_BANK_SELECT`：双 bank 选择。

## 5. PS 软件驱动：软硬件怎么握手

### 5.1 软件总体流程

PS 驱动在
[`gestureflow_hagrid18_dmp_main.c`](../innovation_npu/board_7020/software/gestureflow_hagrid18_dmp_main.c#L535)
的 `main()`。流程：

1. 关闭 ICache、把外设地址设为 device memory；
2. 检查 `MAGIC` 和 `VERSION`；
3. 准备一张内置测试图 `gf_rgb`；
4. 逐层配置权重、bias、requant；
5. 启动每层，等待 done；
6. 校验每层 FNV 和最终类别；
7. 写入 PROBE，供 XSCT 读取 FPS 和 cycles。

### 5.2 权重怎么到 PL

软件不逐字写所有权重，而是用 `weight_dma_load()`，把预打包的 C 数组地址交给
PL 的 weight DMA loader，由 PL 自己从 DDR 突发读入。

对应代码
[`gestureflow_hagrid18_dmp_main.c`](../innovation_npu/board_7020/software/gestureflow_hagrid18_dmp_main.c#L217)
。

预打包权重头文件在 `innovation_npu/board_7020/software/gestureflow_dmp_*_layer.h`。
它们由 Python 工具生成，不要手改。

### 5.3 一层是怎么启动的

`exec_conv_tile()` 在
[`gestureflow_hagrid18_dmp_main.c`](../innovation_npu/board_7020/software/gestureflow_hagrid18_dmp_main.c#L425)
：

1. `CONTROL=1` 复位上一状态；
2. 选择 param/weight bank；
3. 写 layer mode、QCFG、lane mask；
4. 预载权重和 bias/requant；
5. `launch_layer()` 写 DMA/store 参数，最后写 `CONTROL=2`；
6. `wait_layer_done()` 等待 done。

`launch_layer()` 在
[`gestureflow_hagrid18_dmp_main.c`](../innovation_npu/board_7020/software/gestureflow_hagrid18_dmp_main.c#L373)
。

### 5.4 为什么“done && !running”而不是只看 done

`wait_layer_done()` 在
[`gestureflow_hagrid18_dmp_main.c`](../innovation_npu/board_7020/software/gestureflow_hagrid18_dmp_main.c#L203)
。它等待：

```c
if ((status & GF_DONE_BIT) && !(status & GF_RUNNING_BIT)) return;
```

原因是硬件状态机中，`done` 可能和 `running` 在同一拍变化。如果只看 done，可能
在 `running` 还没清 0 时就启动下一层，导致 CONTROL 启动被 fault。这也是上一轮
调试得到的经验。

### 5.5 PROBE：性能是怎么测出来的

PS 把关键数据写到 `0xFFFF0000` 起始的 PROBE 数组，XSCT 再读出来：

- `PROBE[130]`：整帧 `XTime` ticks；
- `PROBE[131]/[132]`：权重相关 ticks；
- `PROBE[133]`：PL 总 cycles；
- `PROBE[10..26]`：逐层 cycles。

代码在
[`gestureflow_hagrid18_dmp_main.c`](../innovation_npu/board_7020/software/gestureflow_hagrid18_dmp_main.c#L696)
附近。

### 5.6 当前“端到端”的真实口径

当前没有接真实摄像头，输入是 C 头文件里的确定性测试图 `gf_rgb`。测试流程把
它当作“模拟摄像头帧”写入 DDR，然后跑完整网络，最后检查分类。因此 41.9 FPS
表示“DDR 测试帧 → 整网 → 类别”的端到端，不是真实摄像头传感器帧率。

## 7. 项目接管开发指南

### 7.1 改代码前先建立“可回退基线”

每次动手前：

1. `git status` 确认工作树；
2. `git log --oneline -3` 记住当前提交；
3. 跑一次最小回归，确认起点是好的；
4. 每次只改一个变量。

如果失败，先 `git checkout -- <file>` 回到可复现版本，不要带着坏版本继续堆。

### 7.2 三类修改的安全顺序

#### A. 改软件调度

风险低，但必须实板验证，不能只看编译通过。重点文件：

- [`gestureflow_hagrid18_dmp_main.c`](../innovation_npu/board_7020/software/gestureflow_hagrid18_dmp_main.c)

修改后先 `build_software_hagrid18_dmp_from_wsl.sh`，再上板看
`FINAL_RESULT=0x600D600D` 和 FPS。

#### B. 改 RTL 数值路径

风险高，必须先 Verilator：

```bash
bash innovation_npu/tests/run_gestureflow_layer_chain_dmp_body2_axil.sh
bash innovation_npu/tests/run_gestureflow_conv4x4_cin_same_stream_dmp_full_layer.sh
```

然后重新 Vivado 综合、布线、上板。

#### C. 改架构 / 资源 / 时序

不要立刻反复综合布线。先想清楚：

- 会多用多少 DSP / BRAM / LUT？
- 新关键路径可能在哪里？
- 能否用寄存器切开关键路径？
- 是否会引入 AXI 端口冲突？
- 是否能先用小 testbench 做行为验证？

### 7.3 常见性能优化入口

按“投入产出比”从高到低：

1. **软件权重 DMA 与计算重叠**：当前同步调度还有串行等待；硬件已支持双 bank。
   修法要点是启动后先确认 `running`，再等待 `done`，并检查 `STORE_STATUS`。
2. **层间 DDR 往返**：把 `pool3 → head1x1 → GAP → FC` 尽量放片上 relay。
3. **提高 requant 并行度**：当前是 4；可以试 8，但必须看时序。
4. **时钟频率 80→90/100MHz**：先优化结构和布局，不要靠空跑综合。
5. **Tile-Valid 稀疏门控**：手势图大量背景，可跳过空白 tile。
6. **事件驱动 / 渐进推理**：静止帧跳过，简单手势早退。

### 7.4 替换网络结构

如果换网络：

1. 先在 Keras 训练，得到 `.keras`；
2. 用量化脚本导出 INT8 TFLite；
3. 用 `innovation_npu/tools/export_hagrid18_all_layers_dmp.sh` 重新导出权重头文件；
4. 更新 `gestureflow_hagrid18_dmp_main.c` 的层参数和 golden；
5. 先 Verilator，再 Vivado，再实板。

权重导出工具入口：

- [`export_hagrid18_all_layers_dmp.sh`](../innovation_npu/tools/export_hagrid18_all_layers_dmp.sh)
- [`export_dmp_conv_layer.py`](../innovation_npu/tools/export_dmp_conv_layer.py)
- [`export_dmp_conv_golden.py`](../innovation_npu/tools/export_dmp_conv_golden.py)

### 7.5 更换数据集

数据集处理脚本在
[`datasets/tools/`](../datasets/tools/)。
重点是按“受试者”划分，而不是随机划分图片；否则测试集会泄漏同一人的相似帧。

### 7.6 排查时序违例

看 Vivado 报告：

```text
Post Placement Timing Summary WNS=...
Route 35-57 Estimated Timing Summary WNS=...
```

排查步骤：

1. 找到最差路径；
2. 看它是逻辑延迟还是布线延迟；
3. 如果逻辑级数多，插流水寄存器；
4. 如果是高扇出，复制寄存器或加 `max_fanout`；
5. 如果是布线拥塞，用 pblock 固定 MAC/BRAM 位置；
6. 确认 XDC 注释用 `#`，不要用 `//`。

### 7.7 排查板上 fault

看 `PROBE[2]` 错误码和 `PROBE[3]` 观测值，再对照
[`gestureflow_hagrid18_dmp_main.c`](../innovation_npu/board_7020/software/gestureflow_hagrid18_dmp_main.c)
里对应 `terminal_failure(...)` 的编号。

常见坑：

- 上一层的 done/running 状态残留；
- 权重 bank 读/写选择错误；
- 输入 DMA 未读完就开始权重 DMA，AR 通道冲突；
- 输出 writer 的 WSTRB 或 burst 长度错误；
- `STORE_STATUS[31:3]` 是字节数，不是 beat 数。

### 7.8 如何判断“这次优化是否成功”

必须同时满足：

- 功能：`FINAL_RESULT=0x600D600D`，所有层 FNV 匹配；
- 时序：`WNS>0`，最好离 0 有一定裕量；
- 资源：DSP、BRAM、LUT 在 7020 余量内；
- 性能：记录 PROBE，和上一稳定版本对比，不要只看一次波动。
