# 计划书“国、内外研究现状和发展动态”重审

## 1. 这份文档解决什么问题

这份文档只聚焦原始大创计划书里的这一节：

```text
3. 国、内外研究现状和发展动态
```

目标不是复述原文，
而是重新回答四个更实在的问题：

1. 这一节哪些内容有真实参考价值。
2. 哪些内容更像立项背景话术，不能直接拿来当项目路线依据。
3. 哪些外部一手资料能支持或修正原文判断。
4. 对当前 `coralnpu + 手势识别 + 上板` 主线，真正该吸收什么。

## 2. 总体结论先说清楚

对这节内容重审后的总判断可以先压成一句话：

```text
这节的“方向感”总体是对的，
但“可直接执行的信息密度”远低于“背景动机的信息密度”；
真正值得吸收的不是它列出的若干案例本身，
而是它背后的三类趋势：任务分层、低比特部署、数据流/复用主导的硬件优化。
```

更具体地说：

- `3.1 手势识别研究现状` 里最有价值的是“静态/动态、图像/关键点、端侧实时”的任务分层，
  不是那些没有给清晰出处的单个案例数字。
- `3.2 卷积神经网络加速现状` 里最有价值的是“量化 + 数据流 + 片上复用 + FPGA 可验证性”，
  不是泛泛地再讲一遍 GPU/ASIC/TPU 都很强。
- `3.3 Coral NPU 研究现状` 里最有价值的是“低功耗边缘、统一工具链、run-to-completion、
  integer-friendly”的平台定位，
  不是把 Coral 的平台宣传语直接等价成当前项目的可执行路线。

## 3. 对 3.1“手势识别研究现状”的重审

### 3.1.1 原文最可靠的部分：任务真的已经分成了三类

计划书这一小节虽然举例比较杂，
但它确实抓到了今天手势识别研究的三个主分支：

1. 静态图像手势分类
2. 动态视频/连续手势识别
3. 关键点 / skeleton / 多模态交互

这三类分法在外部一手资料里都能找到支撑。

#### 静态手势

HaGRID 论文说明，
静态图像手势识别并不是“小儿科 baseline”，
而是完整的设备交互任务入口。  
来源：

- HaGRID - HAnd Gesture Recognition Image Dataset  
  https://arxiv.org/abs/2206.08219

论文摘要明确说：

- 数据集中的 `18` 个手势都具有可解释的设备交互语义
- 虽然手势本身是静态的，但特意挑选成可进一步设计动态交互

这对当前项目非常关键：

- 我们现在先做 `HaGRID` 静态主线，不是退缩
- 反而是在最少变量条件下先把“识别精度、INT8、TFLite、NPU 周期、硬件热点”跑通

#### 关键点 / landmark

MediaPipe Hands 和 Gesture Recognizer 的一手资料说明，
Google 的 on-device 路线本身就大量依赖“检测 -> landmark -> 轻分类器”的分层管线。  
来源：

- MediaPipe Hands: On-device Real-time Hand Tracking  
  https://arxiv.org/abs/2006.10214
- Gesture recognition task guide  
  https://developers.google.com/edge/mediapipe/solutions/vision/gesture_recognizer
- On-device Real-time Custom Hand Gesture Recognition  
  https://arxiv.org/abs/2309.10858

其中 MediaPipe Hands 的摘要直接说明：

- pipeline 由 `palm detector` 和 `hand landmark model` 两个模型组成

Gesture Recognizer 官方文档进一步说明：

- 手势识别任务会同时输出手部 landmarks 和手势类别
- 手势分类 model bundle 实际上是
  - gesture embedding model
  - lightweight gesture classifier
- 官方还支持训练自定义 gesture classifier

这说明：

```text
关键点路线不是“旁门”或“只适合 demo”的轻量替代，
而是今天端侧手势识别的一条主流工程路径。
```

#### 动态连续手势

IPN Hand 和 DeepGRU / ST-GCN 这一类工作说明，
动态手势并不是只能走 RGB 视频 + LSTM 一种方法。  
来源：

- IPN Hand: A Video Dataset and Benchmark for Real-Time Continuous Hand Gesture Recognition  
  https://arxiv.org/abs/2005.02134
- DeepGRU: Deep Gesture Recognition Utility  
  https://arxiv.org/abs/1810.12514
- Spatial Temporal Graph Convolutional Networks for Skeleton-Based Action Recognition  
  https://arxiv.org/abs/1801.07455

IPN Hand 摘要直接给出：

- 数据集包含 `4,000+` 个手势样本
- `800,000` RGB 帧
- 包括静态和动态手势
- 关注连续无停顿的真实交互场景

DeepGRU 摘要直接强调：

- 它只使用 raw skeleton、pose 或 vector data

这组资料合起来说明：

- 动态手势确实值得做
- 但动态建模不等于默认 `LSTM`
- landmarks / skeleton / pose 序列是非常现实的轻量入口

### 3.1.2 原文最不可靠的部分：若干“成功案例数字”不能直接拿来做路线依据

计划书这一节里有不少类似：

- 某团队准确率 `97.9%`
- 某平台 `30FPS`
- 某方案推理速度提升 `5x`
- 某方法 `99.65%`

这些内容的问题不是一定错，
而是：

1. 原文里没有把论文、数据集、输入模态、评价指标讲清楚。
2. 同一“准确率”背后，可能对应完全不同难度的数据集。
3. 它们大多不能直接转成我们当前 CoralNPU 工作区的动作。

所以这类信息的正确用法只能是：

- 证明“这个方向在外部有人做”
- 不能证明“我们现在应该优先这么做”

对当前项目而言，
真正应该继承的是：

- 动态手势存在真实需求
- 关键点路线非常强
- 静态与动态需要分阶段推进

而不是直接拿那些百分比来驱动当前技术路线。

### 3.1.3 对当前项目最重要的吸收结论

从 `3.1` 这一节真正该吸收三条结论：

1. `HaGRID` 静态主线是合理的，不是偏题。
2. landmark / skeleton 路线必须进入正式对照，而不能长期只停留在文档候选。
3. 动态路线后续优先应比较 `GRU / TCN / graph family`，而不是默认先做 `LSTM` 硬件。

## 4. 对 3.2“卷积神经网络加速现状”的重审

### 4.1 原文里真正对当前项目有价值的部分

这一节虽然写了 FPGA、GPU、ASIC、TPU 四大类，
但对当前工程真正有路线价值的，
主要只有两类信息：

1. 低比特量化对部署的决定性意义
2. 数据流与片上复用对硬件效率的决定性意义

#### 低比特量化

LiteRT 官方文档明确说明：

- integer quantization 可把浮点数转成 8-bit 定点数
- 这对低功耗设备很有价值
- integer-only 加速器要求 end-to-end integer 模型

来源：

- Post-training integer quantization  
  https://developers.google.com/edge/litert/conversion/tensorflow/quantization/post_training_integer_quant

官方文档还明确给出：

- 需要 representative dataset
- 需要设置 `TFLITE_BUILTINS_INT8`
- 如果某些算子没有量化实现，就不兼容 integer-only 硬件

这和我们当前工程的现实是完全同向的：

- 真实训练
- 真实 INT8 量化
- 真实 TFLite 评测
- 再看 CoralNPU 映射

也就是说，
计划书这一节关于量化的重要性是对的，
而且当前项目已经沿着正确方向做了。

#### 数据流 / 片上复用 / 行级复用

这节原文里提到：

- 流水线
- 片上存储分层
- 数据流优化

这些词本身很泛，
但外部经典硬件文献把这件事讲得更清楚。

最重要的一篇是：

- Eyeriss: A Spatial Architecture for Energy-Efficient Dataflow for Convolutional Neural Networks  
  https://research.nvidia.com/publication/2016-06_eyeriss-spatial-architecture-energy-efficient-dataflow-convolutional-neural

该工作强调的不是“再加更多 MAC”这么简单，
而是：

- `row-stationary` 数据流
- 利用局部权重复用、激活复用
- 减少 partial sum 搬运

摘要里的核心句子就是：

- `row-stationary (RS)` 通过利用 filter、activation 和 partial sum 的局部复用来降低数据移动能耗

这对当前项目的意义非常直接：

```text
我们最近围绕 48x48 主体层做的 rowhandoff / row-base state / 输出驻留 /
空间复用 / 尾部控制收口，并不是偏门；
它其实比“继续抽象讨论 MAC 并行度”更接近经典数据流优化问题的核心。
```

### 4.2 原文里对当前项目帮助不大的部分

#### GPU 加速综述

这部分对当前项目几乎没有硬件路线价值。

它只留下一个工程层启发：

- 训练本身需要 GPU 资源

而这件事我们已经在本地实践中落实成：

- 训练优先在宿主 GPU 上跑

除此之外，
GPU 训练综述并不会帮助当前 CoralNPU 上板主线收敛。

#### ASIC / TPU 泛泛综述

这部分也更多是背景，不是动作指南。

它能说明的是：

- 专用加速器确实依赖低比特、片上存储、专用数据流

但它不能直接推出：

- 我们当前就该怎么改 `conv.cc`
- 我们当前就该怎么落 RTL

### 4.3 FPGA 文献对当前项目的真正作用

FPGA 相关文献和框架，
对当前项目最有价值的不是“直接拿来替换 CoralNPU 流程”，
而是提供板级验证方法论。

例如：

- FINN: A Framework for Fast, Scalable Binarized Neural Network Inference  
  https://arxiv.org/abs/1612.07119
- Benchmarking Quantized Neural Networks on FPGAs with FINN  
  https://arxiv.org/abs/2102.01341

它们说明：

- 更低比特会显著影响并行化空间
- FPGA 很适合做局部闭环、可观测、可定制的推理验证
- 量化和并行配置的组合，对最终吞吐影响很大

但这条经验在当前项目里的正确吸收方式是：

- 强化板级 trace/counter 与 integer-only 验证
- 不是切换到另一套全新的 FPGA 编译范式

### 4.4 对当前项目最重要的吸收结论

从 `3.2` 这一节真正该吸收的结论是：

1. `INT8` / integer-only 不是可选装饰，而是主流程前提。
2. 对当前 CoralNPU，数据流与数据搬运往往比“再加一点算力”更关键。
3. 48x48 主体层上的 rowhandoff、输出驻留、空间复用收口是合理方向。
4. FPGA 路线应该先做小闭环、可计数、可对账，而不是一步追 full demo。

## 5. 对 3.3“Coral NPU 研究现状”的重审

### 5.1 原文大方向是对的：Coral 确实适合做“低门槛可验证”的专用优化

这一节最靠谱的部分，
不是里面的宣传式措辞，
而是 Coral 平台定位本身：

- 低功耗边缘
- 统一开发生态
- 标量 + 向量/SIMD + 矩阵/MAC
- 适合 run-to-completion 风格推理

本地官方文档也支持这一点。  
来源：

- [coralnpu/doc/overview.md](/home/steveguo/coralnpu-gesture/coralnpu/doc/overview.md:1)

官方 overview 明确说明：

- CoralNPU 是一个带自定义 SIMD 指令和 ML accelerator 数据通路取向的 RISC-V 设计
- 前端是简单标量控制核
- 后端有向量核与 quantized outer-product MAC engine
- 采用 run-to-completion 风格

这意味着计划书把 Coral 选为载体，本身是合理的。

### 5.2 原文最容易带偏的部分：平台能力描述不能直接当当前工作区的已验证事实

计划书这节把 Coral 写得很强，
这本身没问题，
但容易让人误以为：

- 既然平台是为边缘 AI 设计的
- 那我们马上就该做大规模硬件扩展

这在当前工程里是危险的。

因为当前真正已验证的事实只有：

- 仓库能构建
- NPUSim/cocotb 能跑
- 我们已在 `conv.cc` 上形成 current best
- 我们已在工作区里找到 `rowhandoff mode=1` 这条唯一保留的硬件参考候选

而还没有验证的包括：

- 大规模 MAC 扩展是否真比控制/状态复用更值
- `LSTM` 是否真值得直接做成硬件子模块
- 更大 datapath 改造是否能比当前板级最小闭环更快落地

所以对 `3.3` 的正确读取方式应该是：

```text
CoralNPU 给了我们一个非常好的“可验证载体”；
但它不会替代我们自己做 profiling、回放、板级对账和路线收敛。
```

### 5.3 Coral 平台定位对当前算法选择的反作用

这一节再结合当前项目实测，
其实还能推出一个比计划书更具体的结论：

- Coral 官方生态支持 MobileNet / depthwise 这类模型
- 但这不等于 MobileNet 在我们当前任务和 kernel 画像下就是最优

当前本地实测已经很清楚：

- `MobileNetV2` 在正式数据与当前 NPU 画像下
  - 精度落后于 `3x3-heavy`
  - 周期也被 `1x1 pointwise` 主导拖慢
- `3x3-heavy` 主线反而同时赢下精度与模型级加速

所以 `3.3` 这一节正确吸收的不是：

- Coral 官方有 MobileNet 示例，所以主线一定走 MobileNet

而是：

- Coral 给了我们多条可映射路径
- 真正怎么选，要由当前数据集、量化和 NPU 实测结果来定

### 5.4 对当前项目最重要的吸收结论

从 `3.3` 这一节真正该吸收的结论是：

1. Coral 平台是好载体，这一点原计划书判断正确。
2. 但平台宣传能力不能替代当前工作区的局部实测。
3. 当前最合适的 Coral 项目推进方式仍然是：
   - 保住 official current best
   - 保住当前正式模型主线
   - 把 `rowhandoff mode=1` 推成板级最小闭环

## 6. 这一整节对当前路线的最终影响

把 `3.1 + 3.2 + 3.3` 合起来之后，
对当前工程路线的更新不应该是“推翻重来”，
而应该是下面这种更精确的重排。

### 6.1 继续保持不变的部分

- 正式算法主线仍是：
  `static_cnn_regularized_3x3_i96_e70_hagrid6_sample`
- official `conv.cc` current best 仍是软件保底线
- `rowhandoff_rowbase_recur mode=1` 仍是唯一保留的硬件参考候选

### 6.2 应该正式升格为并行方向的部分

#### 方向 A：更强的 plain-conv 候选

这一节加上外部资料，
进一步支持把下面这些候选正式做起来：

- `residual_3x3`
- `RepVGG-like`
- `MobileOne-like`

理由很清楚：

- 它们比 pointwise 主导模型更贴当前 CoralNPU 主收益区
- 它们与计划书“模型-硬件协同适配”的原意是同向的

#### 方向 B：landmark + 轻时序原型

这一节也支持把下面这条线正式做成最小闭环：

- MediaPipe / Hand Landmarker landmarks
- 静态：`MLP`
- 动态：`GRU / TCN`

它的意义是：

- 给动态方向一个低变量入口
- 真实判断 `LSTM` 是否还值得排优先级

### 6.3 应该明确降级的部分

#### 默认先做 LSTM 专用硬件

这一条现在必须从“计划书默认主线”降级为：

- 仅在动态 profiling 证明必要后再启用

#### 泛泛扫描更多加速器类型

继续泛讲 GPU/ASIC/TPU 强不强，
对当前工程帮助已经很小。

更值钱的是：

- integer-only
- 数据流
- 片上复用
- 板级可观测验证

## 7. 当前一句话结论

如果只针对“国、内外研究现状和发展动态”这一节做一句话收口，
当前最准确的判断应该是：

```text
这节最该保留的不是那些零散案例和性能数字，
而是三条已经被外部一手资料和当前项目共同支持的趋势：
先静态后动态、关键点路线必须并行量化、硬件优化重点应从纯 MAC 想象转向低比特与数据流复用。
```

这也意味着，
当前项目后续最正确的推进方式不是回到“大而全”的计划书叙述，
而是：

- 用静态主线继续保住当前硬结果
- 用 `rowhandoff mode=1` 推板级最小闭环
- 用 `RepVGG/MobileOne-like` 补更强 plain-conv
- 用 landmarks + `GRU/TCN` 补动态对照原型

这才是对计划书这一节最有价值的重新吸收。
