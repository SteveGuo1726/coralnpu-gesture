### 2.2 频率演进史（同一设计，逐步提频）

| 频率 | 端到端 | PL 纯计算 | 备注 |
|---|---|---|---|

### 2.3 逐层 PL cycle 画像（80 MHz，总 1,858,032 cyc）

| 层 | cycles | 相对理想开销 |
|---|---|---|
| conv0 | 304,693 | 107% |
| conv1 + pool1 | 459,594 | 56% |
| conv2a | 155,451 ×2 | 111% |
| conv2b + pool2 | 189,438 ×2 | 20–28% |
| conv3a | 57,607 ×3 | 56% |
| conv3b + pool3 | 66,352 ×3 | 20–28% |
| head 1×1 | 6,548 ×4 | **658%** ← requant 串行化的受害者 |
| gap_fc | 5,853 | — |

**理想基线**（8 输入 lane 的 group-walk，taps×groups×windows）约 1,164,672 cyc，
实测 1,858,032 ⇒ **总开销约 1.6 倍**。固定开销来源：MAC tile 每窗口 drain（约 8 级流水）
+ 窗口握手 + line-window 建立。全网络约 31,680 个窗口，纯 drain 约 253K cyc（13.6%）。

**下一步三大优化点**（按收益排序）：
1. **多窗口流水**（约 13%）：accumulator/activation_sum 双缓冲（ping-pong），消除每窗口 8 cyc drain。
   *已尝试两次均回退*，详见 §7.3。
2. **requant 并行度 1→4**（低风险，约 1%）—— **已完成**，就是当前 41.9 FPS 那一代。
3. 复查 conv2a（111%）为何比同 group 数的 conv1（56%）高。

## 3. 算法侧

### 3.1 任务与数据

- **输入**：96×96 RGB 手势图片
- **18 类**：`call, dislike, fist, four, like, mute, ok, one, palm, peace, peace_inverted,
  rock, stop, stop_inverted, three, three2, two_up, two_up_inverted`
- **数据**：HaGRID-v1 384p，18 类共 509,323 张，按 `user_id`（人物）隔离划分
  - 训练 357,748 / 验证 66,264 / 测试 85,311

### 3.2 为什么用知识蒸馏

MobileNetV3-Large 精度高但太大，7020 装不下。所以：
1. 先训**教师**：MobileNetV3-Large（ImageNet 预训练 + 微调）
2. 再训**学生**：4×4 小网络，除硬标签外还学教师的**软标签**（含类间模糊信息）

关键参数（`algorithms/scripts/run_train_hagrid18_student_distill.sh`）：
```text
--distill_alpha 0.35        软标签损失占 35%
--distill_temperature 3.0   温度，让教师分布更平滑
```

### 3.3 学生模型结构（务必记住）

`variant=regularized_plain`、`body_kernel_schedule=4,4,4`、`stage_channels=16,32,48`、
`head_channels=64`、`head_kernel_size=1`：

```text
输入 96×96×3
  Rescaling(1/255)                          # 仅浮点阶段
  3 个 stage，每个 = [Conv4×4 → BN → ReLU] ×2 → MaxPool(2×2, stride 2)
  head: Conv1×1 (48→64) + ReLU
  GAP  →  64 个数
  FC   →  18 个分类分数
  argmax → 手势类别
```

完整推理链路：
```text
RGB(96×96×3)
 → conv1_4x4_a (3→16) → conv1_4x4_b (16→16) → pool1 (→48×48×16)
 → conv2_4x4_a (16→32) → conv2_4x4_b (32→32) → pool2 (→24×24×32)
 → conv3_4x4_a (32→48) → conv3_4x4_b (48→48) → pool3 (→12×12×48)
 → head 1×1 (48→64) → GAP (→64) → FC (→18) → argmax
```

### 3.4 量化约定

- **对称 INT8**，`zero_point = -128`（输入输出都是 -128）
- **per-channel requant**（每个输出通道独立 scale/multiplier）
- 4×4 SAME padding：**上/左补 1，下/右补 2**
- 卷积 stride=1，池化 stride=2

## 4. 硬件架构（GestureFlow-NPU）

### 4.1 数据流

```text
                  ARM CPU (PS)
        AXI-Lite 下发：层尺寸 / 地址 / 量化参数 / 权重 / 启动
                          │
                          ▼
  ┌───────────────────────────────────────────────────────┐
  │           GestureFlow-NPU (PL, 80 MHz)                │
  │  HP0 读输入(DDR) ──► 行缓存 + 滑窗(SAME padding)        │
  │                          ▼                            │
  │              DMP INT8 MAC 阵列（权重驻留）              │
  │                          │ INT32 部分和                │
  │                          ▼                            │
  │               requant + ReLU（量化回 INT8）             │
  │              输出 bank ──► HP0 写回 DDR                 │
  │  最后一层走 GAP→FC→argmax，直接出分类结果，不写 DDR      │
  └───────────────────────────────────────────────────────┘
                          │ 结果/状态
                          ▼
                  ARM 读寄存器得到 class + FNV 校验
```

**分工口诀**：PS 下发「命令/参数/权重」，PL 用 HP0 自己搬「大数据」，算完写回 DDR。
**CPU 不参与逐像素搬运** —— 这是借鉴 CoralNPU 的核心思想（控制-计算解耦）。

### 4.2 关键 RTL 模块（构建用 21 个 .sv，约 5,700 行）

| 模块 | 作用 |
|---|---|
| `gestureflow_line_delay_bank / _vector_bank` | 行延迟（行缓存） |
| `gestureflow_line_window / _vector` | 滑窗生成 |
| `gestureflow_same4x4_cin_window` | 4×4 SAME padding 窗口 |
| `gestureflow_weight_bank` | 权重驻留 bank（双 bank 乒乓） |
| `gestureflow_mac_tile_dmp` | **DMP MAC 核心**（16 out × 8 in） |
| `gestureflow_conv4x4_cin_same_stream_dmp` | 8 lane SAME 流式卷积引擎 |
| `gestureflow_requant_relu` | per-channel requant + ReLU（`REQUANT_PARALLEL_LANES=4`） |
| `gestureflow_output_bank*` | 输出缓冲 / relay 装载 |
| `gestureflow_hp0_rgb_loader` / `_tensor_loader*` | HP0 输入装载 |
| `gestureflow_hp0_weight_dma_loader_dmp` | **DMP 专用权重 DMA**（把 DDR 连续 6 个 32bit 组装成 192bit weight-bank word） |

单时钟域，内部无 PLL/MMCM。
标识：`MAGIC = 0x47464E50`（"GFNP"）、`VERSION = 0x00050001`。

## 5. 核心创新：DMP 双乘打包

> 这是本项目的**架构级突破**，也是论文叙事的主干。

### 5.1 动机

Zynq-7020 只有 **220 个 DSP48E1**，整网已用 191 个。原 MAC 是 `32 输出 × 4 输入`，
**每个 DSP 每拍只做一次 8×8 乘加**。DSP 接近耗尽，无法靠加宽阵列提升吞吐。

### 5.2 原理：16 bit 间距打包

DSP48E1 的乘法器是 **25 bit(A) × 18 bit(B) 有符号**。把两个无符号 8bit 权重按
**16 bit 间距**塞进 A，一个无符号 8bit 激活放进 B：

```text
A = w'0 + (w'1 << 16)        // 两个权重，间距 16bit，A < 2^24 仍为正
B = a'                       // 一个激活，零扩展到 18bit
product = A × B
        = w'0·a'             // 落在 bit[15:0]，最大 65025 < 2^16
        + w'1·a'·2^16        // 落在 bit[31:16]
```

**关键**：每个无符号 8×8 乘积最大 65025，**恰好 16 bit**，所以 16 bit 间距能让
两个乘积干净分离、不串扰。（8 bit 间距会串扰。）

### 5.3 有符号 → 无符号的偏移

有符号 INT8 转无符号只需**翻转符号位**：`a' = a + 128`，`w' = w + 128`。

```text
out[oc] = Σ a'·w'[oc]  −  128·Σa  +  bias'[oc]
bias'[oc] = bias[oc] − 128·Σw[oc] − 16384·N        // 导出时预计算，硬件零开销
```

三个修正项：
1. `Σ a'·w'[oc]` —— DMP 打包乘积累加（硬件正常做）
2. `−128·Σa` —— 有符号激活的**总求和**（所有输出通道共享，只需一个累加器）
3. `bias'[oc]` —— 折叠后的 bias（工具预计算）

### 5.4 收益与约束

- 同样 128 个 DSP，`32 输出 × 4 输入` → **`32 输出 × 8 输入`（256 乘积/拍）**，吞吐翻倍
- **重要约束**：4-lane DMP 兼容模式在 `OUT_LANES=32` 主链上多占约 5000 FF，
  Vivado 报 `9635 slices required > 9040 available`，**装不进 7020**。
  ⇒ 整网 DMP **必须走 8-lane 数据通路**，并同步改权重 DMA 与软件，不能只换 MAC tile。

| 层级 | 测试 | 结果 |
|---|---|---|
| 单元 | `tb_gestureflow_mac_tile_dmp.sv` | 打包乘积高/低 16bit 与朴素有符号 INT8 **位精确一致** |
| 引擎 | `tb_..._conv4x4_cin_same_stream_dmp.sv` | 64bit 参考模型逐点比较**每一个输出向量** |

## 6. 软件侧

**板级驱动**：`innovation_npu/board_7020/software/gestureflow_hagrid18_dmp_main.c`（712 行）

| 检查项 | 结论 |
|---|---|
| 依赖的 Xilinx API | `Xil_In32/Out32`、`Xil_DCacheFlushRange`、`XTime_GetTime`、`xil_printf`、`usleep` |
| PS 专有寄存器 | ✅ 无 SLCR / devcfg / GIC / PS7 专用寄存器 → 移植性好 |
| `PROBE_BASE = 0xFFFF0000` | Zynq-7000 与 ZynqMP 都合法（UG1085：ZynqMP OCM = `0xFFFC0000–0xFFFFFFFF`，OCM3 = `0xFFFF0000`） |
| `FINAL_RESULT = 0x600D600D` | **软件写的**（`probe[index]=value`）；NPU 只写 DDR、不写 OCM |
| 结果/失败码 | `0x600D600D` 成功；`0xBAD0BAD0` 失败；`0xDA7AAB01/02` 其他失败 |
| 编译期符号 | `GF_BASE`（7020=`0x43C00000` / ZCU104=`0xA0000000`）、`GF_FAST_RELEASE` |

**已知坑（记录在交接日志里）**：
- **lane 宽度必须与 bitstream 一致**：构建回退到 `OUT_LANES=16` 但软件仍是 32-lane 调度时，
  权重 DMA 触发 `0x4D01` fault，且**与频率无关、极易误判成时序问题**。
- **HP0 是非相干口**：NPU 写完之后、CPU 读之前是否需要 invalidate，需按实际平台复核。

## 7. 关键历史结论（避免重犯）

### 7.1 项目自述的「已确认的错误判断」

| 曾经的判断 | 实际 |
|---|---|
| 260 字符 Windows 路径限制是根因 | ❌ 缩到 ~120 字符照样复现 |
| IP 的 OOC 综合流程坏了 | ❌ 关掉 OOC 后照样复现 |
| `launch_runs` 的 run 包装是元凶 | ❌ 会话内 `synth_design` 照样复现 |
| 网盘/磁盘/WSL 干扰 | ❌ C 盘干净目录照样复现 |
| 自打包 IP 是根因 | ❌ 7020 母本用打包 IP + OOC 全绿 |
| **`update_compile_order` 顺序错误** | ✅ **真根因（已修）** |
| Module Reference 是更优路线 | ❌ 自创路线，离开两个参照系；SV 顶层不被接受（`[filemgmt 56-195]`） |

**正确顺序（本机已跑通脚本给出）**：
```
add_files → set_property top <top> → update_compile_order → launch_runs impl_1 -to_step write_bitstream
```
`set_property top` 必须在 `update_compile_order` **之前**。反了会把够不到的源文件
全部标 `AutoDisabled=1` 并**持久化进 `.xpr`**，综合随即报
`[Synth 8-439] module 'system_wrapper' not found`。

### 7.2 多窗口流水（性能最大头，两次尝试均回退）

已定位的根因：
1. **`held_window` 单缓冲**：放宽 ready 后下一窗口会在 `mac_active==1` 时覆盖
   `held_window`，而当前窗口还在从它取激活 → 算错。修法：hold 仍要求 `!mac_active`。
2. **retire 竞态**：retire 输出必须门控 `!result_valid`，且 `retire_valid` 要在
   结果真正写出的那一拍才清。
3. **`busy` 单标志失效**：会被上一窗口 retire 提前清零 → 改 2bit `windows_active` 计数器
   （start +1、result 写出 -1，`busy = windows_active != 0`）。
4. **第四处根因未定位**：修完前三处后，pointwise 与 spatial 全层都在
   **第一行最后一列**（pointwise y=0 x=11、spatial y=0 x=95）出现 probe 偏差，
   其余列正确 ⇒ 与**行边界/窗口切换**相关。
   下一步入口：A/B 测试 `spatial_window_ready` 的各种门控组合；
   在行边界逐拍 dump `window_valid / spatial_window_ready / held_row / held_column /
   output_row / output_column`。

### 7.3 权重 DMA 与计算重叠（已隔离回退）

尝试把「下一 tile 权重 DMA + bias/requant 参数 bank 写入」与当前层 store 尾段重叠，
遇到上一层 `done`/`STORE_STATUS` 残留导致提前进入 proof 的竞态。
**为不破坏稳定代，软件已回退到原同步调度**，RTL 能力保留但暂不接入。
下次入口：先确认 `running` 已置位再等 `done`，并把 `STORE_STATUS` 的 busy/done
一起纳入完成条件。

### 7.4 其他已证实的技术事实

| 项 | 结论 |
|---|---|
| `set_property CONFIG.X` 对不存在的属性 | **静默忽略、不报错** ⇒ 必须 dump 实际引脚验证，不能凭"设成功"判断 |
| ZynqMP 从口使能属性名 | `PSU__USE__S_AXI_GP0 → S_AXI_HPC0_FPD`；`GP2 → S_AXI_HP0_FPD`（本项目用这个） |
| `proc_sys_reset` v5.0 的 `C_EXT_RESET_HIGH` | **只读**（实测=1），而 `pl_resetn0` 低有效 → 已插反相器 |
| ZCU104 板卡预置 | PL0 **默认已开且 = 100 MHz**（源 IOPLL）；`M_AXI_GP0/GP1` 都开；**`S_AXI_GP*` 完全不存在**，必须显式开 |
| ZCU104 wrapper 无端口 | **正确**。ZynqMP 的 DDR/固定 IO 是 PS 专用引脚，不走 fabric（7020 的 DDR 走 fabric，所以端口多） |
| RTL 的 `aclk` `FREQ_HZ` | ⚠️ **硬编码 `80000000`** → 打包 IP 时必须覆盖成实际 PL 频率并设 `value_resolve_type user` |
| `s_axi_*` 缺 `X_INTERFACE_INFO` | 依赖打包时按端口名推断 AXI4-Lite（7020 已验证可行） |

## 7A. 项目的架构纪律（读完《7020帧率优化方案》《权重驻留的架构真相》后补）

> 这两份文档是项目的"价值观"来源，比任何性能数字都重要。**接手者必须先接受这些门禁。**

### 7A.1 六条主线架构硬门禁（`7020帧率优化完整方案…_2026-08-21.md` §1.4）

1. **权重生命周期门禁** —— 模型未切换时，连续帧**不得**再通过 AXI-Lite 写权重/bias/requant 参数。
   权重必须在模型加载阶段一次进入 PL 本地 bank，或由 PL 的 AXI master 从 DDR 自动搬入。
   硬件必须提供权重版本号/指纹、命中计数、实际装载字节数、装载 fault。
2. **控制边界门禁** —— PS **不得**逐输出 tile 下发 `WCTRL/WDATA/BIDX/RQ*`，也不得为每个 tile
   单独发启动。PS 只提交**帧描述符或 doorbell**；PL 自主完成 tile 顺序、Cout 分块、pool、
   量化和结束状态。旧寄存器 ABI 只保留为 debug/回退。
3. **CoralNPU 微架构对齐门禁** —— 必须真正落地可编程控制前端、向量/矩阵后端解耦、
   片上状态驻留、统一存储访问、命令队列思想。**不能**把固定卷积外设经 AXI-Lite 挂在 ARM 旁边
   就称为"协同设计"。自研扩展必须标 `PROJECT_LOCAL_SELF_RESEARCH_NOT_GOOGLE_OFFICIAL`，
   **不能冒充上游 RTL**。
4. **数据流门禁** —— 每层必须记录 DDR 读写字节、AXI burst 数、MAC 空闲周期、片上命中率、
   中间张量写回次数。**只报 MAC/cycle 而不报数据搬运与 PS 开销，不构成性能结论。**
5. **连续帧门禁** —— 至少验证连续两帧：第一帧允许 cold miss，**第二帧权重写入必须为零**
   （或仅必要的 tile cache miss），且帧间 FPS/状态可重复。端到端 FPS 以**完整墙钟**为准。
6. **创新性门禁** —— "加 MAC 数量、用长 burst、加行缓存、用 INT8"本身**不构成创新**。
   创新必须落在：资源受限下的跨帧权重驻留、PL 自主 tile/层调度、层间局部数据直通、
   可配置数据流与性能模型闭环。任何"突破业界"的结论必须给出**同硬件、同模型、同精度、
   同输入**的可复现实测对照。

### 7A.2 一条重要纠错：跨帧权重驻留在当前硬件上**不可能**

《权重驻留的架构真相_2026-08-26.md》：

- MAC tile 的权重 SRAM 总共只有 **约 32 KB**（每输出 lane `ADDR_W=9` → 512×32bit = 2KB，
  16 lane = 32KB，分 2 个 bank 各 16KB）
- 整网权重合计 **约 200 KB**（conv3b 一层就 100KB）
- ⇒ **差约 6.25 倍**，单 bank 连最大的一层都装不下
- 而且当前软件里的 `weight_prepare()/weight_commit()` 指纹驻留是**空转**：
  硬件 `weight_resident_key` 只有**一个槽位**，每层 fingerprint 都不同 ⇒ 必然 miss；
  双 bank 也从未被软件使用（`weight_bank_select` 没在 `load_*` 里设置）

**纠正后的正确策略**：
1. **短期（优先级最高）**：把权重装载从 **AXI-Lite 逐字写**改成 **PL DMA burst**（HP0）。
   实测 114 ms 主要来自 conv3a/conv3b（约 150KB）的 `Xil_Out32(WCTRL/WDATA)` 逐字写。
   硬件已有 `gestureflow_hp0_weight_dma_loader`，但板级软件**没用它**。
   预计可把 114 ms 压到 **1~5 ms** 量级。
2. **中期**：把 relay/output bank 省下的 BRAM 还给权重 SRAM。
   当前 `output_bank` 是 `2×16384×128bit`，OOC 用 `RAMB36=224`，**严重超配**；
   改成 K 行 ring 后可释放大量 BRAM，才可能谈真正的跨帧常驻。

> **一句话**：不要再按"软件打开驻留开关就能 2.62→3.42 FPS"去改。
> 板上第一优先动作是把权重装载换成 PL DMA burst。

### 7A.3 一条已修复的确定性浪费（写进周期模型的范例）

RGB 首层只有 3 个有效输入通道（第 4 lane 用 `input_lane_enable=4'b0111` 屏蔽），
但旧代码对所有非 40/80 通道模式都给出 **4 个输入组**，等于做了 4 倍的输入通道组调度：

```text
(4 - 1) 组 × 16 个 4×4 tap × 9,216 个空间窗口 = 442,368 cycles   ← 纯浪费
```

已修正为：RGB=1 组、16 通道 body=4 组、40 通道=10 组、80 通道=20 组。
这类"能精确算出浪费多少周期"的分析方式，是本项目做优化的标准姿势。

### 7A.4 性能数字的口径纪律（务必区分）

| 口径 | 含义 | 例 |
|---|---|---|
| **PL 纯周期** | PL 内部 cycle counter，只看计算 | `PROBE[133]` |
| **IP start-to-done** | 从启动到 done 的 PL 墙钟 | — |
| **PS 端到端** | 整帧 global-timer ticks，含 PS 调度/搬运 | `PROBE[130]` |

三者**不能混用**。历史上 25MHz 版：整帧 381.37 ms，其中**权重装载就占 91.74 ms**；
PL 纯周期 190.29 ms。所以"权重装载占了 PS 端开销的很大一块"才是当时真正的瓶颈。

## 8. 7020 → ZCU104 迁移（当前主线）

### 8.1 为什么迁移

7020 已到 DSP/布线瓶颈；ZCU104（XCZU7EV）资源大得多：

| 资源 | ZCU104 用量 | 可用 | 占比 |
|---|---|---|---|
| LUT | 31,921 | 230,400 | **13.85%** |
| FF | 50,681 | 460,800 | 11.0% |
| DSP | 134 | 1,728 | 7.75% |
| RAMB36 | 95 | 624 | 15.2% |
| **URAM** | **0** | **96** | **0%** |

（含 PS + 2×SmartConnect + reset + NPU。纯 NPU 单看 LUT 仅 **7.49%**）

**⇒ 约 90% 逻辑、92% DSP、100% URAM 空闲**，为"吃满资源提性能"留足空间。

### 8.2 已完成的 ZCU104 工作

| 阶段 | 状态 |
|---|---|
| JTAG 链路验证（`xczu7_0` IDCODE `0x14730093`、`arm_dap_1` `0x5BA00477`） | ✅ |
| LED bring-up（300MHz 差分时钟 + IBUFDS + 28bit 计数器，`WNS +2.619ns`） | ✅ |
| GestureFlow 全网络 bitstream + XSA | ✅ |
| 裸机 NPU 跑通（`0x600D600D`，**36.96 FPS**） | ✅ |
| PetaLinux 定制（USB3 + UVC）—— `BUILD_RC=0`，`BOOT.BIN` 21.1 MB / `image.ub` 9.97 MB / `rootfs.ext4` 430 MB | ✅ 构建完成 |
| Linux 用户态 NPU 驱动（`gf_npu.c`）+ 摄像头链路（`gf_camera.c`） | ✅ 代码就位，已过静态门禁 |
| 烧 SD 卡 → 上板验证（V1–V6） | ⬜ 待板子上电 |

**ZCU104 实测**：`frame_ticks = 2,705,924 @100MHz = 27.06 ms → 36.96 FPS`；
`PL 计算 = 1,702,205 cyc @100MHz = 17.02 ms`；**CPU 侧开销 10.04 ms（占 37%）**；
时序完全收敛 `WNS +2.751ns @100MHz`（理论 ≥137 MHz 仍可收敛）。

> **CPU 侧那 10 ms 是当前最大瓶颈**，根因高度指向 `main.c` 里的
> `Xil_SetTlbAttributes(<buf>, DEVICE_MEMORY)` —— 把所有工作缓冲设成 Device 内存
> （非缓存+强序）。改成 Normal cacheable + 精确 flush/invalidate 是最大杠杆。
>
> **Linux 侧换了一条路**：缓冲区经 `/dev/mem` 映射为**普通非缓存**（不是强序设备内存），
> 且把逐像素拷贝改成 `memcpy`。**V4 步骤必须实测新的 CPU 侧耗时并与 10.04 ms 对比** ——
> 这是硬门禁要求的"分离报告 PL 与 PS 开销"。

### 8.3 ZCU104 关键工程事实

### 9.4 另几个 PetaLinux 配置坑（都已修，详见 `plnx/PITFALLS.md`）

| 坑 | 现象 | 正确做法 |
|---|---|---|
| `CONFIG_YOCTO_PARALLEL_MAKE` 格式 | `ValueError: invalid literal for int() with base 10: '-j8'` | **填纯数字 `"8"`**。`gen_plnx_machine.py` 自己会拼 `"-j %s"` |
| `package-management` 归属 | `ERROR: Nothing RPROVIDES 'package-management'` | 它是 **Image Feature**，正确写法 `CONFIG_imagefeature-package-management`，**不能放进 `user-rootfsconfig`** |
| **DWC3 改成 host-only** | `undefined reference to 'dwc3_gadget_exit_hibernation'`（vmlinux 链接失败） | **保持 DUAL_ROLE**。Xilinx 内核 `core.c:2104/2399` 无守卫调用 gadget 专有函数，host-only 时那个文件不编译 |
| Vitis 的 `app build` 在 xsct 批处理里挂死 | 无输出、无 CPU | 别用它；本工程改走 Yocto recipe |

**共同教训**：这几个坑有 3 个是**照直觉/照抄教程写配置**、没先查生成逻辑或符号归属造成的。
动任何 Kconfig 符号前先做两件事：① grep 生成逻辑或源码消费点；② 确认它是
recipe / image feature / kernel config 中的哪一类。

**另一个反直觉事实**：kernel config fragment 是**按内容校验和**的，
**连只加注释都会触发一次 25 分钟的内核重编**。所以"本来就对、不要修"的清单
（`CONFIG_DEVMEM=y`、`clk_ignore_unused` 已在 bootargs、`v4l2-ctl`/`lsusb` 已在 rootfs 等）
写进 `plnx/PITFALLS.md`，**不写进 `kernel_uvc.cfg`**。

### 9.5 用户态 NPU 访问：定案方案（已实现，代码在 `board_zcu104/linux/`）

**访存**：寄存器 `0xA0000000`（1 MB）+ 缓冲区 `0x70000000`（16 MB）都走 **`/dev/mem` + `mmap`**。

设备树加一段预留：

```dts
reserved-memory {
    npu-buffers@70000000 { reg = <0x0 0x70000000 0x0 0x1000000>; no-map; };
};
```

- **`no-map` 是关键**：不加就还是 System RAM，`devmem_is_allowed()` 会拦掉；加了则被
  `memblock_remove` 摘出内核 RAM 映射 → 可 map，且内核永远不会占用它。
- ARM64 上 `/dev/mem` 对**非 RAM** 地址返回**非缓存**映射 ⇒
  寄存器区与缓冲区都不经 cache ⇒ **整条 HP0 非相干链路上不需要任何 cache flush/invalidate**。
  这正面回答了旧版本这里写的"NPU 写后需 invalidate、读前需 flush"——**本方案把那个问题消除了，而不是去管理它**。
- 已实测：`CONFIG_DEVMEM=y` 与 `# CONFIG_STRICT_DEVMEM is not set` **本来就在**内核里，无需改内核配置。
  回退方案是 UIO（`CONFIG_UIO_PDRV_GENIRQ=m` 也可用），届时只换 mmap 的 fd 与地址来源。

**⚠️ 最容易搞错的一点：输入的 −128 重定心是 PL 做的，驱动只写原始 uint8。**

```verilog
// rtl/gestureflow_hp0_rgb_loader.sv:5,58-60
// pixels. RGB is recentered to q=u-128 before it reaches the convolution.
assign pixel_rgb[0] = {~byte_fifo[7], byte_fifo[6:0]};   // = XOR 0x80 = u-128
```

⇒ **软件绝不能自己减 128**。搞错的话板上会表现为"能跑但类别全乱"。

**预处理链**（`algorithms/static_cnn/train_static_cnn.py:1041`）：
`Image.open(p).convert("RGB").resize((96,96), Image.BILINEAR)` —— **直接拉伸、不裁剪、不保长宽比**；
且 PIL 的 BILINEAR 缩小是**抗锯齿**的。驱动用**面积平均**（box）近似（最近邻会严重混叠）。

**诊断工具**（`images/linux/rootfs.ext4` 里已含）：`lsusb`（enumeration）、
`v4l2-ctl --list-devices/--list-formats-ext`（格式/分辨率）、`dmesg`。

**上板第一步永远是 `gf_npu_probe`**：它跑内置参考图并逐层校验，**必须 `RESULT: PASS`**。
在它通过之前，`gf_camera` 报出的任何类别都不算数。

因此 remote 的 URL 故意分开：
```
fetch = https://github.com/SteveGuo1726/coralnpu-gesture.git
push  = git@github.com:SteveGuo1726/coralnpu-gesture.git
```

**内容只在一端产生时**用对应方向，不要两端各自 commit 同一批文件（会出现
"一端已跟踪、另一端未跟踪"的 pull 冲突）：

```bash
bash sync_repo.sh ubuntu-push    # Ubuntu 提交并推送
bash sync_repo.sh win-pull       # Windows 拉取（先 git clean 未跟踪副本）
bash sync_repo.sh win-to-ubuntu  # 把 Windows 端新写的文档拷进 Ubuntu 工作树
bash sync_repo.sh status         # 看三端状态
```

### 10.3 WSL 性能铁律

且会被反复读）。先 `cp` 到 ext4（`$HOME`）再处理。
PetaLinux 安装包（3.01 GB）就是这样被反复读了好几遍，慢了十几分钟。

## 13. 未决问题与下一步

### 13.1 硬件/性能方向

1. **多窗口流水**（收益最大，约 13%）—— 第四处根因未定位（行边界偏差），已两次回退
2. **消除 CPU 侧 10 ms 开销**（ZCU104）—— 把 Device 内存改成 cacheable + 精确 flush
3. **ZCU104 提频**：100 MHz 下 `WNS +2.751ns`，理论 ≥137 MHz 仍可收敛
4. **吃满 ZCU104 资源**：URAM 完全未用（96 个），适合做权重缓存

### 13.2 摄像头方向（进行中）

```
P1 裸机 NPU 上板           ✅ 已完成（0x600D600D，36.96 FPS）
P2 PetaLinux 定制          🔄 构建中（USB3 + UVC）
P3 烧 SD 卡 + 改 SW6 → 启动 → 验证 /dev/video0
P4 用户态 NPU 驱动（/dev/mem + non-cacheable 缓冲）
P5 V4L2 抓帧 → 预处理 → NPU → 手势，实时循环
```

### 13.3 需要拍板的问题

- ZCU104 的 PL 目标频率定多少（当前 100 MHz 有 2.75ns 余量）
- 摄像头帧格式（建议先 YUYV）
- 是否把 Windows 工作区正式纳入仓库（**已完成**）

## 14. 术语速查

| 术语 | 含义 |
|---|---|
| **PS / PL** | 处理器系统（ARM CPU）/ 可编程逻辑（FPGA 部分） |
| **AXI-Lite** | 轻量控制总线，PS 读写 PL 寄存器 |
| **AXI HP0** | 高性能从口，PL 主动读写 DDR（本项目用 `S_AXI_HP0_FPD`，**非相干**） |
| **DMP** | Dual-Multiply Packing，一个 DSP48E1 完成两次 INT8 乘加 |
| **requant** | 重定标：INT32 部分和压回 INT8（per-channel scale） |
| **GAP / FC** | 全局平均池化 / 全连接 |
| **FNV-1a** | 哈希校验，用于逐层比对硬件与 TFLite golden |
| **WNS / WHS** | 最差建立/保持裕量；>0 表示时序收敛 |
| **OOC** | Out-of-Context 综合，IP 单独综合 |
| **BD** | Block Design，Vivado 的图形化 IP 互连设计 |
| **XSA** | 导出的硬件描述（含 bitstream），喂给 Vitis/PetaLinux |
| **UVC** | USB Video Class，免驱摄像头的标准 |
| **DTG** | Device Tree Generator，PetaLinux 用来生成设备树 |
| **sstate** | Yocto 的共享状态缓存，复用预编译产物加速构建 |
| **CMA** | Contiguous Memory Allocator，物理连续内存 |
