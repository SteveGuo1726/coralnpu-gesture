## 3. 当前 MAC 单元的准确结构判断

核心参考文件：

- `/home/steveguo/coralnpu-gesture/coralnpu/hdl/verilog/rvv/design/rvv_backend_mac_unit.sv`
- `/home/steveguo/coralnpu-gesture/coralnpu/hdl/verilog/rvv/design/rvv_backend_mulmac.sv`
- `/home/steveguo/coralnpu-gesture/coralnpu/hdl/verilog/rvv/inc/rvv_backend_define.svh`

当前应写死的判断：

1. 当前这条 `MAC` 单元是 **RVV 向量乘加单元**，不是 `VME` 外积矩阵阵列。
2. `MAC` 的主要覆盖对象是：
   - `VMACC`
   - `VMADD`
   - `VWMACC`
   - `VSMUL`
   - 以及相关宽化、符号变体
3. `rvv_backend_mulmac.sv` 当前默认只实例化：
   - `NUM_MUL = 2`
   - 也就是两路 `MUL/MAC` 执行单元
4. 当前 `MAC` 路径对 `vd` 的依赖是真实存在的：
   - 对 `VMACC / VMADD` 一类指令，`vs1 / vs2 / vs3(vd旧值)` 同时参与运算
   - 这会直接增加 `VRF` 读口压力
5. 所以当前主链对“卷积、全连接、小型门控”的支持，本质上还是：
   - 靠向量寄存器搬运
   - 靠向量乘加逐批完成
   - 不是“天生就有独立稠密矩阵后端”

## 4. 当前 VRF 的准确结构判断

核心参考文件：

- `/home/steveguo/coralnpu-gesture/coralnpu/hdl/verilog/rvv/design/rvv_backend_vrf.sv`
- `/home/steveguo/coralnpu-gesture/coralnpu/hdl/verilog/rvv/design/rvv_backend_vrf_reg.sv`
- `/home/steveguo/coralnpu-gesture/coralnpu/hdl/verilog/rvv/design/rvv_backend_dispatch_operand.sv`
- `/home/steveguo/coralnpu-gesture/coralnpu/hdl/verilog/rvv/inc/rvv_backend_define.svh`

当前应写死的判断：

1. 当前 `VRF` 是：
   - `NUM_VRF = 32`
   - 每组宽度为 `VLEN`
2. 默认官方主链是：
   - `VLEN = 128`
3. `VRF` 当前写回方式是：
   - 从退休阶段合并写回
   - 支持按字节写使能
4. `VRF` 当前读出方式是：
   - 给 `dispatch` 提供多读口
   - `DISPATCH3` 配置下有 `NUM_DP_VRF = 6`
   - 非 `DISPATCH3` 配置下有 `NUM_DP_VRF = 4`
5. `dispatch_operand` 代码已经能直接看出，第三个发射位的向量源操作数并不是“天然独立富余”的：
   - 它要根据前两个微操作的类别去复用前面已经读出的寄存器口
   - 说明当前瓶颈不只是“寄存器总数够不够”，更是“读口和同周期供数能力够不够”

## 5. 这对算法选型的直接含义

### 5.1 对静态图像分支

当前项目里的几个关键事实要连起来看：

- 官方普通卷积公开主链当前最成熟的特化偏 `4x4 standard conv`
- 官方深度卷积公开主链当前对 `3x3 depthwise` 已真实跑出显著收益
- 当前项目静态最高系统准确率仍然来自：
  - `RepVGG` 图像分支
  - 加 `landmark MLP` 分支融合

因此当前静态图像支线最合理的方向仍然是：

1. 不再把“全网纯 `3x3 standard conv`”当唯一硬件主线；
2. 继续保留 `3x3` 图像强基线与 `RepVGG` 高精度图像线；
3. 后续新空间主线优先探索：
   - 主体偏 `4x4 standard conv`
   - 局部保留必要 `3x3 depthwise`
   - 避免重新掉进大量 `1x1 pointwise` 主导的结构里

### 5.2 对 landmark MLP、全连接层和动态手势

当前必须认清：

- `landmark MLP`
- `FC`
- `GRU gate`
- 以及后续可能的 `TCN` 中部分 `1x1`/投影层

这些都更偏 **稠密矩阵型负载**，而不是空间卷积型负载。

所以：

1. 继续做 `tile/VME` 扩展是必要的，不能放弃；
2. 但在 `tile` 系统级还没完全坐实前，不能把所有这类负载都强塞回空间卷积支线；
3. 当前 `MAC + VRF` 侧要先补的是“更适合小型稠密层”的供数与累加能力，而不是先盲目加更多卷积特化壳子。

## 6. 当前最该优先扩的不是“VRF 数量”，而是三件更关键的事

### 6.1 第一优先级：降低 MAC 对 VRF 三源读取的压力

当前 `VMACC/VMADD` 类路径需要：

- `vs1`
- `vs2`
- `vd旧值 / addsrc`

这会直接把 `VRF` 读口吃紧。

所以第一优先级不是先把 `NUM_VRF` 从 `32` 继续加大，而是先考虑：

1. 给 `MAC` 增加更稳定的部分和驻留路径；
2. 让累加旧值尽量不必每拍都重新从 `VRF` 读回来；
3. 给后续 `FC / MLP / GRU gate` 留出“局部累加缓冲”的结构空间。

如果这一点不做，后面即使把矩阵或向量算力加大，`VRF` 供数也会先卡住。

### 6.2 第二优先级：围绕读口压力重构 VRF 侧的数据供应

当前 `VRF` 真正紧的是：

- 同周期多源读取
- 多发射位共享读口
- 第三微操作对前面端口复用的复杂依赖

因此第二优先级应该是：

1. 优先考虑 `VRF` 分银行或读口分层；
2. 或增加面向 `MAC/FC` 的专用暂存路径；
3. 而不是先去追求“寄存器组个数翻倍”这种收益不确定、代价却不小的改动。

### 6.3 第三优先级：让 MAC 扩展和算法结构同时收敛

当前最值得硬件协同推进的三类算法负载是：

1. `4x4 standard conv`
2. `3x3 depthwise`
3. `landmark MLP / FC / GRU gate`

因此后续 `MAC/VRF` 扩展必须围绕这三类真实负载来设计，而不是做抽象的大而全扩展。

## 7. 当前正式建议的硬件扩展优先级

### P0：继续保留 VME / tile 扩展长期主线

原因：

- 动态手势识别
- 全连接层
- `GRU gate`

后面都需要真正更像矩阵计算的数据流。

但是它当前还不能替代近程主线。

### P1：先补 MAC 局部累加驻留

目标：

- 减少 `vd旧值` 对 `VRF` 的重复读取；
- 给 `FC / MLP / GRU gate` 的累加型循环创造更稳的本地数据驻留条件。

### P2：再补 VRF 读口/银行化能力

目标：

- 缓解 `dispatch` 同周期三源/多微操作争口；
- 给 `MAC` 与后续 `VME` 数据搬运留接口余量。

### P3：最后再考虑扩大寄存器总量

原因：

- 当前从已读代码看，最先暴露出来的不是“32 组寄存器完全不够放”，而是“同拍拿数据和回写路径更紧”。

## 8. 对下一步执行的直接建议

后续紧接着应该做的，不是回去继续围绕旧 `3x3` 线路打转，而是：

1. 在项目工作树里补一条短 `MAC/FC` 微基准，专门测：
   - `VMACC / VWMACC`
   - 小型 `FC / MLP` 风格循环
2. 补一条 `VRF` 压力可观测性验证，至少明确：
   - 同拍读口利用
   - `vd` 旧值参与的热点
3. 再把动态手势第一版主线，优先收口到：
   - `landmark sequence + GRU`
   - `landmark sequence + TCN`
4. 同时保持：
   - `4x4 standard conv`
   - `3x3 depthwise`
   - `RepVGG + landmark` 静态最优系统线

## 9. 今天应记住的最终一句话

当前 CoralNPU 官方公开主链里，

- 空间卷积收益最明确的是 `4x4 standard conv` 与 `3x3 depthwise`
- 稠密矩阵型负载的长期希望仍然在 `VME/tile`
- 但在 `VME` 完整坐实前，**最该先扩的是 MAC 的局部累加驻留与 VRF 的供数能力，而不是盲目先扩寄存器总数**
