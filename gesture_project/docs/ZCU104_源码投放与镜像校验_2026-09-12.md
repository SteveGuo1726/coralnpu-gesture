# ZCU104 Linux 侧：镜像内容校验（2026-09-12）

> 本文记录一次**误诊**以及它最终被澄清的全过程。
> 价值不在结论（镜像本来就对），而在**排查方法**和**几个把人带偏的假线索**。
> 相关：`plnx/05_verify_image.sh`、`plnx/06_install_app.sh`、`plnx/PITFALLS.md #8`

---

## 1. 最初的误判

**观测**：`gf_npu.c` 里有一句新加的诊断文案
`Widen the reserved-memory node in system-user.dtsi`，
但把它从 `rootfs.ext4` dump 出来的 ELF 里 `strings` 搜不到。

**当时的推断（错误）**：改动没进镜像 → 怀疑 Yocto 的 sstate 缓存把
`do_compile` 短路了 → 写了一整套"必须 do_cleanall"的流程。

**错在哪里**：我把"字符串不在二进制里"直接等价成了"代码是旧的"。
在 C 里这两件事**没有必然关系**。

## 2. 真正的成因

那句 `fprintf` 所在的条件是：

```c
const size_t bytes_needed = /* sizeof() 与 #define 之和，全是编译期常量 */;
if (bytes_needed > (size_t)GF_BUF_SIZE) {     /* 578 KB > 16 MiB —— 恒假 */
    fprintf(stderr, "gf_npu: device-tree scratch region too small: ...");
    return -1;
}
```

两边都是编译期常量，GCC 直接证明分支不可达，**连同字符串一起删掉**。
这是正确且期望的死代码消除，不是构建系统的错。

实测对照 —— 同一个二进制里：

| 字符串 | 守卫条件 | 在 ELF 里？ |
|---|---|---|
| `staged weights + activations` | 正常路径 | ✅ |
| `PL id ok (MAGIC` | 正常路径 | ✅ |
| `first difference at byte` | 依赖 memcmp 结果（运行时）| ✅ |
| `CONTENT MISMATCH` | 依赖 memcmp 结果（运行时）| ✅ |
| `scratch region too small for weight image` | 依赖运行时表内容 | ✅ |
| `device-tree scratch region too small` | **常量比较** | ❌ |
| `Widen the reserved-memory node` | **常量比较** | ❌ |

完全符合预期。

## 3. 几个把我带偏的假线索

排查时我一度认为下面这些是"异常"，其实全部**正常**：

### 3.1 `log.do_compile` 恒为 85 字节

内容就两行：

```
DEBUG: Executing shell function do_compile
DEBUG: Shell function do_compile finished
```

因为 recipe 的 `do_compile` 只调用两条 `gcc`，而 **gcc 成功时不输出任何东西**。
所以多次构建日志字节数完全相同是**正常的**，
**不能**用它推断"任务被短路"。

### 3.2 `WORKDIR` 里只剩 `temp/`

`do_rm_work` 在构建收尾时把源码、`recipe-sysroot`、中间产物全部删除，只留日志。
这是**设计行为**。想看源码得先单独跑：

```bash
petalinux-build -c gf-npu -x do_unpack
```

### 3.3 `do_unpack` 日志里的 `Unpacking ... to .../1.0-r0/`

这只是**声明的目标路径**，不代表文件此刻在磁盘上 —— 因为后来被 `do_rm_work` 清了。

### 3.4 三次构建日志大小逐个相同

在 3.1 已解释。且当时源码**确实没改过**（我误以为改了），所以内容相同才是对的。

## 4. 结论：代码一直是对的

最终确认（`petalinux-build -c gf-npu -x do_unpack` 之后）：

```
WORKDIR/gf_npu.c  md5 = 65976d8f94d320d301cd3eedd9978500
仓库   gf_npu.c  md5 = 65976d8f94d320d301cd3eedd9978500     <- 一致
```

镜像里两个二进制与源码的字符串双向比对，**17/17 命中**，
`05_verify_image.sh` 报 `RESULT: PASS`。

**没有发生过"板子跑旧代码"的事故。**

## 5. 保留下来的三道闸门（仍然有价值）

虽然起因是误诊，但工具本身是好的，保留下来：

### `05_verify_image.sh`
不需要 root，用 `debugfs` 从 `rootfs.ext4` 里 dump ELF，四个维度校验：

| 段 | 内容 |
|---|---|
| `[0]` | 镜像 mtime 不早于最新源码 |
| `[3]` | 架构是 aarch64；`gf_camera` 链到 libjpeg |
| `[4]` | 精选探针双向比对（**只用运行时条件守卫的字符串**）|
| `[5]` | 从源码批量抽文案，算命中率（过半即通过）|
| `[6]` | 打印 md5，供写卡后对账 |

### `06_install_app.sh`
投放源码 → `do_cleanall` → 全量重编 → 自动调闸门 1。
虽然本事故不需要它，但"改了本地源码想保证重编"时它是正确姿势。

### `04_make_sd.sh`
写卡前自动跑闸门 1，不 PASS 直接拒绝。写完后打印卡上二进制 md5 供对账。

## 6. 教训

1. **"字符串不在二进制里" ≠ "代码没编进去"。** 先看守卫条件是不是编译期常量。
2. **挑探针字符串时，条件必须依赖运行时数据**（寄存器、memcmp、ioctl 返回值）。
3. **日志小/空不等于任务没跑** —— 成功的 gcc 本来就安静。
4. **`WORKDIR` 空不等于 unpack 失败** —— 那是 `do_rm_work` 的正常收尾。
5. 最可靠的做法始终是：**从最终产物反向验证**，而不是从构建日志里找安心。
