# 项目中期报告：项目进展状况小结、存在问题及解决方案与下一步计划

## （1）项目进展状况小结

本项目从立项开始，始终围绕“面向手势识别的 RISC-V + NPU 软硬件协同优化设计”这一目标推进。到当前中期节点，项目已经完成从任务定义、数据准备、候选算法训练与筛选、INT8 量化评估、CoralNPU official 软件路径回放与优化，到 rowhandoff 硬件参考线、CSR 读回链路和真实 trace 闭环验证的一整套中期主线工作。整体上，项目已经从“研究设想和方向探索”进入“主线收敛和验证闭环建设”阶段。

### 1. 项目初期已完成任务边界收缩、数据准备与统一评估口径建立

项目初期首先对计划书中的任务范围进行了重审。原始设想中同时涉及静态手势、动态手势、不同神经网络结构、软件调度优化和硬件结构创新，如果在项目初期全部并行推进，容易导致主线不清和资源分散。因此，项目先将近期主线收缩为“六类静态手势识别 + 可映射到 CoralNPU 的卷积主导模型 + official 工程路径上的软硬件协同优化”。

围绕这一主线，已完成以下基础工作：

- 完成 HaGRID 数据集子集整理，形成 `gesture_project/datasets/processed/hagrid_sample_static_6cls`。
- 固定当前静态任务为六分类：`fist`、`like`、`ok`、`palm`、`peace`、`stop`。
- 固定当前主线输入尺寸为 `96x96`。
- 建立统一的训练、Keras 评估、TFLite 评估、算子画像、NPU 周期估算流程。

这一阶段最重要的成果，不是“找到了某个模型”，而是建立起一套统一的评价口径。后续所有模型如果要进入主线，必须经过“真实训练 -> INT8 量化 -> TFLite 评估 -> 算子画像 -> NPU 周期估算”这条完整链路，而不能只看论文结构名、参数量或理论计算量。

### 2. 已完成多条候选算法路线的真实训练、量化评估与主线收敛

在任务和数据口径固定后，项目对多条候选算法路线进行了真实训练和部署导向评估，而不是停留在文献层面对比。已经完成的主要工作包括：

- 使用 `train_static_cnn.py` 完成静态卷积模型的真实训练。
- 使用 `quantize_tflite.py` 完成主线模型 INT8 量化。
- 使用 `evaluate_keras_classifier.py` 和 `evaluate_tflite_classifier.py` 完成浮点与量化模型评估。
- 使用 `profile_tflite_ops.py` 完成 TFLite 算子画像。
- 使用 `estimate_npu_cycles.py` 完成 NPU 周期估算。
- 使用 `compare_model_candidates.py` 和 `summarize_candidate_hardware.py` 完成候选模型对比与硬件导向总结。

经过这一轮系统比较，项目当前已经正式收敛出算法主线：

```text
static_cnn_regularized_3x3_i96_e70_hagrid6_sample
```

该模型目前的关键结果如下：

- Keras 测试准确率：`77.29%`
- INT8 TFLite 测试准确率：`77.07%`
- 量化精度损失：`0.22` 个百分点
- 参考周期估算：`1,130,091,474`
- 优化后周期估算：`63,313,051`
- 估算加速比：`17.85x`

这一结果说明，当前主线模型具备三方面优势：

- 准确率在现有已验证候选中最稳。
- INT8 量化后精度几乎不掉点，说明部署稳定性较好。
- 热点高度集中在 `3x3 Conv2D`，与当前 CoralNPU 软硬件优化方向高度一致。

为了避免只在单一路线上做判断，项目还完成了一条正式轻量模型对照线：

```text
mobilenet_v2_a050_96_imagenet_frozen_finetune_hagrid6_sample
```

其关键结果如下：

- Keras 测试准确率：`59.73%`
- INT8 TFLite 测试准确率：`58.40%`
- 估算参考周期：`513,626,757`
- 估算优化后周期：`195,936,730`
- 估算加速比：`2.62x`

这一对照说明，轻量模型虽然理论计算量更低，但在当前 CoralNPU 工程路径下，瓶颈主要落在 `1x1 pointwise Conv2D`，整体收益明显不如当前 `3x3` 主线。这个结果帮助项目避免了“只看轻量化标签选方向”的误判。

此外，项目还对 `RepVGG` 风格和 `Residual 3x3` 风格路线做了首轮真实训练验证。结果表明，这两条路线在当前六类静态手势任务和当前工程实现下，尚未表现出进入正式主线的价值，因此已完成阶段性验证并归档。这意味着项目在算法阶段已经不再是“广泛试试看”，而是已经完成了有取舍、有数据支撑的主线收敛。

### 3. 已完成 CoralNPU official 软件路径回放，并收敛出 current best 软件保底线

在算法主线确定后，项目没有立刻进入 RTL 改造，而是先沿 CoralNPU official 路径回答一个更基础的问题：在不改硬件结构的前提下，当前主线模型映射到 official `conv.cc` 后，软件路径本身到底能优化到什么程度。

围绕这个问题，项目已经完成以下工作：

- 建立 `gesture_project/worktrees/coralnpu-3x3-conv` 作为 official worktree 实验区，避免污染参考仓库。
- 建立 `run_core_3x3_worktree_replay.py`、`build_worktree_core_3x3_bridge.py` 等回放和桥接脚本。
- 完成四个主体热点层的单层回放、四层总回放和 totals compare。
- 完成 `strategy=8` 方向下的多轮入口、尾段、row-end 候选分析。
- 完成 current best 收敛，并将无价值方向系统归档。

截至目前，official 软件路径上的正式保底线已经明确为：

```text
strategy=8
+ x4_id32 / x4_id64
+ 静态主体块调度
+ interior 6tap 分带
+ 顶/底 4/6/4 分带
```

四个主体层总结果如下：

- `ref_cycles = 717,666,345`
- `opt_cycles = 17,596,916`
- `mismatch = 0`

分层结果如下：

- `conv2_3x3_a`：`138,812,960 -> 5,732,506`
- `conv2_3x3_b`：`240,941,500 -> 4,617,766`
- `conv3_3x3_a`：`117,597,531 -> 2,440,498`
- `conv3_3x3_b`：`220,314,354 -> 4,806,146`

这条软件保底线的价值非常关键：

- 它已经是经过真实 official 回放验证的 current best，而不是理论推测。
- 它在四个关键层上全部保持 `mismatch=0`，可以作为后续硬件工作的第一层正确性基准。
- 它明确回答了“软件路径已经做到什么程度”，从而避免后续把软件问题误当成硬件问题。

### 4. 已系统排除多条软件微方向，完成大量探索性试验的止损和归档

为了得到可靠的软件保底线，项目不只是做正向优化，还做了大量反向排除。已经明确不应回到主线的方向包括：

- `3x3 repack`
- `3x3 postprocess` 软件融合
- 边界行中带块调度
- 边界点 `32/64` 窄特化

这些方向之所以被正式判死，不是因为“猜测没用”，而是因为已经做过真实回放和量化比较，结论是要么收益不稳，要么收益太小，要么根本不落在当前最关键的瓶颈上。与此同时，项目还完成了 `tail patch`、`tail micro patch`、`row_end_tail`、`official patch entry` 等分析，把哪些局部入口值得继续关注、哪些已经没有继续扫描价值，做了系统量化。

这一阶段的实质成果，是把大量早期探索性试验变成了可复用的正式结论。后续推进不再需要从零开始重扫这些分支，项目已经从“广泛扫描阶段”进入“正式保护 current best、只保留高价值后续方向”的阶段。

### 5. 已建立 rowhandoff 硬件参考线，并完成最小 CSR / counter / readback 闭环

在软件保底线形成后，项目进一步转向硬件侧，但没有直接进入大规模 RTL 重构，而是优先围绕“是否存在一条值得继续推进的硬件参考语义”展开工作。当前已经保留下来的唯一第二层硬件参考候选为：

```text
rowhandoff_rowbase_recur mode=1
```

围绕这条参考线，项目已经完成以下实质工作：

- 在 official 风格路径上建立 `CoreAxi / CoreAxiCSR` 最小 sideband 接入思路。
- 落地 `RowhandoffCounterBank`，形成 rowhandoff 事件计数模块。
- 完成 `counter bank -> CSR readback` 集成链测试。
- 完成“外部 rowhandoff 脉冲注入 -> CSR readback”测试。
- 完成“最小 row 级 sideband -> RowhandoffSidebandAdapter -> counter bank -> CSR readback”测试。

这意味着，项目已经不再停留在“提出一个新的控制想法”，而是已经把这条参考语义落实到可计数、可读回、可通过 official CSR 路径观测的最小工程闭环里。对后续工作来说，这一点非常重要，因为它把硬件创新从抽象想法拉回到了可验证工程对象。

### 6. 已完成真实 workload 下的 rowhandoff trace 抓取、解析与状态重建

项目在阶段 3 中最关键的一项进展，是确认 `CoreAxi.rowhandoffTrace` 不是空壳观测口，而是在真实 workload 下能够抓到完整事件序列。此前曾一度误判“只能看到 `layer_start`”，后来通过补完整日志读取、修复解析流程和重新重建状态，已经纠正这一错误结论。

当前正式确认的事件统计结果如下：

这一结果的意义在于，项目已经具备了从 trace 反推出 source-style row 生命周期的能力。后续无论做 cocotb 对账、host readback 对账，还是未来更进一步的板级 readback，都不再需要从“如何理解内部行为”重新起步。

### 7. 当前项目已经形成三条正式保底线和一条明确的中期收口路线

截至当前，项目已经正式形成以下三条保底线：

- 算法保底线：`static_cnn_regularized_3x3_i96_e70_hagrid6_sample`
- official 软件保底线：`strategy=8 + x4_id32/x4_id64 + 静态主体块调度 + interior 6tap + 顶/底 4/6/4`，四层总 `opt_cycles=17,596,916`，`mismatch=0`
- 第二层硬件参考线：`rowhandoff_rowbase_recur mode=1`

同时，项目也已经明确哪些方向不应再继续发散，包括 `3x3 repack`、`3x3 postprocess 软件融合`、边界行中带块调度、边界点窄特化，以及 `mode2/mode3/mode4_helper/mode6_terminalptr` 等 rowhandoff 变体。

因此，项目当前并不是“还在前期摸索”，而是已经完成中期主线搭建，进入“冻结前两层保底线、围绕唯一硬件参考线做官方风格收口”的阶段。这说明项目已经具备清晰的事实基础、明确的保留方向和较完整的量化结果，为下一阶段继续推进打下了较扎实的基础。

## （2）项目存在问题及解决方案、项目下一步计划

### 1. 当前存在的主要问题

#### （1）前期探索范围较广，历史材料和中间分支较多，主线表达成本偏高

由于本项目本身是创新项目，早期为了寻找真正有效的软硬件协同切入点，确实开展了较多候选模型、调度策略和局部硬件语义试验。这些试验并非没有价值，当前正式主线正是建立在这些探索基础上的。但从当前阶段看，相关材料和中间结果数量较多，如果不持续收整，就会带来三个问题：

- 新阶段续接成本高，需要反复阅读大量中间记录。
- 阶段汇报和中期表达容易被历史分支干扰，主线不够突出。
- 如果误用已归档结论，可能导致重复走弯路。

#### （2）软件侧继续做微 patch 扫描的边际收益已经明显下降

当前 software current best 已经收敛到 `17,596,916 / mismatch=0`。继续在 residue、terminal、tail micro patch 等细分方向上做无边界扫描，虽然理论上仍可能得到少量周期变化，但这些变化通常只落在几百 cycles 量级，已经不足以支撑项目主线继续停留在软件微调层面。继续深挖这类方向，会直接拖慢硬件参考线收口和后续验证闭环推进。

#### （3）硬件参考线已经建立，但还没有转化为“正式可交付主线”

当前 `rowhandoff_rowbase_recur mode=1` 已经是唯一保留的第二层硬件参考候选，也已经具备 counter、CSR readback 和真实 trace 闭环能力，但它还不是最终可以直接对外交付的硬件终版。换句话说，项目已经走过了“完全没有硬件方向”的阶段，但还没有走到“硬件主线已经最终定型”的阶段。后续仍需继续把参考语义压缩成更简洁、更稳定、更适合官方流程验证的正式候选对象。

#### （4）后续验证阶段对正确性、可读回性和结果解释性的要求更高

从当前阶段往后走，问题不再只是“能不能做出一个更快的想法”，而是“这个想法是否能在 official integration style 下被稳定验证、被 host readback 读回、并且能与软件 trace 对得上”。这意味着后续工作必须更加重视 correctness、readback 和 trace 对账，而不能继续沿着大量分散小试验前进。

### 2. 已采取和拟采取的解决方案

#### （1）以活跃入口文档为准，持续压缩活跃区，归档历史碎片

针对材料分散问题，项目已经建立并启用了新的活跃入口文档、阶段总结文档、工程文件索引和归档清单。后续续接将严格以活跃文档为准，不再从已归档旧材料直接起步。这样做的目的，是把历史探索留下的有效结论保留下来，同时把无须反复回看的碎片材料从主线工作区移开，提升推进效率并降低误读风险。

#### （2）冻结算法主线和 official 软件保底线，不再因局部试验反复漂移

项目已经明确把 `static_cnn_regularized_3x3_i96_e70_hagrid6_sample` 作为算法保底线，把 `strategy=8 current best` 作为 official 软件保底线。所有后续硬件试验、trace 对账和系统验证，都必须以这两条基线为前提，避免出现“每推进一步，前面的口径又变了”的问题。这样既能保护当前已取得的阶段成果，也能让后续结果更容易解释和对比。

#### （3）硬件侧不再继续发散扫 mode，而是只保留 rowhandoff mode=1 做官方风格收口

项目已经明确不再回到 `mode2/mode3/mode4_helper/mode6_terminalptr` 等已判死方向，也不再大规模重开 rowwindow、backhalf、backthird 这类已进入收益平台区的局部试验。后续硬件工作将坚持单主线推进：围绕 `rowhandoff_rowbase_recur mode=1`，沿 `CoreAxi / CoreAxiCSR / RowhandoffCounterBank / CSR readback / trace 对账` 这条 official 风格路径继续收口。

#### （4）把后续阶段重心从“继续扫微小收益”转向“建立稳定验证闭环”

后续最重要的工作，不再是从几百个细分 patch 里继续找局部更优点，而是把已经保留下来的硬件参考线，尽快变成一条 correctness 守得住、host 能读回、trace 能对账的正式验证路线。这样做不仅更符合 CoralNPU official 工程使用方式，也更符合项目的长期目标，因为后续真正的软硬件协同优化，必须建立在稳定闭环之上，而不是建立在不断漂移的试验环境之上。

### 3. 项目下一步计划

#### （1）继续保持算法主线稳定，并补足阶段汇报所需的结果组织

下一步将继续固定 `static_cnn_regularized_3x3_i96_e70_hagrid6_sample` 为正式算法主线，不再重新铺开一轮大规模候选模型扫描。同时，把已有训练结果、量化结果、热点分析和周期估算结果进一步整理成更适合阶段汇报和后续论文写作使用的规范材料，确保项目成果既真实完整，又便于表达。

#### （2）继续保持 official 软件保底线稳定，停止无价值的微 patch 发散

下一步将继续保护 `17,596,916 / mismatch=0` 这条 official current best，不再破坏当前 best 主线，也不再回头捡已经判死的软件融合、边界窄特化等方向。对必要的小范围补充试验，将严格控制范围，要求能够快速止损，不影响主线推进。

#### （3）围绕 rowhandoff mode=1 继续完成事件、计数、读回、trace 的统一收口

下一阶段硬件主线将继续围绕 `rowhandoff_rowbase_recur mode=1` 推进，重点不是继续设计更多新 mode，而是把现有语义进一步压缩成更简洁、更适合验证的形式，并持续加强 `counter`、`CSR readback`、`CoreAxi.rowhandoffTrace` 和项目侧重建结果之间的一致性。

#### （4）继续按官方风格完善 prerequisites / cocotb / elf / official integration style / host readback 这条使用路径

下一步还将继续围绕 CoralNPU official 文档和官方集成风格，梳理 prerequisites、cocotb、elf 运行方式、host 启动顺序和 readback 流程，确保后续验证工作尽量沿官方推荐路径推进，而不是依赖越来越多的临时性局部技巧。这样做的目标，是让后续工作既快，又稳，而且能够更自然地过渡到下一阶段更完整的系统验证。

#### （5）继续收整阶段文档、索引和关键报告，降低后续续接成本

项目下一步还会持续完善阶段 1 到阶段 4 的总结、工程文件索引和归档清单，让后续每一轮续接都能直接从活跃材料起步，减少重复回顾中间碎片的时间成本。这项工作本身不是主线成果，但它对保持后续推进速度和降低误判风险非常关键。

### 4. 中期阶段结论

总体来看，项目到当前已经完成了中期最核心的一轮工作：算法主线已经从多候选中收敛出来，INT8 量化和周期画像已经建立，CoralNPU official 软件路径已经收敛出 `current best`，硬件侧也已经从“没有参考线”推进到“存在唯一保留的 rowhandoff 参考线，并具备 CSR readback 和真实 trace 闭环能力”。

因此，项目接下来的重点不应再是回到早期广泛探索，而应是在现有三条保底线基础上继续做高质量收口，把硬件参考线进一步转化为符合官方风格、可稳定验证、可持续推进的正式工程主线。这将决定项目后半程能否在创新性、工程完整性和结果可信度三方面同时取得较好的成果。
