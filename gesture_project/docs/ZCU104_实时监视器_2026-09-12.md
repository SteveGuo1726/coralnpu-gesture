# ZCU104 实时监视器（浏览器看画面 + 结果 + 指标）

> 2026-09-12 建立。目的：**亲眼判断模型效果** —— 摄像头画面、NPU 实际输入、识别结果、
> 耗时分解、类别分布、真值标注准确率，全部在一个网页里。
>
> 2026-09-12 第二轮（**当前版本**）：去掉多数表决、只显示本帧结果；新增 `--zoom` / `--crop`
> 取景控制（**精度最大的杠杆**）；场景流改为发布"模型实际看到的那块区域"。
> 改动理由见 §3 与 `plnx/PITFALLS.md #23`/`#24`，完整过程见交接文档 **#153**。
>
> **硬约束：它不能拖慢手势识别。** 设计上做到"没人看的时候一分钱不花、有人看也只花
> 一次 memcpy"，下面 §4 有实测数字和验证方法。

---

## 1. 怎么跑

```bash
# 板上（root）—— 推荐起手式：640x480 + 3x 数码变焦（见 §3.1 为什么）
gf_camera -s 640x480 --zoom 300 --view 8080
```

启动时会自己打印地址：

```
gf_camera: viewer started on port 8080 (page: /usr/share/gf/view.html)
gf_camera: viewer ready -- open this in the laptop browser:
gf_camera:    http://192.168.1.57:8080/
```

笔记本浏览器打开那个地址即可。**没插网线时它会明确告诉你**：
`viewer listening on port 8080, but eth0 has no IPv4 address yet`。

`--view-page P` 可以换页面文件（默认 `/usr/share/gf/view.html`）；页面在文件系统上而不是
编进二进制，所以改页面走 `10_push_app.sh page` 只要 **2 秒**，不用重编。

## 2. 网络（唯一需要你动手的地方）

板子的 GbE 硬件是好的 —— 内核日志里 `macb ff0e0000.ethernet` + `PHY [TI DP83867]` 都正常，
`eth0` 只是 `NO-CARRIER`，**意思是没插网线**。

### 2.1 首选：接到路由器/交换机（有 DHCP）

```bash
# 板上
ip link set eth0 up
udhcpc -i eth0          # 会打印租到的地址
```

只要笔记本和板子在同一网段，直接访问 `http://<板子IP>:8080/`。

### 2.2 次选：网线直连笔记本（无 DHCP）

两端各配一个同网段的静态地址：

```bash
# 板上
ip link set eth0 up
ip addr add 192.168.77.2/24 dev eth0
```
Windows 侧：网络适配器 → 该以太网口 → IPv4 → 手动 `192.168.77.1 / 255.255.255.0`。
然后访问 `http://192.168.77.2:8080/`。

> **带宽不用担心**：GbE 下预览流约 0.4 MB/s；全分辨率流约 4.6 MB/s（限速 5 fps）。
> 百兆链路也够。

## 3. 页面里有什么

| 区域 | 内容 | 为什么有用 |
|---|---|---|
| **模型输入 96×96** | NPU 实际吃进去的那张图，像素放大显示 | **判断准确率问题的第一现场**。预处理错、方向错、曝光错都只能在这里看出来 |
| **模型看到的范围** | 送进 NPU 的那块区域的原分辨率画面（默认关闭） | 看构图：手有多大、在不在画面中央、背景、光照。**与上面那张 96×96 是同一块区域**，不可能漂移 |
| **当前结果** | 大字就是**本帧**的类别，不做任何平滑；下面一行给出类别号与帧号 | 监视器的职责是显示模型行为，不是让它好看（见 `PITFALLS.md #24`） |
| **耗时分解** | 解码 / 缩放 / NPU 三条横条 + 端到端 ms | 直接对着 `≤5 ms` 的验收指标看 |
| **类别分布** | 18 类各自的累计帧数 | 一眼看出是否某一类在"吸"所有输入 |
| **真值对照** | 点一个手势当真值，从下一帧开始**逐帧**计分 | **把"看着像对的"变成数字**。只有逐帧一个口径 |
| **滚动日志** | 最近 60 次采样的逐帧一行，判错的行标红 | 看抖动和翻转 |
| **错误计数** | JPEG 坏帧数、NPU 失败数 | 坏帧是真实存在的，别把它当成模型问题 |

两个开关：**暂停画面**（冻结图像看细节，指标继续跑）、**开启模型视野**（默认关，省带宽）。

> **没有"平滑/稳定帧"这个口径了（2026-09-12 起）。** 早期版本对最近 5 帧做多数表决、
> 并且显示表决结果，这是错的：它把"模型在哪些情形下判错"抹成一个更小的数字，
> 并且让标签滞后画面最多 4 帧。现在显示的就是本帧结果，逐帧抖动本身是证据而不是噪声。

**导出 CSV**：页面把每次采样（帧号、本帧类别、各段耗时、当时的真值）导出，
用来做离线分析或写进材料。

> ⚠️ 页面按 ~5 Hz 采样。**要逐帧数据（性能数字、混淆矩阵）请用 stdout**：
> `gf_camera ... -n 1000 | tee /tmp/run.log`，每帧一行，含完整时间戳信息。

### 3.1 取景：`--zoom` 与 `--crop`（**这是精度最大的杠杆**）

模型在 HaGRID 上训练，那里**手就是主体、占满画面**。这个摄像头 1x 时视野覆盖整个房间，
缩到 96×96 后手只有约 15×15 像素 —— 模型没见过这种输入，输出会退化成噪声
（"没有手却报出某个类"就是这么来的）。

```bash
gf_camera -s 640x480 --zoom 300 --view 8080
```

| 参数 | 含义 |
|---|---|
| `--zoom N` | 相机自己的数码变焦（`V4L2_CID_ZOOM_ABSOLUTE`，**100..800 = 1x..8x**）。**实测是居中裁剪**（zoom=400 与 zoom=100 的中心 1/4 吻合，最佳原点 (238,180)、理论中心 (240,180)），ISP 先裁传感器再缩放，所以同一块区域拿到的 JPEG 比特远多于软件裁剪；AE/AWB 也改成对**手**测光 |
| `--crop F` | 软件居中裁剪（F≥1），与 `--zoom` 叠加。用于相机没有变焦、或需要超过 8x 的场合；**代价是丢掉被裁掉的像素** |

两个都**居中**，所以手要被放在画面中央。启动时会打印当前取景：
`model input = 213x160 centred crop of 640x480 (crop 1.00x, on top of the camera's digital zoom), area-average to 96x96`。

> 变焦后画面会**变亮、变暖**（实测逐通道增益 1.31/1.40/1.50）—— 这是 AE/AWB 改了测光区域，
> 不是颜色 bug。详见 `PITFALLS.md #23`。

## 4. 为什么它不会拖慢识别（以及怎么自证）

### 4.1 三条设计约束

1. **没人问就不拷贝。** 每个流记着"最后一次被请求的时刻"；超过 2 秒没人请求，
   `gf_view_publish()` 直接返回。**没有浏览器连着的时候，它每帧只做一次 64 位读 + 两次比较。**
2. **socket 全在后台线程里。** 采集线程一行网络代码都没有。所以客户端卡住、链路饱和、
   笔记本睡眠 —— 最坏结果只是**预览掉帧**，不可能给流水线加一毫秒。
3. **旋转交给浏览器。** 96×96 的输入必须在板上转（那是喂给模型的，转错就没意义），
   但 640×480 的全景由页面的 CSS `rotate()` 转 —— **板子零开销**。

### 4.2 实测 A：板上端到端（**这是最终判据**，2026-09-12）

同一条命令、同样帧数，四组对照。判据是每帧的 `ms` 列（脚本从 `gf_camera` 的输出里取
`$(NF-1)`，**不是 `$NF` —— 最后一列是单位字符串 `ms`**，第一版就踩了这个）：

| 场景 | 帧数 | 每帧均值 |
|---|---|---|
| A 不带 `--view`（基线） | 150 | **32.35 ms** |
| B 带 `--view`，**无人拉流** | 150 | **32.36 ms** |
| C 带 `--view`，板内 loopback 约 15 Hz 拉 `/preview.bmp` | 250 | **32.12 ms** |
| D 带 `--view`，预览 + 全景都拉（最坏情况） | 250 | **32.12 ms** |

**四组差异在噪声之内**（±0.24 ms，且"有人在看"反而略低）。也就是说：
**开着查看器、并且真的有人在看，识别流水线没有可测的变慢。**

端点本身的响应时间（从 WSL 经 Windows NAT + USB 网卡测）：

| 端点 | 响应时间 | 载荷 |
|---|---|---|
| `/stats` | 7 ms | 541 B |
| `/preview.bmp` | **9 ms** | 27 702 B（96×96 BMP）|
| `/scene.bmp` | **88 ms** | 921 654 B（640×480 BMP）≈ 84 Mbps |

### 4.3 实测 B：微基准（x86 笔记本上跑 `tests/run.sh`）

```
一次 96x96 预览大小的 memcpy（基准尺）  :   418 ns
发布一帧，无人关注                      :    37 ns   = 一帧 27.3 ms 的 0.00014%
发布一帧，有人在看预览                  :   553 ns   = 0.0020%
发布一帧，同时拷贝全景（限 5 次/秒）     : 78 485 ns = 0.29%（分摊后 <0.04% CPU）
```

"无人关注 = 37 ns"不是估算：测试里那一段是 **确定性**验证的 —— 先让关注窗口过期、
发布一个不同的图样、再读回流，读回来必须仍是**旧图样**（说明那次发布被丢了）。
计时只是旁证。

> **页面侧也必须节流**，否则会把这三条约束自己破掉：`<img>` 的 `onload` 一触发就立刻
> 再请求，浏览器在局域网上能跑到上百 Hz；每个请求都要板子做一次 memcpy 加一次 TCP 发送。
> 所以刷新率由页面定死（预览 66 ms ≈ 15 Hz、全景 220 ms ≈ 4.5 Hz，见 `view.html`
> 里的 `PREVIEW_MS` / `SCENE_MS`），**板子不做任何定时**。

## 4.4 怎么自己复现

同一条命令、同样的帧数，跑三遍比较每帧 ms：

```bash
gf_camera -n 300                                    # 基线，无查看器
gf_camera -n 300 --view 8080                        # 开了查看器但没人看
# 第三遍：开着 --view，同时用浏览器打开页面并开启全景
```

**判据：前两遍的每帧耗时应当在噪声范围内相同。** 第三遍的增量就是观看的真实成本。

## 5. `--rotate`（相机装反时用；**当前应留空**）

**当前相机是正装的，所以不要加 `--rotate`。** 这一节留着，是因为装反这件事已经发生过一次，
而且它极容易搞错方向：一开始相机是倒装的（`--rotate 180` 才正），后来用户物理转正了，
再照抄旧命令行就会把画面一次转成反的。

模型是在正立手势图上训练的，倒过来的手对它是**另一个手势**，所以必须在喂给 NPU 之前转正 ——
**只转预览是没用的**。参数是运行期的，改它不需要重编：

```bash
gf_camera --rotate 0     ...   # 正装（现在的状态，等价于不加这个参数）
gf_camera --rotate 180   ...   # 倒装
# 90 / 270 也可用（输出是正方形，所以四个角度都是精确的整数置换）
```

**怎么判断该用哪个**：存一帧下来看，别猜。

```bash
gf_camera -n 6 --save-ppm /tmp/chk.ppm && python3 /tmp/gfenc.py /tmp/chk.ppm
```

旋转在**缩放的采样循环里**完成（不是把结果再转一遍），所以对 180° 是精确的、对 90/270
是同一套采样盒的置换，且**不增加任何一次额外遍历**。

`tests/t_geom.c` 对四种角度 × 全部 9216 个输出像素逐一比对，并用独立推导的期望值
（不是复述实现）：`rot180` 等于原图倒着读，`rot90` 再 `rot270` 复合回原图。

## 6. 没有网线怎么办

页面需要 IP，所以没有网线就用不了。此时仍然可用的两条路：

```bash
# ① 只看指标（本来就是文本，走串口）
gf_camera -n 300

# ② 按需取一张"喂给 NPU 的图"回来看（约 2-3 秒一张）
gf_camera -n 6 --save-ppm /tmp/in.ppm
python3 /tmp/gfenc.py /tmp/in.ppm          # gzip+base64 编码器，见交接 #151
```
`--save-ppm` 配上 `-n N` 存的是**最后一帧**（自动曝光已经收敛），不是第 3 帧 ——
第 3 帧存出来是近全黑的，曾经把我们带偏过一轮。

## 7. 已验证 / 未验证

**已验证：主机侧（`bash linux/tests/run.sh`，约 5 秒，x86，不需要板子）**
- 旋转索引数学：四角度 × 9216 像素精确；rot180 = 纯反转；rot90+rot270 = 恒等
- BMP 编码：96×96 与 640×480 头部字段、`Content-Length`、**逐像素**比对（含自下而上的行序）
- 路由：`/`、`/stats`、`/preview.bmp`、`/scene.bmp`、`/favicon.ico`(204)、未知路径(404)
- 首帧之前返回 503（而不是挂住连接）
- **兴趣门控**（§4.3 的确定性版本）

**已验证：板载（aarch64，真板真相机）**
- 编译进 rootfs 并 `05_verify_image.sh` **`RESULT: PASS`**；板上二进制 md5 与镜像里的一致
  （`gf_npu_probe aee2f49a…` / `gf_camera 6b885e73…`）
- `gf_npu_probe` **`RESULT: PASS`**（6/6 张量 bit-exact、4 个硬件 FNV 全对）—— 加了查看器之后
  NPU 路径没有回归
- `gf_camera --view 8080` 实跑：`/` 20393 B、`/stats` JSON 正常、`/preview.bmp` HTTP 200 / 27702 B；
  连续 20 次请求 **20/20 成功**
- **§4.2 的四组开销对照**（本页最重要的数字）
- 方向：取回画面确认当前（不带 `--rotate`）朝上是正确的
- 可达性：Windows `ping` 3/3、WSL 侧 HTTP 正常（浏览器与 WSL 走的是同一块 USB 网卡）
- **相机取景结论（2026-09-12 实测）**：缩略/全景两张图的通道均值一致 ⇒ 解码链路无错；
  AWB 默认就是最平衡的一项（R−B = +8.6）；`zoom_absolute=400` **是**居中裁剪
  （最佳原点 (238,180) vs 理论中心 (240,180)）
- **主机侧测试**：`bash tests/run.sh` 两个程序 **PASS 0 failures**、`-Wall -Wextra` 无警告

**未验证**
- **真机浏览器**（Chrome/Edge/Firefox）实际打开一次。只用了 BMP + 原生 JS + CSS，没有外部依赖，
  也没有用到新 API，但确实还没在真浏览器里点过 —— **这一条请由你打开页面确认**。
- 长时间（数小时）连续拉流下的稳定性；目前最长连续观察约 5 分钟、9500 帧。
- **带 `--zoom` / `--crop` 的那一版还没上板**（源码已改、镜像正在重编）。
- **有真值的准确率一次都没有量过** —— 现有"类别随场景变化"只能说明链路通，不能说明模型好。
