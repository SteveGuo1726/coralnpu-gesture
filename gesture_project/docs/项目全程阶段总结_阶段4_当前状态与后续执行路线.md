## 2. 当前真正完成了什么

如果用“项目总目标是否已有可参考主线”来衡量，当前答案应分层回答。

### 2.1 已经完成的

- 已有一条正式算法主线，可直接作为展示和后续部署保底线。
- 已有一条 official 软件 current best 主线，可作为后续所有对账的第一层基线。
- 已有一条可参考的第二层硬件语义样本，不再是纯空白。
- 已有官方接入风格的最小 CSR / counter / trace 观测链。

### 2.2 还没有完成的

- 还没有形成“可以直接拿去上板交付”的完整硬件修改正式主线。
- `mode=1` 仍然是参考样本，不是已经收口的板级终版。
- 还没有完成基于 host readback / board side 对真实 rowhandoff 事件的最小板级闭环演示。

## 3. 为什么前面会显得推进慢

核心原因不是“硬件天生慢”，而是阶段目标一度被很多微试验稀释了。

具体表现为：

- 过多精力放在 residue / terminal 小变体扫描
- 很多局部 patch 只在单层级别产生几百 cycles 量级差异
- 在还没收口板级主线前，过深地做了“最小 patch 可见性”探索

这些工作不是没价值，但已经超过当前阶段最需要的深度。

从中期报告视角看，这一阶段的关键问题不是“有没有做工作”，
而是前期探索性工作较多，阶段材料和中间分支也较多，
如果不及时收口，就会削弱后续硬件验证与阶段汇报的表达清晰度。

## 4. 后续应如何高效且稳妥完成

从现在起，最优策略不是“更大力地继续扫 patch”，而是收缩为一条上板导向主线。

### 4.1 第一优先：文档与记录收缩

目标：

- 活跃区只保留主线文档、正式结果、关键 trace 闭环和板级接入清单
- 其余历史碎片全部归档备份

这样做的意义是：

- 减少后续新对话查阅成本
- 减少误读旧结论、旧地址、旧路径的概率

### 4.2 第二优先：固定唯一板级推进入口

后续板级路线必须写成：

```text
current best 软件主线不再动
+ rowhandoff mode=1 只保留为唯一硬件参考语义
+ 优先沿官方 CoreAxi / CoreAxiCSR / counter bank / CSR readback 接口推进
```

### 4.3 第三优先：先做“最小板级闭环”，不是先做“最终最优版”

第一版板级演示只需要证明三件事：

1. correctness 守得住
2. host 能读回关键事件/计数
3. 软件 trace 与板级 readback 能对上

不需要一开始就追求所有细节收益都完全复刻。

### 4.4 第四优先：并行但受控地补两条算法对照

这部分不是主线前置条件，但作为中后期补强很有价值：

- `plain-conv / structural re-parameterization` 的更稳实现
- `landmark + GRU/TCN/MLP` 的轻时序对照

要求是：

- 小规模
- 可快速止损
- 不打断当前板级主线

## 5. 当前推荐的执行顺序

### 第一步：保持仓库形态稳定

- 保留 current best 所有直接依赖材料
- 保留 rowhandoff trace / counter / CSR 接入链文档
- 归档大量过时碎片

### 第二步：以官方流程为准整理上板最小清单

应以本地 `coralnpu/doc/` 官方文档为准，结合已跑通的项目链路，统一成一份“正确操作说明”。

重点包括：

- worktree 使用规范
- Bazel `output_base` 共享规范
- cocotb / runfiles / `/tmp` 日志输出规范
- `CoreAxi` / `CoreAxiCSR` / CSR 地址使用规范
- host 加载 ITCM、设置 PC、释放 reset、轮询状态的最小流程

### 第三步：围绕 mode=1 做最小板级近似版

不是继续开新 mode，而是把现有语义收缩为：

- 当前 row 完成
- base 递推
- 下一 row 连续命中条件下复用

并保证这条语义能通过：

- 软件对账
- CSR 计数
- trace 重建

### 第四步：锁定最小板级验证对象

优先对象继续建议收缩到：

1. `conv2_3x3_b`
2. `conv3_3x3_b`

原因是：

- 它们最能体现主体层收益
- 能降低 bring-up 复杂度
- 更适合做展示型最小闭环

## 6. 当前最该避免的三件事

### 6.1 不要再破坏 current best

任何新试验都不应直接覆盖当前 best 主线。

### 6.2 不要再回到已判死方向

尤其不要回到：

- repack
- postprocess 融合
- 边界行中带块调度
- 边界点 32/64 窄特化

### 6.3 不要继续用大量微试验拖慢上板路线

当前阶段最该做的是收口，不是再扩散。

## 7. 与中期报告对应的当前结论

如果把当前状态用更适合中期汇报的话概括，应理解为：

- 项目已完成算法主线筛选、量化闭环和软件执行基线收敛。
- 项目已完成硬件参考线最小观测链与真实轨迹闭环的建立。
- 项目当前最需要的不是继续发散扫微小变体，而是把现有参考线收口成规范的验证对象。
- 后续板级阶段必须建立在当前三条保底线与统一文档入口的基础上推进。

## 8. 一句话版后续路线

后续最稳且最高效的路线应概括为：

```text
冻结算法与软件两条保底线，
把 rowhandoff mode=1 收缩成唯一官方风格板级参考线，
优先完成 CSR/trace/readback 的最小上板闭环，
其余历史试验统一归档，不再扰动主线。
```
