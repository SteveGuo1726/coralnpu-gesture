# CoralNPU 官方仓库源码分析 当前准确判断 2026-07-30

## 1. 这份文档的用途

这份文档只回答一件事：

```text
Google 官方开源的 coralnpu 仓库，当前源码里到底真实实现了什么，

```

后续任何算法路线和硬件改进讨论，都应以这份判断为起点，而不是以旧阶段的 `3x3` 局部试验材料为起点。

## 3. 已由源码证实的硬件主结构

### 3.1 标量前端

官方文档和源码都清楚表明，CoralNPU 不是“纯卷积加速外设”，而是：

- `RISC-V` 标量前端
- 加上 `SIMD / RVV` 向量后端
- 再叠加可选矩阵扩展能力

直接参考：

- `coralnpu/doc/overview.md`
- `coralnpu/doc/microarch/microarch.md`
- `coralnpu/hdl/chisel/src/coralnpu/Core.scala`

当前可以确认：

- 前端是顺序执行、无乱序、无复杂推测的轻量控制核。
- 其核心作用是驱动后端执行队列，而不是自己承担大规模数值计算。

### 3.2 默认主链是 RVV 向量后端，不是“现成成熟矩阵 NPU 主链”

从参数和后端定义看，当前默认可用主链是：

- `RVV` 向量执行后端
- `VLEN = 128 bit`
- 若干向量算术、乘加、访存执行单元

关键源码：

- `coralnpu/hdl/chisel/src/coralnpu/Parameters.scala`
- `coralnpu/hdl/verilog/rvv/inc/rvv_backend_define.svh`
- `coralnpu/hdl/verilog/rvv/design/rvv_backend_mac_unit.sv`

目前可确认的直接事实是：

- 当前默认参数里 `instructionLanes = 4`
- 当前默认 `rvvVlen = 128`
- 向量后端里存在乘加执行资源
- 整体体系更像“轻量标量控制 + 可编程向量/矩阵后端”

而不是“一个已经完全封装好的固定卷积核 NPU”。

### 3.3 矩阵扩展 ZVT / VME 确实存在，但当前公开主链没有完全打通

`ZVT/VME` 不是虚构的，它在源码里真实存在：

- `coralnpu/hdl/verilog/rvv/design/Zvt/zvt.sv`
- `coralnpu/hdl/verilog/rvv/design/Zvt/zvt_ctrl.sv`
- `coralnpu/hdl/verilog/rvv/design/Zvt/zvt_acc.sv`
- `coralnpu/hdl/verilog/rvv/design/Zvt/zvt_pe_array.sv`

参数定义里也能看到矩阵相关结构：

- `NUM_ACC = 16`
- `SUBTILE_SIZE = 16`
- `NUM_PE` 等参数由 `VLEN` 和构建选项决定

关键位置：

- `coralnpu/hdl/verilog/rvv/inc/rvv_backend_define.svh`

但是，当前公开系统整合并没有完全闭环。最关键的直接证据是：

- `coralnpu/hdl/verilog/rvv/design/RvvCore.sv`

里面明确写着：

- `Tie-off VME LSU interfaces`
- `TODO: Support these`

这意味着：

- 矩阵引擎 RTL 的确存在。
- 但当前公开主链下，矩阵引擎的完整系统级访存与软件调用链，并不能直接当成“已经成熟可用”。

## 4. 已由软件源码证实的算子优化方向

### 4.1 标准 Conv2D 当前主优化明确偏向 4x4

在：

- `coralnpu/sw/opt/litert-micro/conv.cc`

可以直接看到，当前官方 `TFLite Micro` 标准卷积优化，首先判断的是：

- `filter_height == 4`
- `filter_width == 4`

并分流到多种 `4x4` 优化路径。

如果这些条件不满足，当前标准 `Conv2D` 很多情况会直接回退到参考实现。

因此当前可以明确写出的判断是：

- `官方当前公开软件主链，对标准卷积最成熟的特化是 4x4`
- 这不等于“硬件本体只支持 4x4”
- 但它会直接影响什么样的模型在当前官方软件路径下更容易吃到收益

### 4.2 DepthwiseConv2D 当前对 3x3 有专门优化

在：

- `coralnpu/sw/opt/litert-micro/depthwise_conv.cc`

可以直接看到 `3x3 Reuse6` 这类中心区域复用优化。

因此可以确认：

- 当前官方公开软件主链，对 `3x3 depthwise` 是有专门加速思路的
- 这条线比大量 `1x1 pointwise` 更接近“当前软件已知优势区”

### 4.3 1x1 pointwise 不是当前公开主链的强项

从项目侧已保留的结果看：

- `mobilenet_v2_a050_96_imagenet_frozen_finetune_hagrid6_sample_npucycles.json`
- `formal_static_candidates_hardware_summary.md`

`MobileNetV2` 这类大量依赖 `1x1 pointwise` 的网络，在当前路径下模型级估算加速只有约 `2.62x`，明显弱于当前 `3x3-heavy` 纯卷积主线。

所以可以确认：

- 现阶段如果只依赖官方公开主链，不适合把 `1x1 pointwise` 占主导的网络当作唯一主线

### 4.4 官方仿真入口已经被项目侧实跑验证

本轮不是只读文档判断，而是把官方模拟器真实跑了一遍：

- `//sw/opt/litert-micro/test:conv_sim_test`
  - 已通过
  - 说明官方软件侧的普通卷积仿真入口可用
- `//tests/cocotb/tutorial/tfmicro:npusim_depthwise_conv`
  - 已通过
  - 运行中打印了优化路径和参考路径的周期对比
  - `opt_cycles` 明显低于 `ref_cycles`

详细命令、耗时和周期表见：

- [official_coralnpu_sim_validation_2026-07-30.md](/home/steveguo/coralnpu-gesture/gesture_project/reports/official_coralnpu_sim_validation_2026-07-30.md)

这个结果很重要，因为它说明：

- 官方源码里的卷积优化不是纸面说明，至少短卷积和深度卷积的模拟链路已经是活的。
- 后续算法筛选不能只靠静态阅读，要继续借助官方仿真入口做周期和行为验证。

进一步的详细输出已经把 `4x4` 与 `3x3` 放到同一官方测试里比较：

- 多组 `4x4` 卷积的官方优化周期收益约为 `3.08x` 到 `30.28x`。
- 同一测试中的 `3x3` 回退样例输出正确，但周期比只有 `0.89x`。

因此当前最准确的硬件适配判断是：

- 官方公开软件路径目前对 `4x4 Conv2D` 的加速支持明显更成熟。
- `3x3` 在当前公开路径中可以正确运行，但不能默认获得加速。
- 项目过去针对 `3x3` 的周期报告必须标成“项目侧估算”，不能冒充官方模拟器实测。

## 5. 对项目最重要的准确结论

### 5.1 不能再把 CoralNPU 简化成“3x3 卷积硬件”

这是错误的。

更准确的表述是：

- CoralNPU 是一个以可编程向量/矩阵计算为核心的轻量融合式处理器架构
- 当前项目过去之所以大量围绕 `3x3`，是因为当时项目自己的最强纯卷积主线恰好是 `3x3-heavy`
- 这不代表官方硬件本体只为 `3x3` 设计

### 5.2 也不能把当前公开仓库当成“矩阵引擎已经软件全打通”

这也是错误的。

更准确的表述是：

- 矩阵引擎方向在官方 RTL 中真实存在
- 但当前公开主链的软件与系统整合并未完全成熟
- 因而当前项目不能想当然地把它当作已经现成可用的完整主路径

### 5.3 当前最稳的工程策略必须分两层

第一层：

- 围绕当前公开主链已证实的软件优势区做模型与硬件共设计
- 主要关注 `plain-conv`、`4x4 Conv2D`、`3x3 depthwise`、轻量量化推理

第二层：

- 把未来更强的 `1x1 / MLP / GRU / 矩阵 tile` 需求，单独规划为后续稠密矩阵后端或矩阵扩展打通任务

### 5.4 这次实测对路线判断的直接影响

- `4x4` 是官方软件优化里真实存在的路径，但它只是“能走这条路”，不是“当前任务上已经赢过 3x3”。
- 当前项目已经有实测结果证明，纯 `4x4` 静态手势候选在当前数据集上的精度不够好，不能直接抬升成唯一主线。
- 但从官方周期角度看，`4x4` 不能再只作为“结构对照”，它已经是当前最值得继续做精度修复和混合结构探索的性能主线候选。
- 因此，当前更稳的做法仍然是：
  - `3x3` 继续做纯卷积保底线
  - `4x4` 作为官方性能主线候选，但必须通过更好的网络结构和训练方案修复精度
  - 关键点融合与动态序列路线继续并行推进

## 6. 对后续硬件改进的直接启示

### 6.1 近期硬件不应再围绕 7Z010 妥协版继续深化

`7Z010` 相关材料已经归档，不再作为当前主线判断依据。

当前硬件思考应回到：

- CoralNPU 架构里真正有长期价值的部分是什么
- 如何为后续更合理的 FPGA / SoC 资源条件准备对口的空间卷积后端与稠密后端

### 6.2 未来更合理的双后端方向

当前最值得保留的长期方向是：

1. 一个面向 `plain-conv` 的空间卷积后端
   重点服务 `3x3 / 4x4` 标准卷积和必要的 `3x3 depthwise`
2. 一个面向 `1x1 / FC / MLP / GRU gate` 的稠密矩阵后端
   重点服务关键点分支、融合头和动态时序模块

这才真正符合当前项目已经看到的算法需求分裂：

- 图像分支更偏空间卷积
- 关键点与动态分支更偏小型稠密矩阵运算
