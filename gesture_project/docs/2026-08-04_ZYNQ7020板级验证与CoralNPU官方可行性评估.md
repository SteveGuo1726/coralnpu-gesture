## 3. 本轮实际建立的脚本

路径：`/mnt/e/coralnpu_vivado/scripts`

- `query_hw.tcl`
  - 用 Vivado Hardware Manager 枚举 JTAG 链和硬件器件。
- `program_axi_dma_loop.tcl`
  - 将 `21_axi_dma_loop` 的 `system_wrapper.bit` 下载到 `xc7z020`。
- `query_xsdb_targets.tcl`
  - 枚举 XSDB 目标。
- `diagnose_axi_dma_loop_xsdb.tcl`
  - 诊断 `DAP/APU/A9` 目标状态、`ps7_init` 是否可执行、DDR/寄存器是否可访问。
- `recover_dap_and_list_targets.tcl`
  - 先恢复异常 `DAP`，再重新枚举 APU/Cortex-A9 目标。
- `run_axi_dma_loop_elf.tcl`
  - 标准下载脚本，验证了单纯标准顺序在当前板子状态下会遇到 `MMU translation fault`。
- `run_axi_dma_loop_elf_fast_halt.tcl`
  - 当前最有效脚本。核心动作是：
    1. 选中 `arm_dap` 顶层目标并做 `rst -system`
    2. 很短延时后立即选中 `ARM Cortex-A9 MPCore #0` 并停住
    3. 下载 `bit`
    4. `loadhw + ps7_init + ps7_post_config`
    5. 下载 `axi_dma_loop.elf`
    6. 在 `main` 处停住，确认程序已成功装入并进入应用入口

## 5. 对当前启动模式的判断

当前用户说明板子拨码处于 `QSPI` 模式。

从 `zynq_fsbl/main.c` 的源码可见，`FsblHandoffJtagExit()` 这条专门用于 JTAG 调试接管的路径，只有在 `Boot mode is JTAG` 时才会走。相关源码位置：

- `vitis/system_wrapper/zynq_fsbl/main.c`
- `vitis/system_wrapper/zynq_fsbl/fsbl_handoff.S`

这意味着：

- 如果后续要严格按 Vitis/FSBL 的标准 JTAG 调试路径跑，切到 `JTAG` 启动模式会更顺手
- 但在当前 `QSPI` 模式下，通过“先恢复 DAP、再尽快停住 A9”的方法，已经可以实际把应用下载到 `main`

所以本轮结论不是“必须立刻改拨码才能工作”，而是：

- 当前 QSPI 模式下可以绕过启动冲突，真实跑到应用入口
- 若后续追求更标准、更稳定的 Vitis 调试流程，建议切到 JTAG 模式再做长期开发

## 6. 对 CoralNPU 官方 FPGA 在 ZYNQ7020 的可行性判断

### 6.1 已确认可行的部分

以下部分已经通过实测和源码分析确认可行：

- `ZYNQ-7020` 板上的基础 JTAG 下载链可用
- `xc7z020` 的 bitstream 下载可用
- A9 裸机应用下载到 DDR 并进入 `main` 可用
- `PS + DDR + AXI + PL` 这种后续 CoralNPU 需要的基本 SoC 协同模式可用

因此，`ZYNQ-7020` 作为 CoralNPU 裁剪版 / 外壳版 / 早期移植验证平台是可行的。

### 6.2 不能直接宣称可行的部分

Google 官方 `coralnpu/fpga/` 目录不是为正点原子 `ZYNQ-7020` 板直接准备的开箱工程。

已核对的只读官方代码：

- `/home/steveguo/coralnpu-gesture/coralnpu/fpga/README.md`
- `/home/steveguo/coralnpu-gesture/coralnpu/fpga/rtl/chip_nexus.sv`
- `/home/steveguo/coralnpu-gesture/coralnpu/fpga/rtl/coralnpu_soc.sv`
- `/home/steveguo/coralnpu-gesture/coralnpu/fpga/rtl/autoboot.sv`

当前不能直接宣称“官方 FPGA 例程可以原封不动烧到 7020”。

原因：

- 官方 `chip_nexus.sv` 面向的是 Google 自己的 Nexus FPGA 板壳，不是当前 7020 板壳
- 该顶层含有 Nexus 板级相关的 DDR4、外设、自举、板级控制结构
- 正点原子板是 `Zynq PS + DDR3 + 本板约束/外设` 体系，板壳完全不同

### 6.3 现实可行路线

对于 `ZYNQ-7020`，更现实的路线不是“直接下官方 Nexus 顶层”，而是：

1. 保留官方 `coralnpu/` 只读，继续作为结构与接口参考
2. 基于当前已经跑通的 7020 `PS + DDR + A9 + PL` 底座
3. 为 7020 重新做一个板级外壳
4. 再评估把 `coralnpu_soc` 或更小粒度模块接入该外壳

换句话说：

- 当前 7020 板已经证明“承载 CoralNPU 移植验证”是可行的
- 但不是“把官方 Nexus bitstream 直接烧进去”这种可行

### 10.2 之前卡住的真正根因

先前一直出现的 `data abort`，最终确认不是单纯软件访问问题，而是板级包装壳地址译码错误：

- PS 访问的是系统绝对地址：
  - `0x43C00000 / 0x43C10000 / 0x43C30000 / 0x43C40000`
- `CoreMiniAxi` 内部看到的应该是窗口内偏移：
  - `0x00000000 / 0x00010000 / 0x00030000 / 0x00040000`

修复后，所有读写都统一按 `addr[19:0]` 取 offset，再做本地 decode 和 core 转发。

### 10.3 新的 A9 裸机程序做了什么

这次没有继续只做寄存器探活，而是让 A9 在板上真实完成：

1. 读取 wrapper 本地寄存器，确认 `magic/version`
2. 向 CoralNPU CSR 空间写 `RESET_CONTROL`
3. 向 ITCM 写入 4 条极小 `RISC-V` 程序
4. 设置 `PC_START=0`
5. 先写 `RESET_CONTROL=1` 释放时钟门控，再写 `RESET_CONTROL=0` 释放复位
6. 轮询 `STATUS`
7. 回读 DTCM[0]，确认程序真实执行

仓库内同步源码镜像：

- `/home/steveguo/coralnpu-gesture/gesture_project/board_validation/zynq7020_coralnpu_official/current/software/coremini_axi_execute_smoke_main.c`

这 4 条指令是：

1. `lui x1, 0x12345`
2. `lui x2, 0x10`
3. `sw x1, 0(x2)`
4. `mpause`
