# 基于大创计划书的阶段重审与路线重规划

## 1. 这份文档解决什么问题

这份文档的目的不是重写原始大创计划书，
而是把下面三件事重新讲清楚：

1. 原始计划书真正提供了哪些方向性目标。
2. 当前工作区从开始到现在，已经实际做成了什么，哪些还没有做成。
3. 在不破坏当前已验证主线的前提下，后续路线应该怎样从“探索收敛”切到“上板导向”。

需要特别明确：

```text
大创计划书是方向参考，不是已经验证过的技术结论。
当前项目路线必须以 gesture_project/docs/项目计划.md
和后续真实训练、量化、NPUSim、official replay 结果为准。
```

如果只想专门看计划书里的
“国、内外研究现状和发展动态”这一节该怎样重读，
另见：

- `gesture_project/docs/计划书_国内外研究现状与发展动态重审.md`

## 2. 重新提炼大创计划书的原始目标

结合 `/home/steveguo/coralnpu-gesture/24348025_面向手势识别的RISC-V+NPU设计.pdf`，
原始计划书想做的事情可以压缩成四条主线。

### 2.1 方向层目标

- 面向嵌入式手势识别场景
- 强调实时性、低功耗、边缘部署
- 基于开源 Coral NPU 做二次开发
- 最终希望形成可上板验证的 RISC-V + NPU 协同方案

### 2.2 软件层目标

- 做静态手势与动态手势模型筛选
- 重点关注 `CNN` 与 `CNN-LSTM`
- 做 `INT8` 量化与结构化剪枝
- 建立“模型特征 -> 硬件映射”的分析链

### 2.3 硬件层目标

- 针对 `3x3` 卷积补更强的并行 MAC / 数据重组能力
- 针对动态手势补 `LSTM` 专用处理子模块
- 改善内存访问与数据搬运效率

### 2.4 交付层目标

- 完成功能仿真
- 完成综合与时序分析
- 完成 FPGA 上板与基础性能验证

原计划书的优点是：

- 目标感明确
- 把“软件模型、硬件架构、板级验证”都纳入了一个完整闭环

但它的局限也很明显：

- 很多前提是立项时的假设，不是实测结论
- 例如“3x3 卷积占比超 60%”“LSTM 延迟占比超 50%”“应直接做 LSTM 专用模块”
  在当前工程里都不能无条件照单全收

## 3. 计划书背景与外部研究里，哪些信息其实很有参考价值

这次重新审视后，一个需要纠正的点是：

```text
不能因为计划书里有不少立项式表述，
就把它的背景信息整体当成“没什么参考价值”。
```

更准确的结论是：

- 计划书里的很多背景判断，需要外部一手资料和当前工程实测来二次校正
- 但其中有几类信息，反而值得正式吸收到当前路线里

### 3.1 HaGRID 本身支持“先静态、后动态”的推进顺序

HaGRID 论文并不是简单的“静态图像分类数据集”说明，
它强调所选 `18` 个手势都带有明确语义，
而且这些静态手势本身就是为了后续设计动态交互手势而挑选的。  
对应论文：

- HaGRID - HAnd Gesture Recognition Image Dataset  
  https://arxiv.org/abs/2206.08219

这对当前项目的启发很直接：

- 我们现在先做 `HaGRID` 静态主线，并不等于偏离动态目标
- 相反，这更像是在用最少变量先把手势语义、模型、量化和 NPU 映射跑通
- 后续如果要扩到 swipe、drag-and-drop 等动态语义，也有自然承接面

因此：

```text
“先静态、后动态”不是保守退让，
而是与 HaGRID 这类真实数据路线相容的工程分阶段做法。
```

### 3.2 MediaPipe / Gesture Recognizer 说明关键点路线绝不是旁门

MediaPipe Hands 和 Gesture Recognizer 的官方资料显示，
Google 自己的 on-device 路线并不是“必须上重 CNN 视频模型”，
而是：

- 先做 palm detector
- 再做 hand landmark
- 再做 gesture classifier

对应一手资料：

- MediaPipe Hands: On-device Real-time Hand Tracking  
  https://arxiv.org/abs/2006.10214
- On-device Real-time Hand Gesture Recognition  
  https://arxiv.org/abs/2111.00038
- Gesture recognition task guide  
  https://developers.google.com/edge/mediapipe/solutions/vision/gesture_recognizer
- On-device Real-time Custom Hand Gesture Recognition  
  https://arxiv.org/abs/2309.10858

这些资料共同说明：

- 手势识别完全存在一条“关键点/嵌入向量/轻分类器”的正统 on-device 路线
- 这条路线既支持静态输入，也支持视频流
- 还支持自定义手势类别

对当前项目的意义不是让我们马上切主线，
而是应该正式承认：

```text
关键点路线不是边缘备选，
而是必须并行量化的一条真实对照路线。
```

但它和当前 CoralNPU `3x3` 主线的关系也要说清楚：

- 如果关键点前端主要跑在 CPU/GPU/现成 MediaPipe 管线，而不是 CoralNPU，
  那它不直接证明 `3x3` NPU 硬件优化的价值
- 所以它更适合作为：
  - 应用层对照路线
  - 动态阶段低成本切入口
  - “是否真的必须做 LSTM 专用硬件”的反证工具

### 3.3 RepVGG / MobileOne 类工作强化了当前 plain-conv 主线的合理性

这次外部搜索里，对当前项目最有价值的不是再找一堆 MobileNet 变体，
而是找到了两类非常贴近我们现在需求的工作：

- RepVGG  
  https://arxiv.org/abs/2101.03697
- MobileOne  
  https://arxiv.org/abs/2206.04040

这两篇工作的共同启发是：

- 训练阶段可以使用更复杂的结构帮助优化
- 部署阶段仍然收敛成 plain-conv / plain-branch 友好的结构
- “低 FLOPs” 不一定等于“低实际延迟”
- 移动端真实延迟 often 更偏爱结构简单、分支少、算子一致的网络

这对当前项目非常重要，
因为它从外部研究上支持了我们已经在本地观测到的事实：

- `MobileNetV2` 虽然理论轻量，但在当前 CoralNPU 画像下被 `1x1 pointwise` 限制明显
- `3x3-heavy` plain-conv 主线反而更容易同时拿到精度和 NPU 加速收益

因此，
计划书里“围绕手势识别做硬件-模型协同适配”这件事，
现在最值得吸收的新解释不是“继续扩大 MobileNet 搜索”，
而是：

```text
优先继续发展更强的 plain-conv / structural re-parameterization 家族，
例如 residual_3x3、RepVGG-like、MobileOne-like 思路，
而不是把 pointwise 主导骨干当成默认最优解。
```

### 3.4 动态手势文献并不支持“默认先做 LSTM 专用硬件”

计划书把 `CNN-LSTM` 和 `LSTM` 专用子模块写得比较重，
但外部文献实际给出的图景更复杂。

这次重新看的动态方向一手资料包括：

- IPN Hand: A Video Dataset and Benchmark for Real-Time Continuous Hand Gesture Recognition  
  https://arxiv.org/abs/2005.02134
- Motion Feature Augmented Recurrent Neural Network for Skeleton-based Dynamic Hand Gesture Recognition  
  https://arxiv.org/abs/1708.03278
- DeepGRU: Deep Gesture Recognition Utility  
  https://arxiv.org/abs/1810.12514
- Spatial Temporal Graph Convolutional Networks for Skeleton-Based Action Recognition  
  https://arxiv.org/abs/1801.07455

这些资料说明了四件事：

1. 动态手势真实场景确实存在，而且数据集并不小。  
   `IPN Hand` 就包含超过 `4,000` 个手势样本和 `800,000` RGB 帧。
2. 动态路线并不只有 `LSTM`。  
   `GRU`、基于 skeleton 的 RNN、图卷积、甚至更轻的时序模型都在用。
3. 只要把输入压成 skeleton / pose / vector，
   动态识别模型可以明显轻很多。  
   `DeepGRU` 明确强调只用 skeleton/pose/vector 数据即可。
4. 3D-CNN / 多模态视频模型当然能做，
   但它们对当前 CoralNPU 上板最短路径并不友好。

所以，
这部分重新审视后的更新结论应该是：

```text
动态手势值得做，
但“LSTM 专用硬件”只能是动态 profiling 之后的候选结果，
不能再被当成先验主线。
```

### 3.5 FPGA / 低比特量化研究对板级展示有参考价值，但不能替代当前 Coral 主线

计划书里强调 FPGA 上板，这个方向本身没有错。
而外部硬件研究里，
真正值得参考的是“如何做低功耗、低比特、可验证的板级闭环”，
例如：

- FINN: A Framework for Fast, Scalable Binarized Neural Network Inference  
  https://arxiv.org/abs/1612.07119
- Benchmarking Quantized Neural Networks on FPGAs with FINN  
  https://arxiv.org/abs/2102.01341

这些工作提醒我们：

- 低比特量化确实会显著改变 FPGA 上的并行度与吞吐
- 板级展示不一定非要从最复杂的完整 SoC 语义开始
- “先拿到可对账、可复现、低比特、局部闭环”的工程策略是合理的

但它们不能直接替代当前项目的主线，
原因也很明确：

- `FINN` 一类框架主要服务于 FPGA streaming/QNN 流程
- 当前项目的正式问题仍然是：
  如何在 CoralNPU 现有 ISA / toolchain / `conv.cc` / RTL 语义上完成协同优化

因此更合适的定位是：

- 可把 `FINN` / 低比特 FPGA 文献作为板级展示方法论参考
- 不能把它们变成“另起一套全新硬件编译框架”的替代主线

## 4. 当前工作区从开始到现在，真实做到了什么

如果按“是否经过真实证据闭环”来划分，
当前进展已经明显不是“只做了前期调研”，
但也还没有达到“硬件正式上板主线已完成”。

### 3.1 已经完成的软件与算法闭环

这部分进展是当前整个工程里最扎实的一层。

已经完成的事实包括：

- 已建立手势识别候选模型搜索、训练、量化、评测链路
- 已形成正式静态主线模型：
  - `static_cnn_regularized_3x3_i96_e70_hagrid6_sample`
- 已完成正式静态主线的真实闭环：
  - Keras test accuracy：`77.29%`
  - INT8 TFLite test accuracy：`77.07%`
  - INT8 TFLite 大小：`94,480 B`
- 已完成 MobileNet 系列对照尝试，并确认当前仍不如静态 3x3-heavy 主线
- 已经不是“只凭 PDF 假设 3x3 值得做”，而是通过真实模型确认：
  - 当前正式主线是强 `3x3-heavy`
  - 适合作为 CoralNPU `3x3` 优化验证主线

这意味着：

```text
在“模型选择与部署闭环”这一层，
当前工作区其实已经走得比大创计划书里最初写法更扎实，
因为现在不是纸面设想，而是已经有真实训练、量化和逐图评测结果。
```

### 3.2 已经完成的 CoralNPU official 软件主线收敛

这部分是当前工程第二个最扎实的成果。

当前正式 `conv.cc` current best 主线是：

- `strategy = 8`
- `x4_id32 / x4_id64`
- 静态主体块调度
- interior `6tap` 分带
- 顶/底 `4/6/4` 分带

当前四层 official 最优总量：

- `opt_cycles = 17,596,916`
- `mismatch = 0`

这条线的意义非常大：

- 它已经不是“单个 patch 有一点感觉”
- 而是正式形成了 current best 软件保底线
- 后续任何硬件语义尝试都必须建立在它不被破坏的前提下

这部分工作和原计划书相比，
虽然没有直接落到 RTL，
但已经把“3x3 方向是否值得继续”这件事做成了强证据。

### 3.3 已经完成的第二层硬件语义探索收敛

当前还没有完成真正可交付的硬件修改正式主线，
但已经不再是完全没有方向。

到目前为止，
唯一仍值得保留为硬件参考候选的语义样本是：

- `rowhandoff_rowbase_recur mode=1`

它相对同骨架 `emptyhooks` 的净收益为：

- `conv2_3x3_a = -38,639`
- `conv2_3x3_b = -9,205`

而且：

- `mismatch = 0`
- 不是空噪声
- 不是只打到错层的偶然布局效应

这说明当前已经拿到一条“可供 RTL 参考”的小语义：

```text
在 48x48 + id32 主体层上，
跨 row 传递 next-row base state
是目前唯一值得继续保留的硬件参考方向。
```

### 3.4 已经开始形成上板导向材料

最近的工作已经不是单纯继续扫 patch，
而是开始把这条唯一硬件候选翻译成更接近板级执行的材料：

- `gesture_project/docs/strategy8_上板导向主线说明.md`
- `gesture_project/docs/strategy8_rowhandoff_mode1_RTL语义整理.md`
- `gesture_project/docs/strategy8_rowhandoff_trace_counter版说明.md`
- `gesture_project/docs/strategy8_板级最小验证清单.md`
- `gesture_project/reports/conv2_3x3_b_ctrl_4x8x8_rowhandoff_trace_pseudo.sv`

这说明当前工程已经进入：

```text
从“继续找可显影 patch”
向“把唯一有效语义抽成板级最小闭环”
过渡的阶段。
```

## 5. 哪些方向已经被实证支持，哪些还只是方向感

### 4.1 已验证有效

目前已经被当前工作区真实支持的结论包括：

- 以静态手势为先、先把变量数压低，是正确推进顺序
- `static_cnn_regularized_3x3_i96_e70_hagrid6_sample` 是当前正式主线模型
- `3x3-heavy` 静态 CNN 路线在当前数据与硬件画像下优于现阶段 MobileNet 对照
- CoralNPU `conv.cc` 沿 `strategy=8` 收敛是有效的
- 48x48 主体层存在继续向更贴近 RTL 的控制语义推进的空间
- `rowhandoff_rowbase_recur mode=1` 是当前唯一可保留的硬件参考候选

### 4.2 方向上正确，但目前没有完成验证闭环

下面这些内容仍然只能算“方向上合理，但尚未被当前工程完成验证”：

- 动态手势是否必须纳入当前阶段主线
- `CNN-LSTM` 是否真是当前项目最值得实现的动态模型
- `LSTM` 是否值得直接专门硬件化
- 是否需要真正改 MAC datapath，而不仅是控制/状态复用
- 是否已经有足够证据支持直接进入较大规模 RTL 结构改造
- 是否已经具备完整板级 end-to-end 演示条件

### 4.3 已证伪或当前阶段明确不值得再回去

这一层非常关键，因为它决定了后面不能再把时间耗回旧坑里。

当前已确认不要回去的方向包括：

- `3x3 repack`
- `3x3 postprocess` 软件融合
- 边界行中带块调度
- 边界点 `32/64` 窄特化
- 继续扫更多 `split* / tailrows* / tailcols* / ocblock32_*`
- `mode6_terminalptr`
- `post_right_edge_row_terminal mod4eq3`
- 继续只沿纯 row-window 扫更多触发条件

这些方向有的是真负收益，
有的是平台化，
有的是虽然能显影但不再值得作为主线继续扩。

## 6. 用大创计划书和外部研究一起来审视当前整体状态

如果把当前状态和原始计划书逐项对照，
更准确的判断不是“做偏了”，
而是“前半段做得更实，后半段还没收口”。

### 5.1 相比计划书，哪些地方实际上是超前或更扎实的

#### 模型与部署层

相较计划书最初的抽象表述，
当前已经完成：

- 真实训练
- 真实 INT8 量化
- 真实 TFLite 逐图评测
- 候选模型对照淘汰

这一层不是滞后，反而比原始计划书更扎实。

#### 3x3 软件优化层

相较“先假设 3x3 值得优化”，
当前已经形成：

- official current best
- 多轮 worktree replay
- 对热点层的细粒度量化
- 对失败方向的系统归档

这也属于比计划书更实的一层。

### 5.2 相比计划书，哪些地方明显滞后

#### 真正的硬件主线收口

当前还没有一条我愿意称为：

```text
可直接交付上板的 coralnpu 手势识别硬件修改正式主线
```

原因不是完全没方向，
而是还差这最后一段：

- 从 C 级 patch 语义
- 抽成 RTL-like 状态
- 接入 trace/counter
- 做单层 correctness / cycle 对账
- 再形成近似生效版

这一步现在仍未做完。

#### FPGA 上板验证

原计划书把上板写进了最终目标。
而当前状态是：

- 已经有上板导向文档
- 已经有最小验证清单
- 但还没有真正进入板级 trace/counter 实施与对账

也就是说：

```text
离“真上板”最近的一步已经被明确出来，
但这一步本身还没正式完成。
```

#### LSTM / 动态手势硬件化

原计划书对这一层写得很重。
但当前证据链和外部文献都不支持马上把它当主线。

更准确的结论是：

- 动态/LSTM 仍是项目远期方向的一部分
- 但不是当前最短上板路径
- 现在若硬切过去，会重新引入过多不确定变量
- 而且动态方向下一步更该先比较：
  - skeleton + GRU
  - skeleton + TCN
  - skeleton + ST-GCN / graph family
  - 再判断 `LSTM` 是否真值得专门硬件化

## 7. 重新审视后，应该正式补进路线图的并行方向

这次广泛复核之后，
当前路线不应只剩一条“继续抠 48x48 patch”的线，
而应当正式增加三条有边界的并行方向。

### 7.1 并行方向 A：继续强化 plain-conv 主线，而不是回 pointwise 主导

这条线和当前硬件主线最一致。

建议明确增加：

- `residual_3x3`
- `RepVGG-like`
- `MobileOne-like`

它们的共同要求是：

- 训练阶段允许更强表达能力
- 部署阶段尽量保持 plain-conv 友好
- 尽量不把模型热点重新拉回 `1x1 pointwise` 主导

这条线当前优先级应高于继续横扫更多 MobileNet 小变体。

### 7.2 并行方向 B：建立关键点路线正式对照，不再只停留在文档里

建议至少做一个最小闭环原型：

- 输入：MediaPipe Hands / Hand Landmarker 的 `21` 点 landmarks
- 静态：
  - `MLP`
  - 小 `FC`
- 动态：
  - `GRU`
  - `TCN`

这条线的目的不是马上替代当前主线，
而是回答三个现在还没被量化的问题：

1. 如果把输入压成 landmarks，正式数据准确率能到多少。
2. 动态手势是否必须用 `LSTM`，还是 `GRU/TCN` 已够用。
3. 关键点路线的总系统成本是否会反过来压过图像 CNN 主线。

### 7.3 并行方向 C：为上板展示准备“低风险备线”，但不替代 Coral 正线

这条线的目标不是另起炉灶，
而是降低最终“完全上不了板”的风险。

可以吸收的外部经验包括：

- 更强调 full integer quantization
- 更强调局部闭环和计数可观测
- 更强调小模型、小输入、小范围可演示

但这条线仍应服从当前主问题：

- 以 CoralNPU current best 为保底线
- 以 `rowhandoff mode=1` 为唯一硬件参考候选

## 8. 当前整体状态的一句话判断

当前最准确的项目阶段判断应该是：

```text
已经完成“算法闭环 + official 软件主线 + 第二层硬件语义收敛”的前半段，
但尚未完成“板级可交付硬件主线”的最后收口。
```

换一种更工程化的表述：

- 不是没有可参考主线
- 但还没有完成真正可上板的正式硬件主线

当前“可交付的一条参考主线”应理解为：

1. 算法保底线：
   `static_cnn_regularized_3x3_i96_e70_hagrid6_sample`
2. official 软件保底线：
   `strategy=8 + x4_id32/x4_id64 + 静态主体块调度 + interior 6tap + 顶/底 4/6/4`
3. 唯一硬件参考候选：
   `rowhandoff_rowbase_recur mode=1`

这三层合在一起，
才是当前阶段真正已经收敛出的“参考主线”。

## 9. 重新规划后的路线

后续路线不应再照原计划书的顺序机械推进，
而应按“证据最强、最接近上板、风险最可控”的顺序重排。

### 9.1 第一阶段：冻结已经做实的三条保底线

这一步的目标不是继续优化，
而是先把后续一切工作的基座固定住。

需要冻结的内容：

#### 算法保底线

- `static_cnn_regularized_3x3_i96_e70_hagrid6_sample`

#### official 软件保底线

- current best `17,596,916`
- `mismatch = 0`

#### 唯一硬件参考候选

- `rowhandoff_rowbase_recur mode=1`

要求：

- 不破坏 current best
- 不把已判死方向重新打开
- 不再把 `mode=2/3/4/6` 这类分支当成后续主路线

### 9.2 第二阶段：从 patch 扫描转成 RTL-like 状态收口

这一步是当前最关键、也是最缺的部分。

目标不是继续追更多 `conv.cc` 细分 patch，
而是把 `mode=1` 抽成明确的状态机语义：

- 何时 produce
- 何时 consume
- 何时 invalidate
- 如何与 row advance / next-row base 选择对接

当前已有材料：

- `strategy8_rowhandoff_mode1_RTL语义整理.md`
- `conv2_3x3_b_ctrl_4x8x8_rowhandoff_trace_pseudo.sv`

后续应优先补的是：

- 更明确的 trace/counter 计数口径
- 与 current best / emptyhooks / mode=1 的对账口径
- 单层 `conv2_3x3_b / conv3_3x3_b` 的板级最小输入闭环

### 9.3 第三阶段：先做 trace/counter 版，再做近似生效版

这一步是连接“软件语义”和“真硬件”之间的桥。

建议顺序必须是：

1. trace/counter 版  
   只证明状态流、命中、失效、计数是否符合预期。
2. 近似生效版  
   再让 next-row base 选择真正受 rowhandoff 状态影响。
3. 单层板级验证  
   优先 `conv2_3x3_b`，再看 `conv3_3x3_b`。

这一步的价值在于：

- 它比直接改大 datapath 风险低得多
- 它比继续扫软件微变体更接近“什么时候能上板”的核心问题

### 9.4 第四阶段：并行补两条外部研究支持的候选线

这一步是这次重审后最重要的新变化。

后续不应只有硬件收口一条线，
而应并行做两条小规模、有边界、可快速止损的候选验证：

#### 候选线 A：RepVGG-like / MobileOne-like 3x3-heavy 模型

目标：

- 继续提高正式静态精度
- 尽量保持 `3x3` 主导
- 检验 structural re-parameterization 是否能同时服务精度与部署

#### 候选线 B：landmark + GRU/TCN 小闭环

目标：

- 量化关键点路线的真实精度/复杂度
- 为后续动态阶段提供低变量起点
- 判断 `LSTM` 是否还有必要作为优先时序候选

这两条线都不该破坏 current best，
但都应该正式进入项目路线图，而不是只停留在想法层。

### 9.5 第五阶段：再决定是否进入更大硬件改造

只有在 trace/counter 版和近似生效版都站稳以后，
才适合重新评估下面这些问题：

- 是否值得真正改更大范围的 row-base / spatial reuse 控制器
- 是否值得改 MAC datapath
- 是否值得扩大到更多层甚至全模型
- 是否值得把动态/LSTM 重新提上近期议程

这一层现在还不该抢跑。

### 9.6 第六阶段：动态手势 / LSTM 路线后移但不删除

基于当前全部实测，
对动态/LSTM 的更合理定位应更新为：

- 保留为项目后续可扩方向
- 不作为当前最短上板路径
- 必须等静态主线和板级最小闭环做稳后再重启

如果后面要回到动态方向，
也应先做：

- 动态数据与标签闭环
- 时序模型 profiling
- GRU/LSTM/TCN 对照
- 再决定是否值得硬件化

而不是直接沿原计划书写法去做独立 LSTM RTL。

## 10. 对“什么时候能上板”的重新回答
