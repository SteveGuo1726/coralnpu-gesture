## 0. 一页结论

> **本节的结论已被阶段 A 的实测数据修订过一次**（见 §1.5）。修订处标了 ★。

| # | 问题 | 根因（已核实） | 决策 | 已有证据 |
|---|---|---|---|---|
| P1 | 手必须占极大画面 | 模型只见过"手占满画面"的输入，**实测**：手占 25% 时 top-1 **6.8%**（瞎猜 5.6%），手占 100% 时 93.4% | **改训练几何**：整帧 + 尺度抖动覆盖手占 5%~40%；配合输入分辨率搜索（§2.1）。**不引入检测器** | ✅ 已有曲线（§1.5） |
| P2 | 部分类区分度低 | ★**数据否定了这个前提**：训练几何下混淆矩阵很干净（最大非对角项只有 8/50 = palm→four），镜像对 peace/stop/two_up **不是**主要误差 | ★**不合并类目**。真正的"分不清"是 P1 造成的整体退化 | ✅ 混淆矩阵（§1.5） |
| P3 | 没有"无手势"、没有置信度 | ★实测确认：手一小，**输出几乎全部塌到 `call`**（手占 25% 时 call 独占 56%，占 6% 时 68%）——这正是用户看到的"没手势报 call" | ① 先靠修 P1 消掉大部分；② 再加 `no_gesture` 类（可从已有标注挖）；③ **改 RTL 导出 FC logits** 才能有真置信度 | ✅ 逐类表（§1.5） |
| P4 | CPU 解码占 9.3/30 ms | libjpeg 软解 MJPEG 640×480 | **换 UYVY**（相机支持，UVC 免熵解码）；二期把 YUV→RGB+缩放搬进 PL | 待做（阶段 D1） |

**最重要的一个纠正**：我上一轮以为"要提高分辨率让手占更多像素"。**这不成立**——
缩放到固定输入尺寸后，手占多少像素只取决于**手占画面的比例**，与源分辨率无关。
HaGRID 全帧里手占短边**中位数 15%**（实测，p5=7% / p95=34%）→ 缩到 96 后手约 14 px。
我们部署时手占几个百分点 → 约 5 px。**所以修法是让训练几何与部署几何一致。**
（而"输入尺寸要不要提到 128/160"是另一个独立问题，见 §2.1。）

## 1.5 ★ 阶段 A 实测结果（2026-09-12，全部可复现）

工具：`gesture_project/algorithms/static_cnn/eval_int8_deployment.py`
（venv 在 `~/gfeval/venv`，numpy<2 + pillow + tflite-runtime；输入按 `q = u - 128` 构造，
与 PL 的 `gestureflow_hp0_rgb_loader.sv` 同约定）。
报告：`gesture_project/reports/2026-09-12_A2_*`、`2026-09-12_A3_*`（含 `confusion.csv`、
`predictions.csv`、`summary.json`）。

### A2 · 训练分布（手部裁剪，test 划分，200/类，n=3600）

**top-1 = 99.00%** —— 与模型声称的 98.88% 一致，**证明工具链与板上模型是同一份东西**。

### A3 · 部署几何（同一批受试者，模型输入改为一帧里的窗口，窗口大小使手占 h）

| 手占模型输入 h | n | top-1 | 实际窗口 |
|---|---|---|---|
| 1.00（贴紧手） | 900 | **93.44%** | 手框大小 |
| 0.50 | 900 | **46.67%** | 2× 手框 |
| 0.25 | 900 | **6.78%** | 已钳到整帧 |
| 0.12 | 900 | 7.56% | 整帧 |
| 0.06 | 900 | 7.44% | 整帧 |

（384p 帧只有 384×512、手约 100 px，所以 h≤0.25 时所需窗口已超过整帧，
三档其实测的是同一个"整帧"几何 —— 这一点必须记住，别把 0.25/0.12/0.06 当成三条独立数据。）

**结论（这是本轮最重要的三个数字）**：
1. **几何一崩就全崩**：93.4% → 46.7% → 6.8%。到整帧几何时**低于瞎猜**（5.6%），
   而 HaGRID 的真实工作点就是整帧（手占 15%）。**模型部署在它从没见过的尺度上。**
2. **失败方向是"塌向 call"**：h=0.25 时 call 独占 56%，h=0.06 时 68%；
   peace / peace_inverted / rock / stop / three / four 全部 0%。
   ⇒ 用户在相机上看到的"没手势也报 call"，**根因是几何，不是缺 no_gesture 类**。
3. **P2 的前提被否定**：h=1.0 时最大的非对角项是 `palm→four` 8/50，镜像对并未突出。
   所以**不能靠合并类目来提分**；分不清的现象是几何退化的一部分。

### 关于"手占画面比例"的分布（从标注统计，n=36000）

```
手的长边 / 图像短边： p5=0.07  p25=0.11  p50=0.15  p75=0.20  p95=0.34
```

⇒ **HaGRID 的工作点是"手占画面 15%"**；这给了阶段 B 训练几何的锚点：
抖动范围取 **5%~40%**（覆盖 p5~p95 再放宽一档），中心放在 15%。


## 1. 现状（全部从源码/实测读出，不是回忆）

### 1.1 现行 INT8 模型（板上跑的那个）

`models/hagrid_v1_500k_384p_targethand_student_4x4_rvv_distill_20260827/model.keras`：

```
Input 96x96x3
Conv2D 16  k=4x4 s=1     96x96x16
Conv2D 16  k=4x4 s=1
MaxPool                  48x48x16
Conv2D 32  k=4x4 s=1
Conv2D 32  k=4x4 s=1
MaxPool                  24x24x32
Conv2D 48  k=4x4 s=1
Conv2D 48  k=4x4 s=1
MaxPool                  12x12x48
Conv2D 64  k=1x1
GlobalAveragePooling
Dense 18
```

- **全部是 4×4 稠密卷积**，没有 3×3、没有任何深度卷积。
- 参数 ≈ 4.2×10⁴（INT8 约 42 KB），**手算 MAC ≈ 1.1×10⁸ MAC/帧**。
  对比：MobileNetV2@96×96 ≈ 1.9×10⁷ MAC（**少 5.8×**），MobileNetV3-Small ≈ 0.8×10⁷（**少 14×**）。
  ⇒ 换架构是**本轮最大的一根杠杆**，比调 RTL 有效得多。

### 1.2 现行 RTL（`innovation_npu/rtl/`，约 9.7 K 行 SV）

可复用：`line_window*/line_delay*/activation_bank/output_bank`（行缓存/激活存储）、
`requant_relu`（重量化+激活）、`hp0_*`（HP0 读写/张量/权重 DMA）、
`axi_stream_rgb_ingress`（**已经有一条 AXI-Stream 的 RGB 输入通路**）、
`mac_tile`/`mac_tile_dmp`（含双乘打包）、`layer_chain_*_hp0_axil`（顶层调度）。

需新增：**3×3 深度卷积引擎**（depthwise 是带宽受限而非 MAC 受限，行缓存窗口要重做）、
**逐通道乘子（per-channel scale）**（MobileNet 的 DW 之后 BN 折叠成 per-channel 乘子，
现行 `requant_relu` 是 per-output-vector 参数，需要确认/扩展）、
**权重常驻存储**（见 §2.4）、**FC logits 导出**（见 §2.5）。

### 1.3 数据集现状

- `datasets/processed/hagrid_v1_500k_384p_targethand_subject_split_20260815`：
  train/val/test = 18 类 × 手部裁剪，test 每类约 4.6~5.0 K 张。
- `datasets/raw/hagrid_v1_500k_384p/hagrid-sample-500k-384p.zip` 内含
  `ann_train_val/<class>.json`（**bbox + labels + landmarks**）和整帧 `hagrid_500k/train_val_<class>/*.jpg`。
  ⇒ **整帧和标注我们本地都有**，做几何实验不需要重新下载。
- 上游 HaGRID 的定义（查证过）：
  - **HaGRID v1**：552,992 张 1920×1080，18 类，**另有 `no_gesture` 类 123,589 样本**；拍摄距离 0.5–4 m。
  - **HaGRIDv2（2024-09）**：1,086,158 张，**33 类 + 独立 `no_gesture` 类**（2,164 样本，
    200,390 个 bbox），另有 hand landmarks 与 **官方的 gesture detection / hand detection /
    full-frame classification 三套预训练模型**；512px 轻量版 119.4 GB。
  - **官方基线做的是"整帧分类"，不是手部裁剪** —— 我们的裁剪是自选的，正是 P1 的来源。

### 1.4 实测性能现状（板上，2026-09-12）

| 项 | 数值 |
|---|---|
| 相机 | See3CAM_CU30，MJPEG 640×480，UVC |
| 摄像头真实上限 | 27.3 ms/帧（≈36.6 fps 上限）；实测稳定 15 fps（相机自身限速） |
| 端到端 | 30.0 ms = 解码 9.2 + 缩放 2.8 + NPU 18.0 |
| PL 单帧 cycle | 见交接 #146/#151（PL 17.02 ms + CPU 1.99 ms，各层 cycle 逐层有记录） |

⇒ **CPU 侧 12.0 ms / 30 ms = 40% 花在软件解码+缩放上**（P4）；
⇒ NPU 18 ms 跑 1.1×10⁸ MAC ⇒ ≈6.2 GMAC/s；换成 1.9×10⁷ MAC 的 MobileNetV2 同效率 **≈3 ms**。

## 2. 目标架构（软硬件协同）

**一句话**：把"相机 → 分类"做成一条**全在 PL 里、权重常驻、带置信度输出**的流水线，
上游训练一个**整帧输入、含 no_gesture、面向部署几何**的 MobileNet 级模型。

```
UVC 相机 (UYVY 640x480)
   │  CPU 只做 UVC DMA + 一次 buffer 交接（目标 <2 ms）
   ▼
PL: YUV→RGB → 行缓存/ROI 裁剪 → 面积平均缩放到 96x96        [二期, §2.3]
   ▼
PL: NPU —— 3x3 DW + 1x1 PW 流水, 权重全部片上常驻          [§2.4]
   ▼
PL: GAP + FC → 18+N 个 logits 写回 DDR (不再是只有 argmax)  [§2.5]
   ▼
CPU: softmax / 能量分 / 拒识判定 (几十微秒)                 [§2.5]
```

### 2.1 输入尺寸 × 骨干的联合搜索空间（由 A3 数据倒推出来的）

A3 说明了两件事：**模型必须在"手占 15%"的几何上训练**；而手在输入里只剩 **14 px**（96×96 时）
时，区分 `three`/`three2` 这类"手指数量 + 朝向"的差别会很吃力。
但**输入尺寸是独立于几何的自由度**——把输入做大，手占的像素就变多，代价是算力 ∝ 面积²。
这就出现一个真实的协同设计问题：**在同样的算力预算下，"小模型 + 大输入" 是否优于 "大模型 + 小输入"？**

| 骨干 | 输入 | 估算 MAC/帧 | 相对现行（1.11×10⁸） | 手占 15% 时的手（px） |
|---|---|---|---|---|
| 现行 4×4 稠密栈 | 96² | 1.11×10⁸ | 1.0× | 14 |
| MobileNetV3-Small w1.0 | 96² | ≈1.1×10⁷ | **0.10×** | 14 |
| MobileNetV3-Small w1.0 | 128² | ≈2.0×10⁷ | 0.18× | 19 |
| MobileNetV3-Small w1.0 | 160² | ≈3.1×10⁷ | 0.28× | 24 |
| MobileNetV3-Small w1.0 | 192² | ≈4.4×10⁷ | 0.40× | 29 |
| MobileNetV2 w1.0 | 160² | ≈1.5×10⁸ | 1.4× | 24 |
| MobileNetV2 w1.0 | 192² | ≈2.2×10⁸ | 2.0× | 29 |

（MAC 数是按 224² 的公开值按面积折算的**估算**，用来排序，不作为结论；
最终必须以实测为准——这点写入阶段 B 的门槛。）

两个必须同时记住的代价：
1. **深度卷积是带宽受限、不是 MAC 受限**。MAC 少了 10× 不等于速度快 10×；
   真正的瓶颈永远是"每层要不要把激活写回 DDR"。⇒ 这正好把 H1/H3（权重常驻 + 层间融合）
   从"锦上添花"变成"必须做"。
2. **激活内存 ∝ 输入面积**。96²→192² 是 4×，对"层间片上融合"的可行性影响很大，
   必须先过 §5-C0 的代价模型再定。

**因此阶段 B 的第一件事不是训练，而是把这个表里的 4~6 个组合各训一版**，
用"部署几何准确率 / MAC / 激活字节"三个数挑出 1~2 个进入硬件。



### 2.2 模型侧（软件）

- **输入 = 整帧**（不做手部裁剪）；训练时加 **尺度抖动**：把整帧按随机倍数缩放后再裁剪，
  使手占画面在 **5%~40%** 之间（锚点 15%，即 A3 实测的 HaGRID 工作点），
  另加平移/旋转/亮度抖动。**这是修 P1 的核心动作，而且不需要改任何硬件。**
- 骨干：**MobileNetV3-Small / MobileNetV2**，按 §2.1 的表做输入尺寸 × 宽度的小网格。
- 类别：**18 类 + `no_gesture`**；★**不合并镜像对**（A3 已否定这个前提）。
- 量化：INT8（QAT 优先），per-channel scale 必须是硬件可实现的（见 §2.4）。

### 2.3 前端（修 P4）

- **一期（便宜、立刻可测）**：`gf_camera` 改成优先协商 **UYVY**（相机支持 640×480@60 UYVY）。
  取消 libjpeg 熵解码，解码段目标 **9.2 ms → ≈1.5 ms**（只剩 YUV→RGB 的整数乘加）。
  同时 JPEG 块效应消失，对精度只有好处。
- **二期**：把 YUV→RGB 与面积平均缩放搬进 PL（`axi_stream_rgb_ingress` 已有入口）。
  指标：CPU 端到端从 12.0 ms → **<2 ms**，并把这个数字作为"零 CPU 数据通路"的证据。

### 2.4 硬件创新（要有可测量的收益）

| 编号 | 改动 | 为什么值得做 | 必测指标 |
|---|---|---|---|
| H1 | **权重全片上常驻** | 现模型 INT8 仅 42 KB，ZCU104 有 312×BRAM36 + 48×URAM（合计 ≈3 MB）。常驻后**每帧权重 DMA 归零** | 权重 DMA 字节/帧、BRAM/URAM 占用、cycles/帧 |
| H2 | **3×3 DW + 1×1 PW 流水引擎** | DW 是带宽受限：需要行缓存 + 每周期多通道并行；PW 复用现有 DMP MAC tile | MAC/cycle、DSP 数、DDR 激活字节/帧 |
| H3 | **层间片上融合** | 现状每层把激活写回 DDR 再读回（16 MB reserved 区）。融合相邻层可大幅降 DDR 流量 | DDR 读/写字节/帧（改动前后对比） |
| H4 | **FC logits 导出** | 没有它就永远没有置信度/拒识/早退（修 P3） | 新增寄存器语义 + logits bit-exact 对账 |
| H5 | **置信度门控早期退出** | 简单帧提前退出 → **平均**延迟与能耗下降；这是最有论文价值的点 | 退出率-精度曲线、平均 cycles/帧、iso-accuracy 能耗 |

> ⚠️ **认清新颖性**：查证后确认"双乘打包（DMP）"**已被发表**（我们引用的 MDPI 论文；
> 另有一篇中文期刊工作用"符号位单独处理重新封装双乘法器"在 Zynq UltraScale+ 上跑
> MobileNetV2 达 130.6 GOPS / 4.1 W）。**因此 DMP 本身不能作为主打创新点**，
> 只能作为既有基础。真正可能站得住的是 **H5（自适应推理：延迟/能耗随输入难度变化）**
> 与 **H1+H2+H3 的"相机到分类全 PL 化 + 权重常驻"系统级指标**。
> 顶刊级**结论**需要 3~6 个月量级的工作量；本文档把它作为 12 个月目标，
> 一个月内可交付的是**可复现的系统 + 完整数据表**（这本身就是投稿的必要条件）。

### 2.5 置信度与拒识（修 P3）

1. **训练侧**：加 `no_gesture` 类（数据来源见 §4），并用"拒识感知"的损失
   （label smoothing + 对负类加权）。文献结论（MDPI《…Unseen Non-Target Gestures》2025）：
   数据增强 + 损失项比单纯调阈值有效得多。
2. **硬件侧**：H4 把全部 logits 写回 DDR，CPU 上算 softmax 与 **能量分**
   `E = -logsumexp(logits)`（OOD 检测的强 baseline），阈值由验证集上的
   **误拒率-漏拒率曲线**决定，而不是拍一个 0.5。
3. **不做的**：不在硬件里造一个"置信度输入"——那样既不可解释也无法标定。

## 4. 数据集决策

| 候选 | 规模 | 可用性 | 结论 |
|---|---|---|---|
| 现有 384p 18 类裁剪 | 36 GB，本地已有 | 已有 | **保留做预训练与消融**，但**不再用作最终几何** |

| HaGRIDv2 512px 轻量版 | 119.4 GB | 需下载 | 若带宽允许，作为"更多类/更好质量"的来源 |
| 自采（ZCU104 + 现相机，部署几何） | 几小时录制 | 需板子（用户要求先不连） | **最终判据**：上板前用它做验收，量小但分布正确 |
| Jester / IPN Hand / NVGesture | 动态手势 | 仓库里已有 IPN Hand | 本轮不动（静态优先） |

**决策**：
1. **几何实验**用本地整帧 + 标注（不下载）。
2. **负类**先从已有标注挖 `no_gesture`，再视需要补 HaGRIDv2 的 493 MB 包。
3. **类目**先量混淆矩阵，镜像对合并与否由数据决定。
4. **最终验收集 = 自采部署几何数据**（等板子恢复后录，几十秒~几分钟即可）。

## 5. 路线图（阶段 / 门槛 / 指标）

### 阶段 A：把决策变成数据（**不需要板子**）
- ✅ **A1** 推理环境：`~/gfeval/venv`（numpy<2 + pillow + tflite-runtime 2.14；
  **numpy 2.x 会让 tflite-runtime 直接 `_ARRAY_API not found`，必须钉 <2**）。
- ✅ **A2** 训练分布基线：**top-1 99.00%**（test 200/类，n=3600）+ 混淆矩阵。
- ✅ **A3** 几何扫描：h=1.00/0.50/0.25/0.12/0.06 → **93.4 / 46.7 / 6.8 / 7.6 / 7.4 %**；
  并从标注统计出"手占短边"的分位数（中位数 15%）。
- ⬜ **A4** 拒识基线：用 A2/A3 已导出的 `predictions.csv`（含 `p_max`/`margin`/`entropy`）
  扫阈值出误拒-漏拒曲线。**注意**：A3 已经说明"拒识"在当前模型上救不了场，
  A4 的价值是给**新模型**提供同一个基线口径。
- **A4 之后可以立刻启动的东西**：从 `ann_train_val/*.json` 挖 `no_gesture` 手框样本
  （已有标注，零下载），并把整帧 + 尺度抖动的数据管线搭起来（阶段 B 的输入）。
- **出口门槛**（A2/A3 已达成）：三个数字 + 一句话结论 ⇒ **已产出，见 §1.5。**

### 阶段 B：新模型（软件）
- **B1** 整帧 + 尺度抖动数据管线（复用本地 zip + 标注）+ `no_gesture` 采样。
  评测一律用 **A3 那套工具**（`eval_int8_deployment.py frames`），这样才能和 §1.5 直接比。
- **B2** **小网格对照**（不是训一版）：骨干 {MBV3-S, MBV2} × 输入 {96,128,160,192} × 宽度 {0.5,0.75,1.0}
  取 6~8 个点，**每个点都报"部署几何准确率 + MAC + 激活字节"**，然后挑 1~2 个进硬件。
  **先做 96² 的两个点确认几何修法有效（把 6.8% 拉回 90%+）**，再决定要不要加大输入。
- **B3** 加 `no_gesture` + 拒识损失；出"已知类准确率 / 负类拒识率"双指标、
  以及误拒-漏拒曲线（与 A4 同口径对比）。
- **B4** INT8 QAT + per-channel scale，导出 TFLite，**在 PC 上用同一个工具复现**，
  并给出"板上应得准确率"的预测值（后续上板对账用）。
- **出口门槛**：部署几何下已知类准确率 ≥ 目标、负类拒识率 ≥ 目标；
  MAC ≤ 5×10⁷；**与现行模型在同几何下准确率不降**。

### 阶段 C：硬件重构（ZCU104）
- **C0（先做，省钱省时间）**：**写一个周期级代价模型**（Python/C++）：
  给一层 (C_in,C_out,H,W,k,stride) 与硬件参数 → 预测 cycles、DDR 字节、DSP/BRAM 用量。
  **所有架构决策先在代价模型上比，再动 RTL** —— 这是"3 分钟仿真上限"下唯一能快速迭代的办法。
- **C1** 3×3 DW 引擎 + 1×1 PW 复用（H2），模块级短仿真（≤3 min）。
- **C2** 权重常驻（H1）+ 层间融合（H3），用 C0 的预测指导，RTL 只做需要的那部分。
- **C3** FC logits 导出（H4），与 PC 侧 bit-exact 对账（沿用现有 golden 机制）。
- **C4** 早退（H5）：先做"两层退出点"的可行性验证。
- **出口门槛**：C0 预测 vs 上板实测误差 <20%；cycles/帧、DDR 字节/帧、DSP/BRAM 三项有前后对比。

### 阶段 D：上板（用户许可后再做）

- **D2** 自采部署几何数据集上的端到端验收（准确率 + 拒识率 + fps + 功耗）。
- **D3** 全 PL 前端（二期）+ 早退，出系统级指标表。

## 6. 工作纪律（针对已反复踩过的坑）

1. **仿真 ≤3 min**：超时的验证一律拆成模块级短仿真，系统级留到上板。C0 代价模型承担大部分迭代。
2. **每个硬件改动必须带前后数据**（cycles / DDR 字节 / 资源 / 功耗），没有数据的改动不算完成。
3. **"我们没做错"不是证据**：所有 RT/N 级别结论都要有可复现的命令与文件路径（#12/#20/#25 的教训）。
4. **每次实验前先写下预测**，实验后对账；不符的地方优先怀疑自己的测量方法。
5. **模型结论必须区分三个口径**：训练分布准确率 / 部署几何准确率 / 上板实测准确率。绝不混用。
6. **数据/格式约定显式断言**（#25）；**跨域先证伪自己的链路**再怀疑别人。
7. 文档：决策进本文，执行与踩坑进交接文档编号章节 + `PITFALLS.md`，绝不留口头结论。
