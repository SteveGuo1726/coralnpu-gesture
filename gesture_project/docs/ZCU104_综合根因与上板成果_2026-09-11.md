## 三、差异定位（本次任务的核心）

审计全部探针脚本的**日志去向**：

| 脚本 | 日志去向 | 结果 |
|---|---|---|
| `run_ooc_probe.sh` | `tee /tmp/gf_ooc_probe.log` | ❌ FAIL |
| `run_param_probe.sh` | `tee /tmp/gf_param_probe.log` | ❌ FAIL |
| `run_synth_variants.sh` | `tee /tmp/gf_variants.log` | ❌ FAIL |
| `run_device_vs_flow.sh` | `tee /tmp/gf_devflow.log` | ❌ FAIL |
| `run_single_thread.sh` | `tee /tmp/gf_single_thread.log` | ❌ FAIL |
| `run_standalone_synth.sh` | `tee /tmp/gf_standalone_synth.log` | ❌ FAIL |
| **`run_probe_b.sh`** | **`>> /mnt/e/...`（Windows 文件）** | ✅ **PASS** |
| **`run_led_rerun2.sh`** | **`>> /mnt/e/...`（Windows 文件）** | ✅ **PASS** |

**唯一实质差异 = Vivado 的 stdout 是否经过 WSL 管道。**

### 机理

Vivado 的 design run 经 `ISEWrap.sh`（shell 包装）启动，`synth_design` 收尾时
清理自己的 scratch 目录 `.Xil/<host>/realtime/tmp`。stdout 为 WSL 管道时这次清理
**输掉竞争**，被记成硬错误：

```
Synthesis finished with 0 errors, ...
Synthesis Optimization Runtime : ...
error deleting ".../realtime/tmp": no such file or directory
589 Infos, 318 Warnings, 0 Critical Warnings and 1 Errors encountered.
synth_design failed
ERROR: [Common 17-69] Command failed: Vivado Synthesis failed
```

本该出现的 `Synthesis Optimization Complete` 被顶掉 → `.dcp` 不写出 → run 判失败。

**判定要点**：`Synthesis Optimization Complete` 是否出现，是成功/失败的分水岭；
那条 tmp 报错本身不致命（成功日志里也有，只是位置在 Complete 之后、不计数）。
**设计越大越容易踩中**，小块（LED、单叶模块）常侥幸通过，从而误导排查。

## 四、修正

`board_zcu104/run_build_gestureflow_hagrid18_dmp_zcu104_from_wsl.sh` 已改：

```bash
cd /mnt/e
cmd.exe /d /s /c "pushd E:\zcu104_vivado\gftmpl\project_local_gestureflow && \
  call E:\Xilinx\Vivado\2023.2\bin\vivado.bat -mode batch -source build_...tcl \
  -tclargs $mode >> E:\zcu104_vivado\gf_zcu104_build.out.log 2>&1"
```

必须同时满足 3 点：
1. `cd /mnt/<盘>`——否则 cmd 相对路径失败，**静默退出（rc=0、无输出）**；
2. `pushd <Windows 目录> && call vivado.bat`——必须 `call`；
3. `>> Windows 侧日志`——**绝不 `tee` 进 `/tmp`**。

文件头已写入这条禁令与验证依据，防止以后退回。

## 六、时序与资源（决定下一步能提多快）

### 时序：完全收敛，且有巨大提频余量

```
WNS = +2.751 ns    TNS = 0.000    失败端点 0 / 163337
WHS = +0.009 ns    THS = 0.000    失败端点 0
WPWS= +3.500 ns    TPWS= 0.000    失败端点 0
Clock clk_pl_0 = 100.000 MHz
All user specified timing constraints are met.
```

10 ns 周期下 WNS 还有 +2.751 ns ⇒ **理论上 ≥137 MHz 仍可收敛**。
这是"阶段 1 提频"的直接依据（100 → 137 MHz 约 +37% 频率，若 FPS 与频率线性则
42 FPS → 约 57 FPS）。

### 资源：ZU7EV 大量空闲（Routed，含 PS + 2×SmartConnect + reset + NPU）

| 项 | 用量 | 可用 | 占比 |
|---|---|---|---|
| Total LUTs | 31921 | 230400 | **13.85%** |
| FF | 50681 | 460800 | 11.0% |
| DSP Blocks | 134 | 1728 | 7.75% |
| RAMB36 | 95 | 624 | 15.2% |
| RAMB18 | 7 | — | — |
| **URAM** | **0** | **96** | **0%** |

纯 GestureFlow IP 单看只占 **LUT 7.49%**（`gf_ooc_util.rpt`）。

→ **约 90% 逻辑、92% DSP、100% URAM 空闲**。用户"后期吃满 ZCU104 资源提性能"的空间极大，
URAM 尤其适合做权重缓存（现在权重走 BRAM/分布式 RAM）。
