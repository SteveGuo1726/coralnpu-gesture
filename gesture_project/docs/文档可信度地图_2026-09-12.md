## 2. 审阅中发现的**具体矛盾**（都有证据）

### 2.1 交接文档尾部"当前有效结论"是 08-02 快照（最严重）

见 §0.2。它的内容与编号章节的冲突是**整代际**的：

| 尾部章节（冻结于 08-02）说 | 编号章节（真实主线）说 |
|---|---|
| 静态最优 = RepVGG 图像分支 + landmark MLP，**94.62%** | 18 类 HaGRID 蒸馏学生，**98.88%** |
| 纯卷积保底线 = `static_cnn_regularized_3x3`，**79.24%** | 18 类全 4×4 学生网络 |
| 算法核心是 **3×3** + landmark + 融合 | 全 **4×4** + 1×1 head + GAP/FC，无 landmark |
| 动态路线 = landmark sequence + **GRU/TCN** | 逐帧复用空间骨干 + **时序 shift/summary/fusion**（零 MAC） |
| 硬件 = **空间卷积后端 + 稠密矩阵后端**（双后端） | 单一自研 GestureFlow-NPU（DMP 16×8） |
| VME 矩阵通路未打通，`tile move` 未坐实 | 已完全转向自研 RTL，与 CoralNPU VME 无关 |
| `7Z010` 已归档 | 早已推进到 7020 → ZCU104 |

### 2.2 `gesture_project/README.md` 的模型结构图**少画了一层**（已核实）

README 写的是：
```
conv0 4×4 3→16 → pool1 → conv2a 16→32 → conv2b 32→32 → pool2
              → conv3a 32→48 → conv3b 48→48 → pool3 → head 1×1 48→64 → GAP → FC
```
**缺了 `16→16` 那一层，且 pool1 的位置因此也不对。**

**证据（第一手：权重头文件）** `innovation_npu/board_7020/software/` 下实际存在：
```
gestureflow_dmp_full_layer.h        （conv0  3→16）
gestureflow_dmp_body2_layer.h       （body2  16→16）   ← README 漏掉的就是这个
gestureflow_dmp_conv2a_layer.h      （conv2a 16→32）
gestureflow_dmp_conv2b_layer.h      （conv2b 32→32）
gestureflow_dmp_conv3a_layer.h      （conv3a 32→48）
gestureflow_dmp_conv3b_layer.h      （conv3b 48→48）
gestureflow_dmp_head1x1_layer.h     （head   48→64）
gestureflow_real_maxpool2d.h / _pool2.h / _pool3.h
gestureflow_real_gap_fc.h
```
= **6 个 4×4 + 1 个 1×1 + 3 MaxPool + GAP/FC**，与 `GestureFlow_静态动态统一硬件架构`
和 `项目完整上下文` 的写法一致，与 README 不一致。

⇒ 正确链路（以代码为准）：
```
RGB 96×96×3
 → conv0  4×4 3→16
 → body2  4×4 16→16   + pool1  → 48×48×16
 → conv2a 4×4 16→32
 → conv2b 4×4 32→32   + pool2  → 24×24×32
 → conv3a 4×4 32→48
 → conv3b 4×4 48→48   + pool3  → 12×12×48
 → head   1×1 48→64            → 12×12×64
 → GAP(64) → FC(64→18) → argmax
```

### 2.3 `innovation_npu/README.md` 停在 v0

它描述的是 `16 输出 × 4 输入`（`gf64`）与 `gestureflow_activation_bank` /
`gestureflow_axil_microkernel` 的 25 MHz 实板基线（`263` cycles / 1.557 GMAC/s）。
**这与最终形态（DMP `16 输出 × 8 输入`、8-lane、80 MHz/100 MHz 整网）不是同一个设计。**

### 2.4 索引类文档全部过时

`工程文件索引.md`、`仓库共享版_活跃代码与文件说明.md` 都把"当前活跃"指向
`static_cnn_regularized_3x3_i96_e70_hagrid6_sample`（6 类、3×3）与 landmark 路线。
按这两份索引接手，会直接走错方向。

## 3. 对上一版审计的**更正**

我上一版审计的 A 部分（自我审计）**全部成立**，不撤回。
B 部分（项目再评估）需要**两处更正与一处加强**：

### 3.1 更正一：项目历史比我说得长得多，且有过一次**有意的**路线分叉

我说"项目是自研 RTL、与 CoralNPU 无代码继承"——这句本身没错，
但我漏掉了**它经历过什么**。真实分期（全部取自编号章节）：

| 时期 | 内容 |
|---|---|
| 2026-08-02 ~ 08-09 | **RVV / CoralNPU 探索期**：官方 worktree 仿真、`CoreMiniAxi` 板上执行 RISC-V 程序、lane1 VMACC、LSU→AXI→HP0→DDR 闭环。**这一段真的是"基于 Coral NPU"在做** |
| 08-09 ~ 08-17 | **转自研**：`RvvCoreMiniAxi` 416K LUT 不适合 7020；转向自研 GestureFlow-NPU；真实 TFLite 层逐个闭环 |
| 08-17 ~ 08-25 | HP0 DDR 接续、descriptor 主线、relay bank、pool 融合 |
| 08-25 ~ 09-01 | 80 MHz 提频（频率墙=布线拥塞）、**DMP 落地**、18 类模型 |
| 09-01 ~ 09-02 | DMP 8-lane 整网集成、**41.9 FPS 稳定代** |
| 09-10 ~ 09-12 | ZCU104 移植、PetaLinux、Linux 用户态 |

**关键**：`7020帧率优化完整方案_2026-08-21.md §1.0` **明确写着**
"本项目当前的 Zynq-7020 PL **不包含 CoralNPU 完整标量前端**……
任何把当前 7020 自研模块称为'CoralNPU 标量核心'或'官方 CoralNPU RVV'**均为错误表述**"。

⇒ 所以"申请书说基于 Coral NPU 二次开发、实际是自研 RTL"**不是遗漏，是一次有记录的、
有理由的路线决策**（官方 RVV 对 7020 太大）。这比"跑偏了"要轻得多 ——
但**口径仍需与导师对齐**，因为申请书是正式文件。

### 3.2 更正二：动态手势并非"零基础"，项目已有明确规划与 RTL 积木

我说"LSTM / 动态手势完全没做"——**"没上板"是对的，但"没做"是错的**。
`GestureFlow_静态动态统一硬件架构_2026-08-31.md` 已经给出：

- 动态模型结构（`algorithms/temporal_cnn/gesture_temporal_model.py`）：
  逐帧空间骨干（与静态**同类算子**）→ 逐帧 GAP → 96 维/帧 →
  `temporal shift`（零 MAC）+ `temporal_summary`(mean/max/delta) + `temporal_fusion 1×1(288→96)` + `FC(96→14)`
- **决策：时序积累默认放 PS**（数据仅 768 字节、算量约 3 万 MAC，比空间部分小 3~4 个数量级）
- 已落地 RTL：`gestureflow_temporal_accumulator.sv`（零 MAC 片上规约引擎，挂在 GAP 之后）
- 静态与动态**唯一区别在尾部**，空间骨干完全复用

⇒ **这正好是我建议的"选项 A"**，而且比我说的更成熟（已有模型定义 + 已有 RTL）。
**但要注意**：这套方案用的是 `shift + summary + fusion`，**不是 LSTM**。
申请书写的是"LSTM 专用处理子模块" ⇒ **这里也有一个口径需要对齐**。

### 3.3 加强：`≤5 ms` 的判断不变，但依据更硬

`ZCU104_综合根因与上板成果_2026-09-11.md` §6 给出 `WNS +2.751 ns @ 100 MHz`
（10 ns 周期还剩 2.751 ns）⇒ 理论 ≥137 MHz 仍可收敛。
与我上一版给的"提频到 137 MHz"一致。**结论不变**：
去 CPU 开销（≈18 ms）+ 提频 137 MHz（≈13.4 ms）后仍 > 5 ms，
单帧串行 + 16-lane 架构下达不到。
