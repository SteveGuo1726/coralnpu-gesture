### 2.1 官方推荐的正确顺序

官方网页给出的顺序可以压缩成下面这条链：

```text
Prerequisites
-> cocotb / hello_world / behavioral or cycle simulator
-> 用 ELF 做软件验证
-> 再进入 bare-metal / SoC integration / host boot
-> 再做更真实的性能评估或板级闭环
```

这意味着：

- 当前项目先做 official replay、再做 rowhandoff CSR/readback 闭环，是正确顺序。
- 不是应该先大改 RTL、再回头补软件和启动链。

### 2.2 官方 prerequisites 关键点

官方 prerequisites 页面明确要求先在 Coral NPU 仓库中完成：

1. `git clone https://github.com/google-coral/coralnpu`
2. 安装 Bazel 与 Python
3. 跑通：
   `bazel run //tests/cocotb:core_mini_axi_sim_cocotb`
4. 构建：
   `bazel build //examples:coralnpu_v2_hello_world_add_floats`
5. 构建行为/Verilator 仿真器
6. 用 `.elf` 运行最小程序

对我们项目的含义：

- 任何新环境、新机器或新板级前准备，都应先回到这条最小链做体检。
- 如果这一条没通，不要直接往当前项目的 rowhandoff 或 current best 回放上叠复杂度。

### 2.3 官方 simulators 关键点

官方 simulator 页面把仿真器分成两类：

1. `MPACT-CoralNPU` 行为级模拟器
   - 更快
   - 适合功能等价、脚本流程、软件开发
2. Verilator/RTL cycle-accurate 模拟器
   - 更慢
   - 适合精确周期、硬件开发、调试、波形

对应项目里的正确理解：

- 我们当前的 project-side JSON 分析、模型对账、很多工作流，天然更适合先挂在行为/脚本链上。
- 一旦涉及更真实的板级参考、信号可见性、精确周期和事件对账，就应转向 cycle-accurate / cocotb / CoreAxi 可观测链。

官方还明确偏好：

- `.elf` 优先于 `.bin`

因为：

- `.elf` 带符号、带节区、带更完整的装载信息
- 更适合调试与内存装载

这和我们当前依赖 ELF / runfiles / symbol lookup 的做法完全一致。

### 2.4 官方 bare-metal 页面关键点

官方 bare-metal 页面强调：

- Coral NPU 本质上是 bare-metal RISC-V 微控制器
- 需要自己处理 ITCM / DTCM 装载、`PC_START`、`RESET_CONTROL`
- 启动依赖 ELF 装载和 bootstrap

对我们当前主线最重要的约束有两点：

1. 后续 host 读回 / 上板 bring-up 不能跳过最小 boot 顺序。
2. 所有“板级闭环”都必须建立在能正确装载 ELF、设置 `PC_START`、释放时钟门控和 reset 的前提下。

### 2.5 官方 IP evaluation 关键点

官方 evaluation guide 的重点是：

- 评估时要区分 wall-time 与 cycle
- 真正评估硬件时，要用能真实反映 memory latency 的系统
- 行为模拟器快但不 cycle-accurate
- RTL Verilator 慢但 cycle-accurate
- 更真实的评估最好走 FPGA emulation

对项目的现实含义：

- 现在继续做纯软件回放和事件闭环，并不等于绕远路，而是在给后续更真实平台评估打地基。
- 一旦进入上板或 FPGA 阶段，重点会从“还能不能再省几百 cycles”转向“读回链、观测链、计数链是否可信”。

### 2.6 官方 IP integration 关键点

官方 integration guide 明确：

- Coral NPU 作为 AXI4/TileLink 外设集成
- 可用 Bazel 生成 scalar-only 或 RVV 版本的 SystemVerilog
- 关键接口包括 `s_axi`、`m_axi`、`halted`、`fault`、`debug`
- host / SoC 侧要负责装载 ITCM、设置起始 PC、释放时钟门控、释放 reset、轮询状态

这和我们当前要沿 `CoreAxi / CoreAxiCSR` 做 rowhandoff sideband / counter / readback 的思路是高度一致的。

## 3. 本工作区的代理正确用法

## 3.1 为什么“梯子开着”但 Bazel 还会失败

当前已经确认过：

- Git 全局代理已配置
- 但 shell 环境里未必有 `HTTP_PROXY / HTTPS_PROXY / ALL_PROXY`
- Bazel 的外部依赖下载由 Bazel/Java 负责，不一定读取 Git 的 `http.proxy`

也就是说：

```text
git clone 能通
!=
bazel http_archive 一定能通
```

### 3.2 当前已确认的 Git 代理配置

当前机器上保存过的 Git 全局代理：

```text
http.proxy=http://127.0.0.1:7897
https.proxy=http://127.0.0.1:7897
```

### 3.3 当前正确做法

开梯子后，跑 Bazel 前要显式传环境变量，推荐直接用：

```bash
env HTTP_PROXY=http://127.0.0.1:7897 \
    HTTPS_PROXY=http://127.0.0.1:7897 \
    ALL_PROXY=socks5://127.0.0.1:7897 \
    bazel --output_base=/tmp/bazel-coralnpu build //examples:coralnpu_v2_hello_world_add_floats
```

如果你已经在当前 shell 里 export，也可以这样：

```bash
export HTTP_PROXY=http://127.0.0.1:7897
export HTTPS_PROXY=http://127.0.0.1:7897
export ALL_PROXY=socks5://127.0.0.1:7897
```

然后再跑 Bazel。

### 3.4 如果 Bazel 仍不走代理

可以继续尝试显式给 Java 主进程代理参数：

```bash
bazel \
  --host_jvm_args=-Dhttp.proxyHost=127.0.0.1 \
  --host_jvm_args=-Dhttp.proxyPort=7897 \
  --host_jvm_args=-Dhttps.proxyHost=127.0.0.1 \
  --host_jvm_args=-Dhttps.proxyPort=7897 \
  --output_base=/tmp/bazel-coralnpu \
  build //examples:coralnpu_v2_hello_world_add_floats
```

如果本机代理暴露的是 SOCKS 口，可以改成：

```bash
bazel \
  --host_jvm_args=-DsocksProxyHost=127.0.0.1 \
  --host_jvm_args=-DsocksProxyPort=7897 \
  --output_base=/tmp/bazel-coralnpu \
  build //examples:coralnpu_v2_hello_world_add_floats
```

### 3.5 pip 安装时的相反注意事项

在 `gesture_project/algorithms` 的虚拟环境里，如果使用国内镜像，之前的经验是：

- `pip install` 反而常常不需要挂这些代理

已有建议命令：

```bash
env -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY -u http_proxy -u https_proxy -u all_proxy \
  .venv/bin/python -m pip install -r requirements.txt
```

也就是：

- Bazel 下载依赖时，经常要显式带代理
- Python 虚拟环境装包时，经常要先取消代理

不要把这两件事搞混。

## 5. 当前与上板直接相关的正确做法

### 5.1 先保证官方 bring-up 顺序

按照官方 integration / bare-metal 文档，host 或板级前最小 bring-up 顺序应是：

1. 装载 ELF 的 loadable sections 到 ITCM / DTCM
2. 配置 `PC_START`
3. 释放时钟门控
4. 释放 reset
5. 轮询 `STATUS` 里的 `HALTED / FAULT`

### 5.2 当前 rowhandoff 板级接入应沿官方 AXI / CSR 路线

不要绕开官方路径乱做私有接口。

当前项目正确做法是：

- `CoreAxi`
- `CoreAxiCSR`
- `RowhandoffCounterBank`
- CSR readback
- host 读回 / trace 对账

### 5.3 当前 rowhandoff sideband CSR 地址口径

应使用：

```text
0x0820 ~ 0x083c
```

不要再用旧的：

```text
0x0800 ~ 0x081c
```
