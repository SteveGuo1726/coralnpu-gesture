# ZCU104 Linux 侧 NPU 与 USB 摄像头 —— 设计与实施

**日期**：2026-09-12
**前提**：裸机已验证通过（`0x600D600D`，36.96 FPS）。本文是把同一条 NPU 链路搬到 Linux 用户态、并接上 USB3 摄像头的完整设计。
**状态**：设计定稿，代码与设备树改动已就绪，等待 PetaLinux 构建产物。

> 本文中所有地址、寄存器、量化参数都注明来源；标 **[实测]** 的是从已生成的产物里读出来的，不是推断。

## 1. 为什么必须走 Linux（重申硬约束）

USB 摄像头 = **Host 模式 + UVC 类驱动**。AMD 官方文档（ZynqMP USB Standalone Driver）明确：

> **"Host mode is not supported by the standalone driver"**

裸机 `usbpsd` 只有 Device 模式。所以摄像头必须在 Linux 下工作。

**好消息：硬件前提已在设备树里验证通过** **[实测]**。从已生成的 `system.dtb` 反编译：

```dts
usb@ff9d0000 {                              /* USB0 wrapper */
    status = "okay";
    compatible = "xlnx,zynqmp-dwc3";
    phy-names = "usb3-phy";
    phys = <&psgtr 2 PHY_TYPE_USB3 0 2>;    /* PS-GTR Lane 2, ref clk 2 */
    usb@fe200000 {                          /* dwc3_0 */
        status = "okay";
        dr_mode = "host";                   /* ← Host 模式，官方板级 DTS 白送 */
        snps,usb3_lpm_capable;
        maximum-speed = "super-speed";      /* ← USB3 SuperSpeed */
    };
};
usb@ff9e0000 { status = "disabled"; };      /* USB1 不用，正确 */
```

这与板卡预设 `PSU__USB3_0__PERIPHERAL__IO = GT Lane2` + `PSU__USB0__REF_CLK_SEL = Ref Clk2` **完全一致**。
`MACHINE_NAME = zcu104-revc` 这一步的收益在此兑现——**不需要手写任何 USB 设备树补丁**。

## 2. 地址映射（全部来自实测产物，不是推断）

| 区域 | 物理地址 | 大小 | 来源 |
|---|---|---|---|
| DDR（Linux `memory@0`） | `0x0 – 0x7FF00000` | 2032 MB | `system.dtb` **[实测]** |
| **NPU 控制口（AXI-Lite）** | **`0xA0000000`** | **1 MB** | `system.dtb` + 构建脚本 **[实测]** |
| **NPU 数据口可达范围（HP0 FPD）** | **`0x0 – 0x80000000`** | 2 GB | `build_..._zcu104.tcl:301` **[实测]** |

关键事实：

- NPU 用的是 **`PSU__USE__S_AXI_GP2` → `S_AXI_HP0_FPD`**，即**非相干**端口——与 7020 的 `S_AXI_HP0` 语义相同（构建脚本注释里专门纠正过属性名：`PSU__USE__S_AXI_HP0_FPD` 这个名字**不存在**）。
- 设备树里已经有 NPU 节点（DTG 从 XSA 自动生成）：
  ```dts
  gestureflow_layer_chain_dmp_hp0_axil@a0000000 {
      compatible = "xlnx,gestureflow-layer-chain-dmp-hp0-axil-1.0";
      reg = <0x00 0xa0000000 0x00 0x100000>;
      clocks = <&zynqmp_clk 0x47>;          /* clk_pl_0 */
      /* 标签 gestureflow_0 可用，见 __symbols__ */
  };
  ```
  **没有 Linux 驱动**匹配 `xlnx,gestureflow-...`，所以这个节点目前是"挂着不生效"的。
- **当前设备树里没有 `reserved-memory` 节点** **[实测]** —— 需要我们自己加。

## 3. 用户态如何访存：决策与理由

### 3.1 三个候选

| 方案 | 优点 | 缺点 |
|---|---|---|
| **`uio_pdrv_genirq`** + `generic-uio` | Xilinx 文档推荐；mmap 天然非缓存 | 需要改 bootargs（`uio_pdrv_genirq.of_id=generic-uio`）；UIO 只映射节点的 `reg`，缓冲区要再开一个节点；**不接管 `clocks`**，PL 时钟仍需另行确保 |
| **`uio_dmem_genirq`** | 寄存器 + 动态 DMA 缓冲一个节点搞定（分配的是 DMA-coherent，天然非缓存） | DT 绑定方式与版本相关，需先核驱动源码；多一层不确定性 |
| **`/dev/mem` + `reserved-memory(no-map)`** | **零内核代码、零 bootarg 改动、两个区域同一套代码**；非缓存由内核 mmap 路径保证 | 需要 `CONFIG_DEVMEM=y`；理念上"不优雅" |

### 3.2 选择：`/dev/mem` + `reserved-memory(no-map)`

理由：**这是唯一不需要在内核/启动参数上引入新变量的方案**，也最容易在板子上一句话验证。技术依据：

- ARM64 上 `/dev/mem` 的 mmap 走 `phys_mem_access_prot()`，对**非 RAM** 物理地址返回非缓存属性 → **寄存器区和缓冲区都不经 cache**，因此**完全不需要任何 cache flush/invalidate**。
- **必须用 `no-map`**：`reserved-memory` 带 `no-map` 时该段被 `memblock_remove` 从内核内存映射里摘除，于是
  - 内核不会拿它当 System RAM 用；
  - `devmem_is_allowed()` 判它"非 RAM" → **即使 `CONFIG_STRICT_DEVMEM=y` 也允许 mmap**。
  
  反过来若不加 `no-map`（只 reserved），它仍是 RAM，`STRICT_DEVMEM` 会拦掉。
- 需要的内核选项只有 `CONFIG_DEVMEM=y`。

**这一节的依据已被实测确认**（读第一次成功构建产出的内核 `.config`）：

```
CONFIG_DEVMEM=y                      ← 已经开着，无需改动
# CONFIG_STRICT_DEVMEM is not set     ← 连 RAM 都能 map，我们两段更没问题
CONFIG_UIO_PDRV_GENIRQ=m             ← 回退方案也可用（模块）
```

因此**不需要改动内核配置**。特意**不**往 fragment 里追加 `CONFIG_DEVMEM=y`：功能上是 no-op，但会改变 fragment 的散列、触发一次完整的 25 分钟内核重编，白等。**这个判断记录在 `plnx/PITFALLS.md`**（而不写进 `kernel_uvc.cfg` 的注释，因为注释同样会改散列）。

**回退方案**：若 `/dev/mem` 实测被拦，改走 UIO——本文 §6 的缓冲区地址与寄存器偏移都不用改，只换 mmap 的 fd 与地址来源（`/sys/class/uio/uioN/maps/mapN/addr`）。

### 3.3 布局决定

```
reserved-memory @ 0x70000000  大小 16 MB   (0x70000000 - 0x70FFFFFF)
  ├─ 0x70000000 + 0x00000  weight blob      (~256 KB，各层权重/偏置/重量化参数顺序摆放)
  ├─ 0x70000000 + 0x40000  input RGB        27648 B (96*96*3)
  ├─ 0x70000000 + 0x50000  activation_1     147456 B (96*96*16)
  ├─ ...                   中间张量池
  └─ 0x70000000 + 0x100000 输出 / 调试区
```

选 `0x70000000` 的理由：**远离内核常用的高端保留区**（DDR 顶端 `0x7FF00000` 之上是 TZ 保留），且距 2 GB 边界留 240 MB 余量。
16 MB 对当前网络（激活总量 ~400 KB）非常宽松，是为了**后续双缓冲流水线**预留——P5 想让摄像头抓帧与 NPU 计算重叠，需要 A/B 两组缓冲。

## 4. NPU 寄存器协议（用户态必须复刻的完整序列）

来源：`board_7020/software/gestureflow_hagrid18_dmp_main.c`（已在 7020 与 ZCU104 两板验证）。

### 4.1 关键寄存器

| 偏移 | 名字 | 作用 |
|---|---|---|
| `0x000` | `GF_MAGIC` | 期望 `0x47464E50`（"GFNP"） |
| `0x004` | `GF_VERSION` | 期望 `0x00050001` |
| `0x008` | `GF_CONTROL` | **写 1 = 复位/中止；写 2 = 启动本层** |
| `0x00C` | `GF_STATUS` | bit2 `FAULT`、bit6 `LAYER_FAULT` |
| `0x034` | `GF_CYCLES` | 本层 PL 周期数 |
| `0x040` | `GF_OUTPUT_FNV1A` | 逐层输出校验 |
| `0x044/48/4C` | `GF_DMA_SOURCE/BYTES/PIXELS` | 输入侧 |
| `0x050` | `GF_DMA_STATUS` | bit0 BUSY、bit1 DONE、bit2 FAULT；`>>3` = 已读字节 |
| `0x054/58/5C` | `GF_STORE_DESTINATION/BYTES/CONTROL` | 输出侧 |
| `0x060` | `GF_STORE_STATUS` | 同上语义 |
| `0x064` | `GF_LAYER_MODE` | 0/1/2/3 = 卷积+池化档位，4 = GAP/FC，5 = 1×1 head |
| `0x068/6C` | `GF_JOB_WIDTH/HEIGHT` | |
| `0x074/78` | `GF_STORE_STRIDE/VALID_BYTES` | |
| `0x080…0x9C` | `GF_POST_*` | GAP/FC 专用：mult/shift/qcfg/FNV/class/cycles/progress |
| `0x0C0…0x0FC` | `GF_WEIGHT_*` | 权重 DMA（`SOURCE/BYTES/CFG/CONTROL/STATUS`）与 bank 选择 |
| `0x150` | `GF_PARAM_BANK_SELECT` | |
| `0x15C` | `GF_WEIGHT_READ_BANK_SELECT` | |

### 4.2 单层启动序列（`launch_layer` / `run_layer`）

```c
reg[LAYER_MODE]      = mode;
reg[DMA_SOURCE]      = phys_in;
reg[DMA_BYTES]       = in_bytes;
reg[DMA_PIXELS]      = width * height;
reg[JOB_WIDTH]       = width;
reg[JOB_HEIGHT]      = height;
reg[STORE_DESTINATION]= phys_out;
reg[STORE_BYTES]     = out_bytes;
reg[STORE_STRIDE]    = stride;
reg[STORE_VALID_BYTES]= valid_bytes;
reg[STORE_CONTROL]   = store_control;
reg[CONTROL]         = 2;            /* 启动 */
/* 轮询 GF_STATUS 的 DONE，然后读 GF_CYCLES */
```

**注意**：轮询要用 `DMA_STATUS` 的 **DONE 位**而不是 `BUSY==0`——源码注释明确写了这是为了避开启动瞬间 `busy` 还没拉起的竞态。

### 4.3 整网 21 个 tile 的调度

| 阶段 | mode | tile 数 | 通道变化 | 输入 → 输出 | 尺寸 |
|---|---|---|---|---|---|
| conv0 | 0 | 1 | 3→16 | `gf_rgb` → `gf_activation_1` | 96×96 |
| conv1 (body2, fused pool1) | 1 | 1 | 16→16 | `gf_activation_1` → `gf_pool1` | 96×96 |
| conv2a | 1 | 2 | 16→32 | `gf_pool1` → `gf_conv2` | 48×48 |
| conv2b (fused pool2) | 2 | 2 | 32→32 | `gf_conv2` → `gf_pool2` | 48×48 |
| conv3a | 2 | 3 | 32→48 | `gf_pool2` → `gf_conv4` | 24×24 |
| conv3b (fused pool3) | 3 | 3 | 48→48 | `gf_conv4` → `gf_pool3` | 24×24 |
| head 1×1 | 5 | 4 | 48→64 | `gf_pool3` → `gf_head1x1` | 12×12 |
| GAP(64)+FC(18) | 4 | 1 | 64→18 | `gf_head1x1` → class | — |

每个 tile 前有 `GF_CONTROL=1` + 选 bank + 通过 `GF_WEIGHT_DMA_*` 预载权重 + 配置参数（`multiplier` / `right_shift` / `folded_bias`）。这些都在 `exec_conv_tile()` 里，**逻辑原样搬运即可**。

`preload_conv_tile()` 的权重偏移公式（DMP 是 pair-major）：
```c
first_pair = first_oc >> 1;
pairs      = tile_lanes >> 1;
word_off   = first_pair * 16 * groups * 6;
words      = pairs * 16 * groups * 6;
```

### 4.4 逐层校验

每层跑完读 `GF_OUTPUT_FNV1A`，与头文件里的 `GF_*_OUTPUT_FNV1A` 比对。**这是移植正确性的判据**——用户态第一版必须把每个 FNV 打出来，任何一个不匹配就说明搬运出错（而不是"最终 class 对就行"）。

## 5. 输入预处理（源码级确认，不是猜的）

| 环节 | 结论 | 出处 |
|---|---|---|
| 图像处理 | `Image.open(p).convert("RGB").resize((96,96), Image.BILINEAR)` | `algorithms/static_cnn/train_static_cnn.py:1041` |
| 模型量化 | `q_input = (camera_rgb.astype(np.int16) - 128).astype(np.int8)` | `tools/export_real_conv4x4_full_layer.py:209` |
| 零点 | `GF_FULL_INPUT_ZERO_POINT = -128` | `gestureflow_dmp_full_layer.h:13` |
| 布局 | **HWC 交错**（每像素 3 通道连续），96×96×3 = 27648 B | `gf_full_camera_rgb[27648]` **[实测]** |

### ⚠️ 关键：−128 由 PL 做，驱动**只写原始 uint8**

**不要**在软件里做 `pixel - 128`。RTL 的 RGB 载入器自己完成了这次重定心：

```verilog
// rtl/gestureflow_hp0_rgb_loader.sv:5, 58-60
// pixels. RGB is recentered to q=u-128 before it reaches the convolution.
assign pixel_rgb[0] = {~byte_fifo[7],   byte_fifo[6:0]};   // 取反 MSB = XOR 0x80 = u-128
assign pixel_rgb[1] = {~byte_fifo[15],  byte_fifo[14:8]};
assign pixel_rgb[2] = {~byte_fifo[23],  byte_fifo[22:16]};
```

取反 MSB 等价于 `u XOR 0x80`，按 int8 解释即 `u − 128`（例：37 → 165 → 视为 int8 得 −91 = 37−128）。

裸机驱动的做法与此一致：它把 `gf_full_camera_rgb`（**原始 uint8**）逐字节拷进 `gf_rgb`，由 PL 转换。

**所以预处理链只有三步**：抓帧 → 转 RGB → 面积平均缩放到 96×96 → **原样写入输入缓冲**。

另一个印证的细节：RTL 的 `QCFG` 写入值是 `0x00038080`，拆开是
`input_zero_point = 0x80 (= −128)` / `output_zero_point = 0x80 (= −128)` / `requant_enable = 1` / `requant_relu_enable = 1`
（`rtl/gestureflow_body2_dmp_hp0_axil.sv:134`）。其中 `input_zero_point` 在卷积窗口里当**补零值（padding_value）**用，不是用来转换输入像素的。

### 两个实施注意点：

1. **PIL 的 BILINEAR 在缩小场景下是抗锯齿的**（滤波器 support 按缩放比例放大，等效于三角窗面积平均），不是朴素 2 抽头双线性。用**面积平均（box）**实现更接近 PIL，也更稳。差异对分类精度影响很小，但不能用最近邻。
2. 摄像头一般给 **YUYV 或 MJPEG**：
   - MJPEG 需要 JPEG 解码（可用 `libjpeg`）；
   - YUYV 需要 YUV422→RGB 转换（公式写进代码注释）。
   - 建议**优先请求 MJPEG**（带宽小、帧率高），失败再退 YUYV。

## 6. 缓存一致性：不需要任何 cache 操作

这是本设计最省事的一点，值得单独说明：

- HP0 是**非相干**端口 ⇒ 如果缓冲区是 cacheable，ARM 写完后必须 flush、NPU 写完后 ARM 读前必须 invalidate。
- 而本方案里缓冲区经 `/dev/mem` 映射为**非缓存**，ARM 的每次读写直达 DDR ⇒ **两侧都不需要任何 cache 维护**。
- 代价：ARM 访问走 DDR 而非 cache，慢。但 ARM 侧的流量只有：写 27 KB 输入 + 读 18 类结果 + 启动时灌一次权重（~256 KB）。**中间张量全部由 PL 读写，ARM 完全不碰**。所以这个代价可以忽略。
- 顺带解决一个疑点：裸机版把缓冲区设成 `DEVICE_MEMORY`（强序）后整帧有 **10.04 ms CPU 开销**（占 37%）。用户态这里用普通非缓存（non-cacheable normal）而非强序设备内存，且**逐像素拷贝改成 `memcpy`**，预计这部分开销会显著下降。**P4 第一版必须测出新的 CPU 侧耗时并与 10.04 ms 对比**——这是硬门禁要求的"分离报告 PL 与 PS 开销"。

## 7. 设备树改动

追加到 `project-spec/meta-user/recipes-bsp/device-tree/files/system-user.dtsi`（文件见同目录 `system-user.dtsi`）：

```dts
/ {
    reserved-memory {
        #address-cells = <2>;
        #size-cells = <2>;
        ranges;
        npu_buffers: npu-buffers@70000000 {
            reg = <0x0 0x70000000 0x0 0x1000000>;   /* 16 MB */
            no-map;                                  /* 关键：见 §3.2 */
        };
    };
};

/* 让 PL 时钟不被内核"清理未使用时钟"时关掉 */
&{/chosen} {
    bootargs = "… clk_ignore_unused …";   /* 追加，不是覆盖 */
};
```

`clk_ignore_unused` 的理由：NPU 节点**没有任何驱动认领**，内核 `clk_disable_unused()` 可能把 `clk_pl_0` 关掉，导致 PL 逻辑断电。这个 bootarg 阻止该行为。

> bootargs 的追加方式需要按 PetaLinux 的实际生成结果确认（`&chosen { bootargs = "..."; }` 是覆盖语义，要拼上原值）。**应用后必须反编译 `system.dtb` 校验 `bootargs` 与 `reserved-memory` 都在**——这是 boot 之前的最后一道检查。

## 8. 内核配置：无需改动（已实测）

第一次成功构建产出的 `.config` 里，本阶段需要的一切都已经就位：

```
CONFIG_DEVMEM=y                          userspace 访问 PL
# CONFIG_STRICT_DEVMEM is not set
CONFIG_UIO_PDRV_GENIRQ=m                 回退方案
CONFIG_USB_VIDEO_CLASS=y                 UVC 摄像头
CONFIG_MEDIA_USB_SUPPORT=y
CONFIG_MEDIA_SUPPORT=y
CONFIG_VIDEO_V4L2=y
CONFIG_USB_XHCI_HCD=y
CONFIG_USB_DWC3=y
CONFIG_USB_DWC3_DUAL_ROLE=y              ← 不是 HOST-only（见下）
CONFIG_PHY_XILINX_ZYNQMP=y
```

**所以 `kernel_uvc.cfg` 不需要再动。** 追加 `CONFIG_DEVMEM=y` 虽然无害，但会改变 fragment 散列并触发一次完整的 25 分钟内核重编，属于纯浪费；这个判断写进了 fragment 的注释。

### 8.1 DWC3 必须留在 DUAL_ROLE（踩过的坑）

这是本轮构建唯一一次真正的失败，也是**我自己写错配置**造成的：

```
do_compile 失败:
  drivers/usb/dwc3/core.o: in function `dwc3_remove':
  core.c:(.text+0x580): undefined reference to `dwc3_gadget_exit_hibernation'
```

原因链：

1. 我最初在 fragment 里写了 `CONFIG_USB_DWC3_HOST=y` 并把 `DUAL_ROLE`/`GADGET` 关掉。
2. Xilinx 内核（6.1.30）的 `core.c` **无条件**调用 gadget 专有函数：
   `core.c:2104`（`dwc3_remove`）与 `core.c:2399`（`dwc3_suspend`），两处都在 `#ifdef CONFIG_PM_SLEEP` 内，**没有** gadget 守卫。
3. 该函数定义在 **gadget 专有文件** `drivers/usb/dwc3/gadget_hibernation.c:399` → host-only 时该文件不参与编译 → 符号未定义 → vmlinux 链接失败。
4. `drivers/usb/dwc3/Kconfig` 里 `USB_DWC3_HOST` 的 help 原文就警告 *"the gadget feature will be regressed"*。

**正确做法**：保持 defconfig 默认的 **DUAL_ROLE**，host 行为由设备树给。而设备树**确实**给了：

```dts
/* zcu104-revc.dtsi:458 —— 官方板级 DTSI，随 MACHINE_NAME=zcu104-revc 自动引入 */
&dwc3_0 {
    dr_mode = "host";
    snps,usb3_lpm_capable;
    maximum-speed = "super-speed";
};
```

这一条同时印证了 §1 的结论：**USB3 Host 不是我们补出来的，是官方板级 DTSI 白送的。**

| `yocto/gf-npu/gf-npu_1.0.bb` | Yocto recipe：把两个二进制直接打进 rootfs，板上无需 SDK |
| `plnx/04_make_sd.sh` | 写 SD 卡（分区 + 写 rootfs + `resize2fs` + 写后校验） |

### 9.1 为什么用 recipe 而不是 SDK

两条路都留了，但**recipe 是主路径**：它让 `gf_npu_probe` / `gf_camera` 直接出现在 rootfs 的 `/usr/bin/`，板子启动即可运行，不必手工拷贝。recipe 里把 `board_7020/software/` 的 18 个权重头文件原样拷入 `files/`，保证量化模型只有**一个真源**。

Makefile 则留给需要快速迭代的场合（装一次 SDK，之后秒级编译）。

### 10.1 关于逐层校验的强度（诚实说明）

裸机驱动只在三处做 FNV 比对：conv0（`GF_FULL_OUTPUT_FNV1A`）、conv1/pool1（`GF_BODY2_OUTPUT_FNV1A`）、以及 GAP/FC 的 `fc_fnv`/`class`；中间 6 个阶段只检查 DMA 写入字节数。

用户态版本**保持同样的判据**（不擅自加严，以免引入预期值猜错的假故障），但**额外用软件算并打印** conv0/pool1/conv2/pool2/conv4/pool3/head1x1 的 FNV1A 基线值。这样以后一旦有改动，可以用这些基线做二进制对比——这是裸机版没留下的信息。

## 11. 未决问题（诚实列出，不假装已经确定）

1. **`clk_pl_0` 在 Linux 下是否真的会被关** —— `clk_ignore_unused` 是防御性措施。若 V1 阶段发现 PL 无响应（读 `GF_MAGIC` 不是 `0x47446E50`），要优先怀疑时钟。
2. **PIL BILINEAR 的精确一致性** —— 我们用面积平均近似。若实测精度下降明显，再改为逐点复刻 PIL 的三角滤波器。
3. **摄像头在 USB3 还是 USB2 枚举** —— 若链路协商失败退到 USB2，MJPEG 640×480 仍够 30 FPS，但要记录实测。
4. **`/dev/mem` 是否被 `CONFIG_IO_STRICT_DEVMEM` 之类额外拦截** —— 文档上不应拦（非 RAM），但**以板子实测为准**；回退方案见 §3.2。
5. **权重总量** —— 尚未统计全部层的确切字节数。缓冲区按 16 MB 预留，远大于估计值，风险低；但摆布局时要先算出真实总量再定偏移。
