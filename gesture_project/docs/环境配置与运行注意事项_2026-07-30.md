## 3. 代理与网络规则

如果要访问 GitHub、拉官方依赖或跑 Bazel 外部下载，当前历史上验证过的代理口径是：

```bash
export HTTP_PROXY=http://127.0.0.1:7897
export HTTPS_PROXY=http://127.0.0.1:7897
export ALL_PROXY=socks5://127.0.0.1:7897
```

注意：

- `git` 的全局代理设置，不能保证 `Bazel / Java` 自动继承。
- 跑需要联网的 `Bazel` 之前，优先显式导出上面的环境变量。
- `pip install` 在某些情况下反而可能需要先取消代理再装。

补充一条本轮实测结论：

- 现在 WSL 里直接访问 `pypi.org` 是通的。
- 之前 `bazel run` 失败的原因，是误把一个已经不可用的本地代理带进了 Bazel，导致 Python 依赖 `pillow==11.0.0` 拉取失败。
- 所以后续如果不是明确知道本地代理可用，就不要默认给 Bazel 塞旧代理。
- 先用直连确认网络，再决定要不要开代理，是更稳的做法。

## 4. Bazel 规则

### 4.1 当前统一 output_base

后续如果需要重新启用 Bazel 相关流程，统一使用：

```text
/tmp/bazel-coralnpu-gesture-main
```

建议显式导出：

```bash
export CORALNPU_BAZEL_OUTPUT_BASE=/tmp/bazel-coralnpu-gesture-main
```

### 4.2 为什么不能再乱开 output_base

因为 `output_base` 不是小标签，而是一整套缓存树。

如果继续为不同试验随手创建很多：

- external 依赖
- toolchain
- execroot
- action cache

会被重复展开，最终把 `/tmp` 和磁盘占满。

### 4.3 正确做法

- 实验名称写到报告名和文档名里。
- 不把实验标签塞进 `output_base`。
- 只有共享缓存明确损坏时，才临时换目录。

## 6. Windows / WSL 混合开发注意事项

### 6.1 EDA 工具路径规则

如果未来再次使用 Windows 侧的 `Vivado` 等 EDA 工具：

- 不要从 `UNC` 路径，也就是 `\\\\wsl.localhost\\...` 直接开工程。
- 应先把工程放到 Windows 本地磁盘路径下再运行。

原因：

- `Vivado` 对 `UNC` 路径兼容性差
- 会反复出现路径、锁文件、脚本调用和工程保存问题

### 6.2 WSL 更适合做什么

优先放在 WSL 里做：

- Python 训练
- 量化
- JSON / Markdown 报告生成
- 源码阅读与脚本分析
- Git 管理

### 6.3 Windows 更适合做什么

优先放在 Windows 本地路径下做：

- 需要 GUI 的 EDA 工具
- 板卡烧录工具
- 厂商 SDK 与驱动相关流程
