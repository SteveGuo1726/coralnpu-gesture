# 项目计划

## 基本定位

本项目以 Google Coral NPU 开源仓库为基础，探索面向嵌入式手势识别的
RISC-V NPU 软硬件协同优化。PDF 申请书中的内容作为方向参考，不直接视为
已经验证的技术结论。后续工作需要以 Coral NPU 实际源码、仿真数据和模型
profiling 结果为准。

当前更稳妥的切入点不是马上改 RTL，而是先建立可重复的基线：

- 上游仓库能否稳定构建。
- Conv2D、DepthwiseConv、TFLM 模型在 NPUSim/cocotb 中的周期数是多少。
- 手势识别模型里是否确实以 3x3 卷积为主。
- LSTM/GRU 是否真的适合在这个 NPU 上做硬件扩展，还是先用 RVV 软件核更合理。
- 算法选择必须经过“资料调研 -> 静态 MAC/算子估算 -> NPUSim 周期 -> 真实训练/量化”
  的比对闭环，不能只因为 PDF、官方示例或已有实验偏好而预设答案。

## 第二阶段：手势模型和算子 profiling

目标：先证明手势模型的算子瓶颈是什么，再决定优化方向。

任务：

- 建立候选模型池，包括自定义 3x3 CNN、MobileNetV1/V2、EfficientNet-Lite、
  ShuffleNet/SqueezeNet、MediaPipe/关键点 + TCN/MLP 等路线。
- 先用静态 shape/MAC 工具比较候选模型的 Conv2D、DepthwiseConv、1x1 Conv、
  FullyConnected 等算子构成。
- 至少选择一个标准 3x3 CNN 和一个 MobileNet 风格模型进入真实训练/量化对比。
- 使用 INT8 量化，确保能在 TFLM 或类似路径中部署。
- 统计 Conv2D、DepthwiseConv、FullyConnected、激活函数、数据搬运的耗时占比。
- 如果动态手势需要时序建模，先做一个小 LSTM/GRU microbenchmark，而不是直接
  做复杂模型。

阶段产物：

- 模型结构说明。
- INT8 量化模型。
- 算子级 profiling 表格。
- 与 Coral NPU 当前支持路径的映射关系。
- 候选算法对比报告，记录为什么保留或淘汰某条路线。

## 第三阶段：3x3 卷积优化

PDF 里强调 3x3 卷积，这是合理的方向，但需要用真实模型验证占比。

当前观察：

- 上游 `conv.cc` 已有较多 4x4 Conv2D 优化路径。
- 3x3 Conv2D 是否会走 reference fallback，需要通过构建和测试进一步确认。
- 已保存一个初始 3x3 Conv2D 实验补丁：
  `gesture_project/patches/0001-experimental-3x3-conv2d-baseline.patch`。

建议流程：

1. 先跑原始上游 Conv2D 基线。
2. 应用 3x3 实验补丁。
3. 对比 `run_ref` 和 `run_opt` 的正确性与周期数。
4. 再考虑更系统的 3x3 weight repack、padding buffer、输出通道向量化。
5. 最后才考虑是否需要 RTL 层的 MAC/数据重组改动。

应用实验补丁：

```bash
cd /home/steveguo/coralnpu-gesture/coralnpu

```

撤销实验补丁：

## 第四阶段：LSTM/时序路径

PDF 中提出 LSTM 专用模块，但这一步风险较高。更稳妥的路径：

- 先用 C/RVV 写 LSTM 单元 microbenchmark。
- 记录矩阵乘、门控激活、状态更新各自耗时。
- 判断瓶颈在 MAC、访存、激活函数还是调度。
- 如果确实有硬件价值，再设计接口。可能的方案包括：
  自定义指令、RVV 后端扩展、或者 memory-mapped 协处理模块。

不建议一开始就直接写独立 LSTM RTL，因为很容易做成无法接入工具链和测试链路的
孤立 IP。

## 第五阶段：RTL/FPGA

只有在软件基线和 microbenchmark 足够清楚后再动硬件。

候选工作：

- 分析 RVV MAC 后端吞吐是否限制 3x3 卷积。
- 分析 load/store 和寄存器压力是否比 MAC 更关键。
- 如果瓶颈确实在 MAC 或数据重组，再修改
  `hdl/verilog/rvv/design/rvv_backend_*`。
- 每个 RTL 改动都要绑定一个软件 benchmark 和 cocotb/NPUSim 测试。

## 当前阶段结论

截至 2026-06-01，项目已经从“环境准备”推进到“3x3 卷积软件基线验证”。

已验证事实：

- Coral NPU 上游仓库可以构建和运行 NPUSim。
- 依赖下载失败的主要原因是 Bazel/Java 没有自动继承 Git 代理配置。
- 上游 Conv2D 已有明显优化，4x4 测试项相对 reference 有 3x 到 10x 左右加速。
- 初始 3x3 Conv2D 补丁可以正确运行，新增 3x3 测试项相对 reference 有 5x 到
  9x 左右加速。
- 3x3 输出通道向量化对多输出通道层收益明显：`3x3_16x16` 的 optimized cycles
  从 44,540 降到 20,277；新增 `3x3_16x32` 为 37,437 cycles。
- 小输出通道层不适合强制走输出通道向量化，`output_depth < 8` 时应回退到
  reduction 路径。
- 算法侧已建立 `gesture_static_cnn_v1`，其 Conv2D MAC 约 3,991 万，其中 3x3
  Conv2D 约占 99.0%。这说明静态 CNN baseline 能有效验证 3x3 优化。
- 已用 NPUSim 回放 `gesture_static_cnn_v1` 的真实 3x3 Conv2D 层。放宽
  dispatch 后，六个真实 3x3 层全部命中 OC-vectorized 并通过正确性校验，reference
  cycles 为 491,614,428，optimized cycles 为 22,960,503，整体加速 21.41x。
  因此当前不应优先做 RTL MAC 扩展，下一轮更适合做 3x3 weight repack 和训练/量化闭环。
- DepthwiseConv 当前优化路径也很强，NPUSim 上相对 reference 约 20x 到 35x。
  因此 MobileNetV1/V2 等 depthwise separable CNN 必须纳入候选，不能只围绕标准
  3x3 CNN 做算法选择。
- 静态候选估算显示，`mobilenet_v1_0.25_64` 约 208 万 MAC，显著小于当前
  `gesture_static_cnn_v1_64` 的约 3991 万 MAC；但 MobileNet 风格模型高度依赖
  1x1 Conv 和 DepthwiseConv，必须继续用 NPUSim 和真实训练比较。
