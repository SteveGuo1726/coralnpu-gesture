### 1.4 一条**必须纠正**的记录（关于"上次重编"）

我此前在日志里写过"10:15 跑了 `do_cleanall` + 全量重编，镜像在 ~10:17 重新生成"。
**这句话是错的**，实测：

- `06_install_app.sh` 确实在 **10:15:55** 跑过，`BUILD_RC=0`，**10:17:39 结束**；
- 但构建摘要写的是 **`Attempted 4854 tasks of which 4835 didn't need to be rerun`**
  —— **只重跑了约 19 个任务**；
- 而且 `images/linux/` 里的 `BOOT.BIN` / `rootfs.ext4` 时间戳**仍是 01:18**，
  **并没有被重新生成**。

**为什么这不是故障**：源码自 01:15 之后没有再改过，重编出来的是**逐字节相同**的二进制，
所以 bitbake 正确地跳过了下游的打包与镜像任务。**01:18 那份镜像就是对的**，
`05_verify_image.sh` 的 `PASS` 是它的证明（第 1.2 节）。

**要记住的教训**：`BUILD_RC=0` **不等于**"镜像被重新生成了"。
判据永远是 `05_verify_image.sh` 的 `RESULT: PASS`，不是构建日志的返回码 ——
这正是 `IDENTITY.md` D6 那条。**上板前不需要再重编**，现在这份就是正确的。

### 1.6 SD 卡与 WSL 的事实核对（**2026-09-12 实测**）

**问题一：官方套装那张 16 GB 卡插上后只显示 ~120 MB，是不是坏了？**
**不是。** 实测该卡在 Windows 里是 `G:`，可移动，卷标 **`PYNQ`**，`文件系统名 : FAT`，
内容为 `BOOT.BIN`(1.7 MB) / `image.ub`(23 MB) / `boot.py` / `boot.scr` / `REVISION`。
**120 MB 就是它的 FAT32 引导分区**；剩下约 15 GB 是 **ext4 根分区，Windows 读不了，
所以不显示**。这正是 PYNQ 镜像的标准布局。

**顺带得到一条好消息**：这张卡能跑 PYNQ，说明**卡、读卡器、板子 SD 通路三者都是好的**。

**问题二：另一张 32 GB 卡是 U1 速度等级，够不够？**
**完全够，而且绰绰有余。**
- **速度**：U1 = 持续写 **≥10 MB/s**。我们的 `rootfs.ext4` 是 431 MB → 写卡约 **45 秒**。
  Linux 从 U1 卡启动、以及我们这种"启动后把模型全放进内存"的负载，对卡速毫无压力。
  （U3/A2 更快，但这里用不到。）
- **容量**：镜像占约 1 GB 引导 + 431 MB 根，剩余空间 `resize2fs` 撑满即可。32 GB 远超需求。

**建议：用那张 32 GB 的。** 16 GB 的 PYNQ 卡**留着不动** ——
既保留了一个可用的 PYNQ 环境（见下方备注），也是这套"卡/读卡器/板子"链路的对照物。

> **备注（备选环境，不在本次关键路径上）**：PYNQ 自带 Python + Jupyter，并且
> `pynq.Overlay` 可以**运行时下载 bitstream**，对快速迭代很有吸引力。
> 但它的设备树是通用板级 DTB —— **没有我们的 `npu-buffers` 预留段、没有 `clk_ignore_unused`**，
> 内核 `CONFIG_DEVMEM` 也不确定；换过去等于把已经校验过的环境变量全部重开一遍。
> **本次不换。** 如果后面发现 PetaLinux 侧有硬伤，再作为 B 计划评估。

**问题三：WSL 到底能不能写插进来的 SD 卡？**
**默认不能，而且 `wsl --mount` 这条路对读卡器是死的。**

- **默认不能**：WSL2 是轻量虚拟机，**不会自动把 USB / 块设备透传进来**。
  实测 WSL 内 `lsblk` 只有 `sda/sdb/sdc/sdd` 四块虚拟盘，**看不到 SD 卡**。
- **`wsl --mount` 不行 —— 这是微软官方文档写明的**：
  > *The `wsl --mount` command does not currently support USB/flash drives/SD card readers.*
  （`learn.microsoft.com/windows/wsl/wsl2-mount-disk`）

  实测吻合：管理员下执行 `wsl --mount \\.\PHYSICALDRIVE2 --bare` 两次都失败，
  报 **`Wsl/Service/AttachDisk/MountDisk/0x8007000f`**
  （`0x8007000f` = Win32 **ERROR_INVALID_DRIVE**，即"系统找不到指定的驱动器"）。
  把盘脱机后重试，错误变成 `.../HCS/0x8007000f`，**仍然失败**。
  社区报告一致：**配读卡器是长期未修的已知问题**，不是我们的操作错。

- **正确路径：USB 透传（usbipd）**，也是微软文档在 `--mount` 不支持时指向的方案。
  **本机条件已核实具备**：`winget` 可用（`C:\Users\SteveGuo\AppData\Local\Microsoft\WindowsApps\winget.exe`），
  且 WSL 内核 6.18.33.2 里 `vhci-hcd` / `usbip-core` / `usb-storage` / `uas` **全部存在**
  （`/lib/modules/6.18.33.2-microsoft-standard-WSL2/kernel/drivers/usb/usbip/`）。
  完整步骤见 **P1**。
- **如果 usbipd 也不顺**：备选方案 B（在 WSL 里造 `.img` + Windows 用 Rufus/Etcher 写）
  **脚本已就绪**（`07_make_sd_image.sh`），见 P1 末尾。它完全不需要卡被 WSL 看见。

### P1 · 把 SD 卡接进 WSL，然后写卡 —— 你执行（需 sudo / 需管理员）

> **⚠️ 2026-09-12 更正：本节初版写错了。** 初版直接让你 `lsblk` 找卡 —— 但
> **WSL2 默认看不到任何插进来的 SD 卡**。实测 WSL 里 `lsblk` 只有虚拟盘：
> `sda 356.9M` / `sdb 159.4M` / `sdc 3G (swap)` / `sdd 1T (/mnt/wslg/distro)`。
> **必须先把卡"挂"进来**，否则 `04_make_sd.sh /dev/sdX` 根本找不到设备。

#### P1.1 找到卡的物理盘号（普通 PowerShell）

```powershell
Get-Disk | Select-Object Number,FriendlyName,@{n='GB';e={[math]::Round($_.Size/1GB,1)}},BusType,PartitionStyle
```

认准**容量对得上**（32 GB）且 `BusType = USB` 的那个，记下 `Number`（下文写作 **N**）。

> 也可以直接看「磁盘管理」：可移动的 32 GB 盘就是它。

#### P1.2 安装 usbipd（**管理员**，一次性）

```powershell
winget install -e --id dorssel.usbipd-win --accept-package-agreements --accept-source-agreements
```
装完**新开一个管理员终端**（要让 PATH 刷新）。

> usbipd 就是微软文档在 `--mount` 不适用时给出的那条路：把 USB 设备从 Windows
> "拔"下来，直接"插"进 WSL 的内核。

#### P1.3 找到读卡器的 BUSID

```powershell
usbipd list
```
认 **`Generic MassStorageClass`**（或 `USB Mass Storage Device`）那一行，记下首列的
**BUSID**（形如 `2-13`，下文写作 `<BUSID>`）。

#### P1.4 绑定 + 透传给 WSL（**管理员**）

```powershell
usbipd bind   --busid <BUSID>          # 一次性；状态应变成 Shared
usbipd attach --wsl --busid <BUSID>    # 真正交出去
```

> ⚠️ `attach` 之后，**Windows 资源管理器里这张卡会消失** —— 这是**正常的**，
> 设备已经进 WSL 了。要让 Windows 拿回来就 `usbipd detach --busid <BUSID>`。
> ⚠️ `attach` 期间 **WSL 实例必须保持运行**（可以只开一个 `wsl` 窗口占着）。

#### P1.5 在 WSL 里确认它出现了

```bash
sudo modprobe vhci-hcd        # USB/IP 虚拟主机控制器（首次需要）
sudo modprobe usb-storage     # 大容量存储驱动
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT
```

**判据**：多出一块约 **28.9 G** 的盘，形如 `sde 28.9G disk`，且**没有挂载点**。

> **若 `lsusb` 能看到设备、但 `lsblk` 里没有盘** → 就是驱动模块没加载。
> 这正是社区报告里的经典坑，上面两条 `modprobe` 就是为它准备的。
> 本机已确认这几个模块**都存在**：`vhci-hcd.ko` / `usb-storage.ko` / `uas.ko`
> （`/lib/modules/6.18.33.2-microsoft-standard-WSL2/kernel/drivers/usb/{usbip,storage}/`）。

#### P1.6 写卡

```bash
sudo bash ~/coralnpu-gesture/gesture_project/innovation_npu/board_zcu104/plnx/04_make_sd.sh /dev/sde
```
（把 `/dev/sde` 换成 P1.5 里看到的设备名。**要是整盘名，不要带数字。**）

> **⚠️ 一个已修掉、但你要知道它长什么样的坑**（PITFALLS #11）：
> `sudo` 会把 `$HOME` 重置成 `/root`，而这些脚本原先用 `$HOME` 定位工程树，
> 于是会报 `missing /root/gf_linux_ws/.../BOOT.BIN` —— 镜像其实一直都在。
> 四个脚本（04/05/06/07）现在都会自动解析"调用 sudo 的那个用户"的家目录；
> 万一仍有偏差，显式覆盖即可：
> ```bash
> sudo GF_HOME=/home/steveguo bash <脚本> <参数>
> ```

脚本会依次：**自动跑 `05_verify_image.sh`（不 PASS 直接拒绝写卡）** → 校验 manifest 含 `gf-npu`
→ 让你把设备名**再手打一遍**确认 → 分区（p1 FAT32 1 GiB / p2 ext4 剩余）→ 写 rootfs
→ `resize2fs` 撑满 → 只读挂载复核、打印 `file` 与 **md5**。

**判据（三条都要）**
1. `usr/bin/gf_npu_probe`、`gf_camera`、`v4l2-ctl`、`lsusb` 四项全 `OK`；
2. `gf_camera` 显示 `ARM aarch64`；
3. 两个二进制的 md5 **等于** `2ed2ef05ab52e145` / `bb04ced68ea693e9`（与 `05` 的 `[6]` 段一致）。

#### P1.7 用完把设备还给 Windows

```powershell
usbipd detach --busid <BUSID>
```

> 之后卡会重新出现在 Windows 里（可能需要在磁盘管理里给它一个盘符）。

### P2 · 插卡 / 拨码 / 上电（你执行）

1. 卡片插到 **J100**
2. **SW6 [4:1] = `OFF, OFF, OFF, ON`**（SD1）
   - ⚠️ 极性 **ON = 0，OFF = 1**。出厂默认是 QSPI32（`ON,ON,OFF,ON`），**必须改**
3. 串口：板载 FT4232H 的 **channel 0**，**115200 8N1**
   - Windows：设备管理器里找哪个 `COMx` 对应 channel 0
4. 上电

**判据**：串口出现 U-Boot 与内核启动日志，最终落到登录提示符（PetaLinux 默认 `root` / 无密码，若要求密码试 `root`）。

> **失败分支 A：串口完全无输出**
> ① 复查 SW6 极性（最容易错）；② 重插卡；③ 换一根 USB 线/另一个口；
> ④ 把 SW6 拨回 QSPI32（`ON,ON,OFF,ON`）上电 —— 若这样能起，说明**板子本身没问题**，
> 是卡或镜像的问题；⑤ 若 QSPI 也不起，才是板子/供电问题。
>
> **失败分支 B：卡在 `Starting kernel ...` 之后停住**
> 多半是 `image.ub` 加载失败或 DTB 不匹配。**注意：我们已经验证过 `image.ub` 内嵌 DTB 与
> `system.dtb` 一致**（§1.3），所以这一项可以排除，把串口完整输出贴回来。

### P3 · V1：确认系统起来了、摄像头被枚举（板上）

```bash
uname -a
cat /proc/cmdline                    # 应含 clk_ignore_unused 与 root=/dev/mmcblk0p2
lsusb
ls /dev/video*
dmesg | grep -i -E "usb|xhci|uvc|dwc3" | tail -30
```

**判据**
- `lsusb` 里能看到摄像头；
- `/dev/video0` 存在。

**若不是 `super-speed`（即退到 USB2）也算通过** —— 640×480 带宽足够，
**但要如实记下来**（USB3 需要 PS-GTR Lane2 协商成功）。

> **失败分支：`lsusb` 里没有摄像头**
> ① `dmesg | tail -40` 看有没有 USB 枚举动作；② 换 USB 线（很多「USB3 线」其实是 USB2 线）；
> ③ 换板子上的另一个 USB 口；④ 换一个有源 USB Hub 排除供电不足；
> ⑤ `lsusb` 有设备但**没有** `/dev/video0` → 记录 `lsusb` 的 VID:PID，
> 那是内核 UVC 匹配问题（内核里 `CONFIG_USB_VIDEO_CLASS=y` 已开）。
>
> **这一阶段失败不影响 P5**：NPU 自检不依赖摄像头。**可以先跳过摄像头去做 P5**，
> 把摄像头问题单独解决 —— 这样能把两个变量分开。

**判据**：能列出格式（`MJPG` 和/或 `YUYV`）与分辨率。**把完整输出贴回来**——

### P5 · V3：★ NPU 自检 —— **最关键的一步**

```bash
sudo gf_npu_probe
```

**必须看到 `RESULT: PASS`**，并且逐层内容校验全 `MATCH`：

```
gf_npu: PL id ok (MAGIC 0x47464E50, VERSION 0x00050001)
gf_npu: staged weights + activations, ... of 16 MiB
=== reference-image pass ===
class = 1 (...), expected 1
  --- golden content checks (bit-exact memcmp) ---
    conv0  MATCH / pool1 MATCH / conv2 MATCH / pool2 MATCH / conv4 MATCH / pool3 MATCH
    6/6 matched
  --- hardware FNV registers ---
RESULT: PASS
```

**这一条是整条链路的门禁。在它 PASS 之前，`gf_camera` 报的任何类别都不算数。**

> **失败分支 1：`open /dev/mem failed`**
> → 忘了 `sudo`。仍失败则 `ls -la /dev/mem`、`dmesg | grep -i devmem`。
> 设备树已确认 `no-map` 预留段存在，所以理论上 `STRICT_DEVMEM` 拦不住。
>
> **失败分支 2：`GF_MAGIC` 是 `0x00000000` 或 `0xFFFFFFFF`**
> → **PL 没有配置**（bitstream 没加载）或 **PL 时钟被关**。
> ① `cat /proc/cmdline` 确认 `clk_ignore_unused`（设备树已确认有，但看板子实际用的）；
> ② `dmesg | grep -i -E "fpga|zynqmp-fpga"` 看 FPGA manager 是否加载了 bitstream；
> ③ `cat /sys/class/fpga_manager/fpga0/state`（应为 `operating`）。
> **这是本项目最可能出问题的点**，因为 PL 无驱动、时钟是"防御性"保留的。
>
> **失败分支 3：`GF_VERSION` 不匹配**
> → bitstream 与驱动不是同一版。确认烧的是新镜像（`BOOT.BIN` 里带 `system.bit`，
> `system.bit` 时间戳 09-11 23:35）。
>
> **失败分支 4：某一层 `*** MISMATCH ***`**
> → **这是真正的信号**。记下程序打印的**首个差异字节偏移 + 实际值 + golden 值 + 两侧 FNV**，
> 连同层名和**完整输出**贴回来。**不要改任何东西再跑一遍** —— 那会掩盖问题。

---

### P6 · V4：性能与分离口径（板上）

```bash
sudo gf_npu_probe --bench 200
```

**判据**：报出 **PL 计算** 与 **CPU 侧开销** 两个数字。**必须贴回来**，与裸机对比：

| 口径 | 裸机（已知） | Linux（待测） | 意义 |
|---|---|---|---|
| PL 计算 | 17.02 ms @100 MHz | ? | RTL 未变，应接近 |
| CPU 侧开销 | 10.04 ms（占 37%） | ? | **Linux 换了普通非缓存 + `memcpy`，这里应显著下降** |

> **这是硬门禁要求的"分离报告 PL 与 PS 开销"**（`7020帧率优化 §1.4` 第 4 条）。
> 只报一个总帧率不算性能结论。
>
> **如果 CPU 侧没有下降**：说明 `/dev/mem` 拿到的不是非缓存映射，或拷贝路径没优化。
> 记下来，这是 P8 之后的第一优先级。

### P7 · V5：实时摄像头闭环（板上）

```bash
sudo gf_camera --list                      # 只列格式，先确认
sudo gf_camera -s 640x480 -n 100           # 先跑 100 帧
sudo gf_camera -s 640x480                  # 持续跑
sudo gf_camera -s 640x480 -n 50 --save-ppm /tmp/npu_in.ppm   # 存一帧 96×96 输入
```

**判据**：连续打印类别；帧率合理；`--save-ppm` 能存出 96×96 的图。

> **`--save-ppm` 那一步很重要**：它把**真正送进 NPU 的 96×96 图**存下来，
> 是唯一能验证「面积平均缩放」预处理是否正确的手段（对比原图看是否被拉伸/裁错）。
> 把 `/tmp/npu_in.ppm` 也带回来（转成 png 更好）。
>
> **失败分支：类别乱跳或全错**
> **先回去确认 P5 是 PASS**。P5 PASS 而 P7 乱 → 问题一定在预处理或颜色通道顺序，
> 用 `--save-ppm` 定位。**不要先怀疑 NPU。**

## 4. 风险登记表（按可能性排序）

> **当前最先会遇到的风险**（2026-09-12 实测修订）：
> **① `wsl --mount` 对 SD 读卡器是死的**（微软官方文档明说不支持，实测 `0x8007000f`）
> ⇒ 改用 **usbipd**，见 P1。
> **② usbipd 也不通** ⇒ 走备选方案 B（`07_make_sd_image.sh` + Rufus），见 P1 末尾。

| # | 风险 | 可能性 | 预先准备的处置 |
|---|---|---|---|
| R0 | ~~WSL 看不到 SD 卡~~ **`wsl --mount` 不支持读卡器** | **已发生** | 官方文档明确；已实测 `0x8007000f`。**改用 usbipd（P1.2–P1.5）** |
| R0b | usbipd 装上后 `lsblk` 里没有盘（模块未加载） | 中 | `sudo modprobe vhci-hcd usb-storage`；模块已确认存在 |
| R0c | usbipd 也不通 | 低 | 备选方案 B：`07_make_sd_image.sh` + Rufus/Etcher |
| R1 | **SW6 极性搞错**（ON=0） | 高 | 已写死：`OFF,OFF,OFF,ON`；无输出时第一件事查它 |
| R2 | **PL 时钟被内核关掉**（`GF_MAGIC` 读不到） | 中 | 设备树已确认 `clk_ignore_unused`；失败时查 `fpga_manager/state` |
| R3 | 摄像头需要换线/换口才枚举 | 中 | P3 失败**不阻塞 P5**，分开处理 |
| R4 | 软件忘了 `sudo` | 中 | 本文所有板上命令已带 `sudo` |
| R5 | 摄像头不支持 640×480 MJPEG | 低 | P4 先取证，按支持的组合改 `-s` |
| R6 | `/dev/mem` 被额外拦 | 低 | 设备树 `no-map` 已确认；回退方案是 UIO |
| R7 | 读卡器写卡不稳定 | 低 | P1 的 md5 复核能立刻发现 |
| R8 | 串口 COM 口选错 | 低 | channel 0；Windows 逐个试 |

**恢复手段（万一要退回）**：
- **板子不会坏**。最坏情况只是卡上的内容不对，重烧即可。
- **可随时验证板子本身是好的**：SW6 拨回 **QSPI32（`ON,ON,OFF,ON`）** 上电，
  应能起出厂镜像。**这是"板子 vs 卡"的判据**。
- 镜像产物都在 WSL（`~/gf_linux_ws/gf_linux/images/linux/`），随时可重烧。
