# 7020阶段 GestureFlow 模块级复盘与 CoralNPU 参照突破路线 2026-08-25

> 本文讨论的是项目自研 `GestureFlow-NPU` 当前 7020 主线，以及它如何借鉴 Google 官方 `coralnpu/` 的具体硬件思想继续演化。  
> `/home/steveguo/coralnpu-gesture/coralnpu` 是 Google 官方只读参考仓库，不允许修改；本文中一切可改内容都位于 `gesture_project/innovation_npu/`。

## 1. 本文解决什么问题

这份文档只解决四件事：

1. 重新用 **官方源码** 而不是旧对话结论，确认 `coralnpu/` 当前到底实现了什么。
2. 重新用 **当前 RTL** 而不是过时描述，确认 `GestureFlow-NPU` 现在到底是什么结构。
3. 对照外部公开轻量加速器实现，判断哪些结构值得借鉴，哪些不该照搬。
4. 给出一条面向 `Zynq-7020` 可落地、同时为后续更大器件保留上升空间的 **模块级硬件突破路线**。

本文不讨论“抽象前后端理念”本身，重点全部落在：

- 具体 RTL 模块；
- 具体片上数据流；
- 具体存储组织；
- 具体后续改造次序；
- 以及这些改造为什么更适合手势识别。

## 2. 先给结论

### 2.1 当前路线没有走偏，但还只到第一版可行的层次

当前 `GestureFlow-NPU` 已经不是 ARM 逐窗口控制的普通卷积外设，也不是简单把一个 HLS 卷积核挂到 AXI 上。它已经具备：

- 片上权重驻留；
- 行缓存和滑窗生成；
- INT8 乘加与 INT32 部分和驻留；
- descriptor/doorbell 雏形；
- HP0 DDR 读写；
- 板上 pooling、GAP、FC 和整网闭环。

这些都是真实板测过的，不是设想。

但它现在仍然主要是：

```text
一个围绕空间卷积展开的单主后端
+ 少量尾部后处理特化
```

这足够完成“第一版可行硬件”，还不够形成“对手势识别显著优于常见轻量加速器”的专用微架构。

### 2.2 之后不能再把 CoralNPU 简化成“3x3 卷积器”，也不能误写成“现成完整矩阵 NPU”

根据当前只读源码：

- `coralnpu/hdl/chisel/src/coralnpu/Parameters.scala`
- `coralnpu/hdl/verilog/rvv/inc/rvv_backend_define.svh`
- `coralnpu/hdl/verilog/rvv/design/RvvCore.sv`
- `coralnpu/hdl/verilog/rvv/design/Zvt/*.sv`
- `coralnpu/sw/opt/litert-micro/conv.cc`
- `coralnpu/sw/opt/litert-micro/depthwise_conv.cc`

当前最准确的结论是：

1. CoralNPU 的**真实价值**在于：
   - 轻量标量控制；
   - 向量/矩阵命令解耦；
   - 片上寄存器/累加状态驻留；
   - 统一访存和可编程执行。

2. 当前这份开源代码的**默认可见主链**仍然是：
   - `RVV`
   - `VLEN = 128`
   - `NUM_VRF = 32`
   - `NUM_MUL = 2`
   - `NUM_ALU = 2`
   - `NUM_LSU = 2`

3. `ZVT/VME` 相关 RTL **确实存在**，但 `RvvCore.sv` 里当前仍明确写着：
   - `Tie-off VME LSU interfaces`
   - `TODO: Support these`

这意味着：

- 不能再把项目未来押回“纯 3x3 思维”；
- 也不能把当前公开仓库当成“已经完整打通、直接能拿来上板的矩阵引擎成品”。

### 2.3 对当前项目，最合理的突破方向不是“再堆一个更大卷积核”，而是做五个具体结构突破

真正值得继续推进的突破点应该是：

1. **统一 `3x3 / 4x4 / 1x1` 的空间/点积双模 MAC 集群**
2. **权重生命周期管理器**
3. **层间 relay bank（接力 bank）**
4. **tile-valid / ROI 前景门控**
5. **归约/分类后端独立化**

这五项都能直接落到当前 RTL 模块上，也都比“再做一个普通 HLS CNN 加速器”更有研究价值。

### 2.4 7020 上必须先固定的硬约束

当前已通过整网 bitstream 的 routed 结果已经给出真实资源边界：

- `LUT = 38,206`
- `FF = 51,679`
- `RAMB36 = 107`
- `DSP48E1 = 180`
- `WNS = +0.165 ns @ 25 MHz`

这意味着当前 7020 主线只剩下大约：

- `40` 个 DSP 余量；
- `33` 个 `RAMB36` 余量；
- 时序裕量极小，不能再接受长组合控制链和大范围宽总线扇出。

因此后续所有结构设计必须同时满足：

1. **不复制第二套完整 MAC 阵列**
2. **不引入新的大规模全局交叉开关**
3. **不把 BRAM 放在数据路径中间再做大范围跨区回绕**
4. **不把动态除法、动态取模、宽地址重排放进主时序路径**
5. **控制、搬运、计算必须层次化分区并在边界寄存**

如果违反这五条，7020 上大概率不是资源爆，就是 route 后时序掉穿。

### 2.5 截至 2026-08-25 晚间的最新执行状态

本路线文档不是空规划。当前已经有一项模块级推进完成并通过真实回归：

- `gesture_project/innovation_npu/rtl/gestureflow_conv4x4_cin_same_stream.sv`

这两个模块已经完成第一步 `3x3/4x4` 共形化：

- 物理窗口仍保持 `16 tap`
- `3x3` 只 issue `9 tap`
- `4x4` 继续 issue `16 tap`
- 不复制新的 MAC 阵列

并且已经实际通过三条回归：

- `gestureflow_conv3x3_cin_same_stream`
- `gestureflow_conv4x4_cin_full_layer`
- `gestureflow_layer_chain_hp0_postprocess`

因此接下来的路线不是再讨论“要不要做统一空间引擎”，而是继续把这个已经落地的基础往 `hybrid344` 和后续 `1x1` 双模 MAC 推进。

补充当晚第二项已经落地的推进：

- `gesture_project/innovation_npu/rtl/gestureflow_conv1x1_cin_stream.sv`

这条新路径已经通过：

- `gestureflow_conv1x1_cin_stream`
- `gestureflow_head1x1_tile_real`

其中第二条不是 toy case，而是当前静态主线真实 `head_1x1` 的前 `16` 个输出通道回归。  
因此“空间卷积 / 点积双模”不再只是后续设想，而是已经有了真实 `1x1` 点积原型。

补充当晚第三项已经落地的推进：

- `gesture_project/innovation_npu/rtl/gestureflow_conv4x4_cin_same_stream.sv`
- `gesture_project/innovation_npu/rtl/gestureflow_layer_chain_hp0_axil.sv`

这两处已经把独立 `1x1` 原型并回共享主后端：

- `gestureflow_conv4x4_cin_same_stream.sv` 新增运行态 `pointwise_mode`
- `gestureflow_layer_chain_hp0_axil.sv` 新增 `layer_mode = 5`
- `mode 5` 复用原 `80-Cin` HP0 loader，不复制第二套 MAC 阵列
- 真实顶层回归 `gestureflow_layer_chain_head1x1_axil` 已通过
- 7020 板级 ARM 软件 `gestureflow_layer_chain_hp0_main.c` 已同步改成 `head_1x1 -> mode 5`，并完成交叉编译

因此当前模块级路线已经从：

```text
3x3/4x4 空间统一
+ 独立 1x1 原型
```

推进为：

```text
3x3/4x4/1x1 共享主后端
+ 顶层真实 head_1x1 模式
```

这意味着后续动态模型如果继续保留 `spatial_embedding_1x1` 和 `temporal_fusion_1x1`，优先应该复用这条共享 `pointwise` 路径，而不是再起新的点积特化核。

### 2.6 截至 2026-08-26 上午的最新推进：`body -> pool -> conv2a` 已经从“先池化再写 DDR”推进到“池化后直接片上接力”

这一步的新增内容不是又做一个普通 testbench，而是把 `2x2 maxpool` 正式搬到 `output_bank` 的输入接力侧：

- 新增 `gesture_project/innovation_npu/rtl/gestureflow_output_bank_pool_relay_loader.sv`
- 修改 `gesture_project/innovation_npu/rtl/gestureflow_layer_chain_hp0_axil.sv`
- 新增 `gesture_project/innovation_npu/tests/tb_gestureflow_layer_chain_pool_relay_conv2a_axil.sv`
- 新增 `gesture_project/innovation_npu/tests/run_gestureflow_layer_chain_pool_relay_conv2a_axil.sh`

具体结构是：

1. 上一层 `body` 输出仍先量化写入片上 `output_bank`
2. 新的 `pool relay loader` 通过 `output_bank` 两个读口同时读 `2x2` 窗口
3. 在片上完成 `16 lane INT8 maxpool`
4. 直接把 pooled tensor 作为下一层 `conv2a` 的输入流送入共享主后端

最重要的细节不是“能做 pooling”，而是：

- `output_bank` 的两个读口只在 `relay_pool_busy` 期间切给这个模块；
- `pool relay` 一结束，读口立即还给 `store` 或普通 relay；
- 因而不会把后面的写回阶段卡死。

这次已经实际跑通的回归是：

- `bash gesture_project/innovation_npu/tests/run_gestureflow_layer_chain_pool_relay_conv2a_axil.sh`
  - 输出：`GESTUREFLOW_LAYER_CHAIN_POOL_RELAY_CONV2A_AXIL_PASS body=893afa60 conv2a_tile0=db73532c pixels=2304`

这条回归不是只看输出哈希，它还额外证明：

- `conv1` 只写 bank0，不写 DDR
- `body` 从 bank0 读、写 bank1，不走 DDR
- `conv2a tile0` 的输入侧不允许出现任何 HP0 读事务
- `conv2a tile0` 写回的 `48x48x16` 输出逐点对账真实 golden

因此当前 7020 主线已经从：

```text
conv1 -> body 片上直通
```

推进到：

```text
conv1 -> body -> pool -> conv2a(tile0) 片上直通
```

这一步的价值非常直接：它第一次把“池化后的中间张量”也纳入片上复用，而不是只解决一层卷积到下一层卷积的直接搬运。

### 2.7 截至 2026-08-26 上午的第二个关键结论：`output_bank` 必须继续从“全帧 bank”演化，否则 BRAM 会成为主约束

这次为了验证新 `pool relay` 是否真能往 7020 上走，不只是停在 Verilator，而是继续跑了：

- `bash gesture_project/innovation_npu/board_7020/run_ooc_gestureflow_wide80_synth_7020_from_wsl.sh`

第一次 OOC 真实失败，失败点不是 `pool relay loader`，而是旧的：

- `gesture_project/innovation_npu/rtl/gestureflow_output_bank.sv`

Vivado 直接报：

- `size of variable 'storage' is too large to handle`

因此已经实际把 `output_bank` 从“一个超大数组”改成了：

- `gestureflow_output_bank_slice`
- 每片 `4096 x 128bit`
- 顶层 bank/slice 选择与返回 mux

改完以后再次重新跑通：

- `run_gestureflow_layer_chain_pool_relay_conv2a_axil.sh`
- `run_gestureflow_layer_chain_relay_axil.sh`
- `run_ooc_gestureflow_wide80_synth_7020_from_wsl.sh`

其中 OOC 最终已经输出：

- `GESTUREFLOW_WIDE80_OOC_PASS`

并生成新的：

- `gestureflow_wide80_ooc_utilization.rpt`
- `gestureflow_wide80_ooc_timing.rpt`
- `gestureflow_wide80_ooc_drc.rpt`
- `gestureflow_wide80_ooc_synth.dcp`

这次最需要记住的不是“综合过了”，而是资源画像：

- `Total LUTs = 39,585`
- `FFs = 43,808`
- `RAMB36 = 224`
- `RAMB18 = 16`
- `DSP = 107`
- `WNS = 16.478ns @ 40ns`

这说明：

1. 片上接力方向在功能和综合可达性上都是成立的
2. 当前问题的重心已经从“能不能综合”转到“全帧 activation bank 的 BRAM 代价太大”

所以接下来的结构突破重点必须从：

```text
继续做更大 bank
```

转成：

```text
更细粒度、更短生命周期的 activation residency
+ 更高价值层的 selective relay
```

也就是：继续坚持“少走 DDR”的方向，但 bank 组织本身要变得更聪明，不能长期维持现在这种粗粒度全帧缓存方式。

## 3. 官方 CoralNPU 这次重新核对后的准确判断

### 3.1 必须以代码为准，网页和文档只能当作架构意图

Google 官方网页 `coralnpu/doc/overview.md` 写得很清楚：

- 标量前端驱动命令队列；
- 核心思想是 `quantized outer product`（量化外积）；
- 文档中描述了“外积矩阵引擎”和“256 MAC/cycle”的目标架构。

但当前只读代码默认参数又明确表明：

- `Parameters.scala` 中 `enableVme = false`；
- `rvv_backend_define.svh` 默认 `VLEN = 128`、`NUM_VRF = 32`；
- `RvvCore.sv` 中 VME-LSU 系统接口仍被 tie-off。

因此这三层必须分开写：

1. **架构目标**  
   CoralNPU 的目标是“轻量标量控制 + 可编程向量/矩阵后端 + 外积式 ML 数据通路”。

2. **当前默认可运行公开主链**  
   当前更稳的是 RVV 向量路径，而不是“现成完整矩阵 NPU 主链”。

3. **当前源码中真实可借鉴的具体硬件思想**  
   不是照搬整个系统，而是借鉴：
   - ready/valid 解耦；
   - 队列与依赖管理；
   - 片上状态驻留；
   - 累加和量化尽量在片上完成；
   - 外积/广播式数据重用的组织思路。

### 3.2 对当前算法最重要的官方软件事实

从当前只读源码可以直接确认：

1. `coralnpu/sw/opt/litert-micro/conv.cc` 对标准卷积的成熟特化明显偏向 `4x4`。
2. `coralnpu/sw/opt/litert-micro/depthwise_conv.cc` 对 `3x3 depthwise` 有专门复用优化。
3. 这不等于“硬件本体只支持 4x4 或 3x3”，但会直接影响：
   - 当前算法什么结构更容易先在官方主链拿到收益；
   - 我们的自研硬件什么结构更值得优先做成专用化能力。

### 3.3 对当前项目真正该借鉴的不是“完整前端”，而是三件硬件思想

对 7020 当前阶段，最值得借鉴的不是把完整标量核/RVV/ROB/矩阵前端一股脑搬进 FPGA，而是这三件更本质的东西：

1. **命令解耦**  
   PS 只提交层级或 tile 级任务，不做卷积内层循环。

2. **局部状态驻留**  
   权重、部分和、量化参数、层间小张量尽量留在片上，而不是每层都回 DDR。

3. **计算形态分层**  
   空间卷积、通道归约、分类头、时序归约不是同一种计算，不该硬塞进一种执行方式。

## 4. 当前 GestureFlow-NPU 的真实结构

### 4.1 当前板测已经坐实的事实

当前 7020 主线已经完成整网板级闭环，最近一次正式验收结果在：

- `gesture_project/docs/会话交接_最高优先级_2026-07-11.md` 第 84 号记录

关键结果是：

- `conv3_b FNV = 0xEA998550`
- `pool3 FNV = 0x8EF3B2CB`
- `head FNV = 0x53C6484E`
- `GAP FNV = 0xABBC5831`
- `FC FNV = 0xDDE32561`
- `FINAL_RESULT = 0x600D600D`

所以现在讨论的不是“是否能跑通”，而是“下一代结构怎么改得更值”。

### 4.2 当前 RTL 模块和职责

当前 7020 主线最关键的模块是：

| 模块 | 文件 | 当前职责 | 当前问题 |
|---|---|---|---|
| 顶层控制与 AXI | `gesture_project/innovation_npu/rtl/gestureflow_layer_chain_hp0_axil.sv` | 寄存器、descriptor、HP0 读写仲裁、权重 bank、postprocess 控制 | 结构过重，既管寄存器又管数据流又管后处理，后续难持续扩 |
| 空间卷积主体 | `gesture_project/innovation_npu/rtl/gestureflow_conv4x4_cin_same_stream.sv` | 4x4 same-padding 滑窗、Cin 分组累加、与 tile 握手 | 主要服务 4x4，难自然承接高精度主线里的首层 3x3 与尾部 1x1 |
| 计算 tile | `gesture_project/innovation_npu/rtl/gestureflow_mac_tile.sv` | 16 输出 × 4 输入 INT8 乘加，INT32 局部累加，权重本地 bank | 只服务“空间 tap 驱动”的卷积数据流，尚未抽象成可复用点积/归约单元 |
| 后处理 | `gesture_project/innovation_npu/rtl/gestureflow_hp0_gap_fc.sv` | DDR 读 head、GAP、FC、argmax | 已能跑通，但还是单用途后处理器，不是通用归约/分类后端 |
| 写回 | `gesture_project/innovation_npu/rtl/gestureflow_hp0_tensor_writer.sv` | burst 写回、pool 融合、尾字节处理 | 仍以“写回 DDR”为主，缺少直接 relay 到下一层的局部接力 |
| 读取 | `gesture_project/innovation_npu/rtl/gestureflow_hp0_tensor_loader_banked.sv` | 分 bank/ring 式张量读取 | 已优于旧 shift loader，但还缺 tile-valid、ROI、层间预取协同 |

补充状态更新：

- 上表中的“空间卷积主体”这一项已经完成第一步修正：当前 RTL 已支持 `KERNEL_SIZE=3/4`，只是模块名暂时还保留历史名字 `gestureflow_conv4x4_cin_same_stream.sv`。
- 真正还没有完成的是：把它继续推成适配 `hybrid344` 主线的稳定统一空间引擎，并和后续 `1x1` 点积路径自然衔接。

### 4.3 当前主线模型和硬件匹配的真实状态

当前项目里必须分清三个层次：

1. **当前 7020 硬件协同主线**
   - `gesture_project/models/repvgg_hybrid344_c16_48_80_h112_noidentity_pairedseed20260811_hagrid6_20260812`
   - `INT8 test accuracy = 87.82%`
   - 部署卷积结构是 `3x3 / 4x4 / 4x4 / 1x1`

2. **更高精度图像单分支**
   - `gesture_project/models/repvgg_3x3_i96_hagrid6_tuned_20260731`
   - `INT8 test accuracy = 89.02%`
   - 精度更高，但对当前 4x4 主后端并不最匹配

3. **蒸馏相关事实**
   - 已完成的蒸馏学生 `...distill3x3a35t2...` 最终 `INT8 = 87.64%`，没有替代当前硬件协同主线；
   - 交接文档里确实记录过一条 **18 类 HaGRID 学生蒸馏训练中断**；
   - 但本轮在当前环境中检查时，历史 `/tmp/hagrid_v1_500k_384p_targethand_student_4x4_rvv_distill_20260815_nocache/` 目录已经不存在，不能假定可直接恢复。

这意味着：

- 用户提醒“之前有高准确率蒸馏线，不要漏看”是对的；
- 但当前能被正式复用的，是**已完成结果和脚本参数**，不是已经丢失的 `/tmp` 临时训练目录。

## 5. 为什么当前路线合理，但不够强

### 5.1 当前路线合理的地方

当前设计抓住了四个正确方向：

1. **片上 INT32 部分和驻留**  
   这是卷积硬件最关键的省带宽点。

2. **行缓存与滑窗复用**
   避免 ARM 逐窗口下发，是对的。

3. **权重先驻留再计算**
   比每拍从 AXI-Lite 写权重强得多。

4. **后处理已下板**
   说明系统已经不是“卷积跑完靠 ARM 收尾”的半成品。

### 5.2 当前路线不够强的地方

真正的不足不在“功能不完整”，而在“结构还没有针对手势任务做深度专用化”：

1. **空间卷积和点积/归约还没分成两类计算路径**
2. **层间中间结果大多还是以 DDR 为主通路**
3. **背景冗余和前景集中这类手势特性还没转化成门控机制**
4. **权重生命周期还只是 bank + key 雏形，不是完整模型级管理**
5. **当前主线模型是 `3x3 / 4x4 / 4x4 / 1x1`，硬件却还没有“统一核大小 + 点积后端”的自然对应**

## 6. 外部公开加速器对照后，哪些思路值得借鉴

本轮补查了四类外部资料：

1. Google 官方 `coralnpu/` 文档与源码  
2. 用户指定仓库 `Arunachalam-212223060022/CNN-Accelerator`
3. `ucb-bar/gemmini`
4. `apache/tvm-vta`

### 6.1 不该照搬的路线：普通 ARM + 单大核 CNN 外设

用户指定的 `CNN-Accelerator` 仓库，本质上是：

- ARM 负责预处理、控制、后处理；
- PL 里是一整个 HLS CNN kernel；
- 通过 AXI HP 搬图像和权重；
- 强调的是“CPU-only 对比加速”。

这类方案的价值在于：

- 工程简单；
- 容易快速出一个“板上 CNN”。

但它有两个明显上限：

1. **没有清晰的权重生命周期管理**
2. **没有把空间卷积、归约、分类、时序归约分开做结构专用化**

因此它适合作为“普通 7020 CNN 外设”的对照反例，不适合作为本项目主路线。

### 6.2 最值得借鉴的路线：Gemmini 的 scratchpad + accumulator + access/execute 解耦

`Gemmini` 最值得我们学的不是大阵列规模，而是：

1. **scratchpad（片上暂存）与 accumulator（片上累加存储）分离**
2. **load / store / execute 三类控制分离**
3. **weight-stationary / output-stationary 等数据流是运行时或配置时选择，不是写死一种**
4. **量化缩放和激活尽量在 accumulator 读出时完成**

对当前 `GestureFlow` 最有价值的对应改造是：

- 把“输出 bank”演化成真正的 relay/accumulator bank；
- 把“后处理模块”演化成通用归约/点积后端；
- 把“descriptor”演化成更清楚的 load/store/execute 协同协议。

### 6.3 VTA 给出的启发

`VTA` 的价值主要不是阵列形式，而是：

- 模块化；
- 自带 simulator（模拟器）和软件调用栈；
- 可用较快行为模型支持编译/映射探索。

这对项目的直接含义是：

- 后续做结构尝试时，要尽量先做**短路径行为仿真或小模块仿真**；
- 不要每个新想法都直接用长时间整网 RTL 仿真或整板来判。

## 7. 当前最值得执行的模块级突破路线

这一节是本文最重要的部分。

### 7.1 路线总原则

对 7020 当前阶段，原则不是“尽量接近官方完整前端”，而是：

```text
借鉴 CoralNPU 的局部状态驻留、命令解耦、外积/广播思想，
把当前 GestureFlow 逐步改造成更适合手势识别的专用计算后端。
```

### 7.1.1 7020 物理布局与数据通路原则

后续 RTL 重构时，逻辑结构和物理布局要一起想，不能先写完 RTL 再临时救时序。当前建议固定成四个物理逻辑岛：

1. **输入岛**
   - `gestureflow_hp0_tensor_loader_banked.sv`
   - 行缓存 / 窗口缓存
   - 放在靠近 HP0 / AXI 互连一侧

2. **计算岛**
   - `gestureflow_conv*_stream.sv`
   - `gestureflow_mac_tile.sv`
   - 局部 requant
   - 紧贴一列或相邻几列 DSP 与相邻 BRAM 列

3. **relay / output 岛**
   - output bank
   - relay bank
   - pool / writer 前级
   - 不要夹在输入岛和计算岛之间

4. **写回与尾部后处理岛**
   - `gestureflow_hp0_tensor_writer.sv`
   - `gestureflow_hp0_gap_fc.sv`
   - 靠近 AXI 写通路

BRAM 和 MAC 的关系要遵守三个原则：

1. **行缓存 BRAM 必须贴计算岛**
   - 因为它每拍供窗，最怕长线。

2. **权重 bank 必须贴 DSP 列**
   - 权重读取扇出到 16 个输出 lane，距离一长就会直接拖跨时序。

3. **relay / output bank 不与行缓存抢同一条关键短路径**
   - 它更适合偏 writer/postprocess 一侧，靠多一级寄存解决，而不是强行和滑窗放一起。

控制与数据边界必须强制寄存的地方：

- HP0 读返回 -> loader ring buffer
- loader -> window engine
- window engine -> MAC tile
- MAC tile -> requant / relay
- relay / writer -> AXI W channel

这不是“实现细节优化”，而是 7020 上是否还能继续扩结构的生死线。

### 7.2 路线一：把 `gestureflow_mac_tile.sv` 升级成“双模计算集群”

当前模块：

- `gesture_project/innovation_npu/rtl/gestureflow_mac_tile.sv`

当前问题：

- 它本质上只服务“滑窗 tap 驱动”的空间卷积；
- 尾部 `1x1`、`FC`、关键点 `MLP`、未来动态手势的时序归约都没有自然入口。

建议升级方向：

1. **不增加第二套大阵列**
   - 7020 资源不允许再复制一套完整 MAC 阵列。

2. **把现有物理 16×4 INT8 乘法簇抽象为双模执行**
   - `mode_spatial`
     继续服务 `3x3 / 4x4` 空间卷积；
   - `mode_reduce`
     服务 `1x1 / FC / MLP / temporal reduce`。

3. **空间模式**
   - 保留当前“每拍 16 输出 × 4 输入”；
   - tap 维度由统一窗口发生器提供。

4. **归约模式**
   - 取消空间 tap 维；
   - 把同一 64 路 INT8 乘法资源重用于通道点积；
   - INT32 累加继续留在本地。

这条路线的价值是：

- 不复制大硬件；
- 把当前“卷积后处理器”思维，推进到“统一卷积/点积算力簇”；
- 为后续关键点分支和动态手势时序分支打通硬件入口。

### 7.3 路线二：把 `gestureflow_conv4x4_cin_same_stream.sv` 演化成统一 `3x3/4x4` 空间引擎

当前模块：

- `gesture_project/innovation_npu/rtl/gestureflow_conv4x4_cin_same_stream.sv`

当前问题：

- 当前硬件协同主线模型是 `3x3 / 4x4 / 4x4 / 1x1`；
- 但现 RTL 主体仍以 `4x4` 空间引擎为中心；
- 高精度图像线又明显偏 `3x3`。

建议升级方向：

1. 新增统一窗口引擎，不再把 `3x3` 和 `4x4` 理解成两套完全不同模块。
2. 采用：
   - 共用行缓存；
   - 共用输出通道 tile；
   - 由 `tap_mask` 或 `kernel_mode` 选择 `3x3` 或 `4x4` 有效 tap。
3. 首层高分辨率处重点支持 `3x3`；
4. 中后层继续保留 `4x4` 的高吞吐优势。

这条路线的价值是：

- 让当前最优硬件协同模型 `hybrid344` 真正有硬件一一对应；
- 不必在“高精度 3x3”与“高吞吐 4x4”之间二选一；
- 能把算法探索范围从“纯 4x4”放宽到“混合核但同一引擎支持”。

### 7.4 路线三：把 `weight key/hit/miss` 雏形升级成真正的权重生命周期管理器

当前模块位置：

- `gesture_project/innovation_npu/rtl/gestureflow_layer_chain_hp0_axil.sv`

当前已有：

- `WEIGHT_KEY`
- `WEIGHT_HIT_COUNT`
- `WEIGHT_MISS_COUNT`
- `WEIGHT_DMA_*`

当前问题：

- 还更像“寄存器化 bank 控制”，不是完整模型级生命周期管理。

建议升级方向：

1. 定义模型级 `model_id + layer_id + tile_id`
2. 区分：
   - 模型切换；
   - 同模型跨帧复用；
   - 层内 tile 切换；
   - 参数 bank 切换
3. 为每帧统计：
   - 首次装权重字节；
   - 复用命中次数；
   - 由于容量不足引起的重装次数

这条路线对手势识别特别重要，因为：

- 静态/动态手势部署时，模型通常长时间不变；
- 真正商业系统里，跨帧复用比单帧极限吞吐更重要。

### 7.5 路线四：把 writer/output bank 升级成 relay bank

当前相关模块：

- `gesture_project/innovation_npu/rtl/gestureflow_hp0_tensor_writer.sv`
- 顶层中的 output bank / writer 路径

当前问题：

- 当前主通路仍然以“写回 DDR，再读出下一层”为主；
- 对尾部 `pool3 -> head1x1 -> GAP` 这种链来说，片上接力空间还没吃透。

建议升级方向：

1. 引入小容量 relay bank，只服务：
   - 下一层马上消费的局部张量；
   - 或池化后立即进入 head/GAP 的尾部特征。
2. 先不追求整网所有层完全不落 DDR；
3. 优先选：
   - `conv3_b -> pool3`
   - `pool3 -> head1x1`
   - `head1x1 -> GAP`

这样做的价值是：

- 直接减少 DDR 往返；
- 对 7020 的小模型尾部特别划算；
- 比起盲目扩大卷积阵列，更容易拿到真实系统收益。

### 7.6 路线五：在 loader 侧引入 tile-valid / ROI 门控

当前相关模块：

- `gesture_project/innovation_npu/rtl/gestureflow_hp0_tensor_loader_banked.sv`

建议方向：

1. 给 loader 加入 coarse tile-valid mask（粗粒度 tile 有效掩码）
2. 输入可以来自：
   - ARM 侧前景检测；
   - 早层极低成本前景估计；
   - 或后续关键点/手框先验
3. 对明显空白背景 tile：
   - 不读整 tile；
   - 或直接送零并跳过部分 MAC 使能

这条路线特别适合手势识别，因为：

- 手通常集中在中部或少数区域；
- 背景空白和冗余很高；
- 动态手势未来的连续帧里，这种前景稳定性更明显。

### 7.7 路线六：把 `gestureflow_hp0_gap_fc.sv` 从“后处理模块”升级成“归约/分类后端”

当前模块：

- `gesture_project/innovation_npu/rtl/gestureflow_hp0_gap_fc.sv`

建议升级方向：

1. 把它从“只做 GAP+FC”升级成统一的：
   - `GAP`
   - `FC`
   - 小型 `MLP`
   - `temporal reduce`
   - 小型 `1x1` 点积类
   后端。

2. 与上面的双模 MAC 集群对接：
   - 共用部分 INT8×INT8→INT32 点积路径；
   - 保持 requant / 激活 / argmax 融合。

3. 未来关键点分支和动态手势分支都尽量走这条后端，而不是再重新造一套小矩阵核。

这条路线是当前项目从“纯卷积板级演示”走向“系统级手势专用 NPU”的关键一步。

## 8. 这条路线为什么比当前常见公开轻量加速器更适合手势识别

### 8.1 比普通 7020 HLS CNN 核更强的地方

普通公开 7020 CNN 加速器常见问题是：

- 只会整层 kernel；
- 权重和特征全部走 DDR；
- 缺少模型级权重复用；
- 缺少归约/分类后端独立结构；
- 动态手势和关键点路线几乎没法接。

当前提出的路线不是继续复刻这种形态，而是：

- 保留可编程 descriptor；
- 保留权重和部分和局部驻留；
- 引入 relay bank；
- 把空间卷积和归约/分类做成统一算力簇上的两种执行模式。

### 8.2 比只做“纯 4x4 卷积器”更强的地方

只做纯 `4x4` 卷积器的问题是：

- 当前图像高精度线并不纯 `4x4`；
- 静态图像单分支最优仍明显保留 `3x3` 价值；
- 未来关键点分支和动态手势尾部完全不适配。

统一 `3x3 / 4x4 / 1x1 / reduce` 的路线，虽然设计更难，但更贴近最终完整系统。

## 9. 对算法侧的直接约束

### 9.1 当前最值得保留的图像主线

当前最值得保留为硬件协同图像主线的是：

- `gesture_project/models/repvgg_hybrid344_c16_48_80_h112_noidentity_pairedseed20260811_hagrid6_20260812`

原因不是它精度绝对最高，而是：

1. 它已经达到 `INT8 87.82%`；
2. 它的结构正好对应 `3x3 / 4x4 / 4x4 / 1x1`；
3. 最适合作为当前“统一空间引擎 + 归约后端”路线的硬件驱动对象。

### 9.2 当前最值得保留的高精度图像参考线

作为图像分支精度上限参考，当前仍应保留：

- `gesture_project/models/repvgg_3x3_i96_hagrid6_tuned_20260731`

因为它说明：

- 图像分支单独做到更高精度是可能的；
- 当前 4x4 路线不应只盯吞吐，必须继续想办法保留 `3x3` 表达能力。

### 9.3 当前不该再作为唯一主线的结构

在没有新 reduce 后端前，不建议把这些结构当唯一主线：

- 深度可分离卷积占主导的 `MobileNet` 型结构；
- 大量 `1x1 pointwise` 占主导的结构；
- 需要大矩阵主链才能真正受益的结构。

原因很直接：

- 当前自研硬件主力不是为它们最优设计；
- 当前官方公开主链也没有给出“这类结构天然最优”的充分证据。

## 10. 接下来最应该按什么顺序推进

### 10.1 第一阶段：先重构结构边界，不先盲增算力

先做：

1. 把顶层 `gestureflow_layer_chain_hp0_axil.sv` 继续拆分职责
2. 统一空间引擎支持 `3x3 / 4x4`
3. 把 `gap_fc` 路径抽象成通用 reduce 后端

不要先做：

- 再复制一套完整 MAC 阵列；
- 直接上更宽通道；
- 大量零碎 patch。

### 10.2 第二阶段：围绕 `hybrid344` 做第一次真正的“模型-硬件一一对应”

目标是让当前主线模型：

```text
3x3 / 4x4 / 4x4 / 1x1
```

在硬件里不再是“4x4 主后端硬套 3x3 和 1x1”，而是：

- 首层 `3x3` 有自然入口；
- 中段 `4x4` 吞吐最大化；
- 尾部 `1x1` 走 reduce/dot 模式。

### 10.3 第三阶段：再回头做新的算法搜索

等硬件具备以上三个能力后，再去大规模做算法搜索才有意义：

1. 混合核图像网络
2. 图像 + 关键点双分支
3. 动态手势的轻量时序模块

否则会出现“算法选了，但硬件完全不自然”的情况。

## 11. 当前正式结论

当前最合理的正式表述是：

> 项目当前已经在 Zynq-7020 上完成了自研 `GestureFlow-NPU` 的第一版整网板级闭环。  
> 下一阶段不应再把工作收缩为单一 `4x4` 卷积器补丁，而应借鉴 Google 官方 CoralNPU 的命令解耦、状态驻留和外积广播思想，把当前主线演化为：  
> **统一 `3x3/4x4` 空间引擎 + 可复用点积/归约后端 + 权重生命周期管理 + relay bank + ROI/tile-valid 门控**。  
> 这条路线既比普通 7020 CNN 外设更有研究价值，也更贴近手势识别真实系统的长期最优解。

## 12. 2026-08-25 晚间全量硬件审计新增结论

这一节不是重复前面路线，而是基于**当前真实 RTL**和**当前 routed 报告**补上的优先级校准。

### 12.1 先按真实最差路径排优先级，不再凭直觉

检查：

- `E:\coralnpu_vivado\projects\gestureflow_wide80_7020_v1\axi_gpio.runs\impl_1\system_wrapper_timing_summary_routed.rpt`

当前最差 setup 路径不在主卷积 `MAC tile`，而在：

- `gesture_project/innovation_npu/rtl/gestureflow_hp0_gap_fc.sv`

具体是 `GAP requant + FNV hash` 链。  
这次已经实际把它拆成：

- `GAP_QUANT`
- `GAP_HASH`

并重新跑通：

- `run_gestureflow_hp0_gap_fc_real.sh`
- `run_gestureflow_layer_chain_hp0_postprocess.sh`

所以后续节奏必须改成：

1. 先看 routed 真正最差路径；
2. 再决定先拆哪条结构；
3. 不能再默认“主卷积一定是唯一关键路径”。

### 12.2 当前最被低估、但最值得重构的一块：requant 过度并行

当前：

- `gesture_project/innovation_npu/rtl/gestureflow_requant_relu.sv`

是 `16 lane` 全并行 `32x32` requant。

这在“功能上”没问题，但从当前数据流看很可能是**资源和时序都不划算**：

1. 主卷积后端不是每拍都产生一组 `16 lane` 结果。
2. `3x3 / 4x4 / 1x1` 主路径都要先走完大量 `tap x Cin-group` 累加后，才吐出一组向量。
3. 因此 requant 即使改成更窄的时间复用结构，只要总完成时间仍小于下一个结果向量到来间隔，就**不会卡主吞吐**。

这意味着当前最强的一条结构优化候选，不一定是“继续加乘法器”，而是：

- 把 requant 从 `16 lane` 全并行改成 `4 lane` 或 `8 lane` 时间复用；
- 用更深流水换更高频率；
- 把省下来的 DSP 和布线余量让给更有价值的模块。

这条路线的价值非常大，因为它可能同时解决三件事：

1. DSP 占用过高；
2. requant 自身 DPOP 告警；
3. 给后续 relay / 预取 / 权重管理腾资源。

### 12.3 真正值得扩资源的地方，不是“再堆后处理并行度”，而是三类数据流结构

如果通过 requant 和哈希的重构收回了一部分资源，优先把资源投到这三类地方：

1. **relay bank / 层间直通**
   - 目标：减少中间层回 DDR
   - 受益最大的是 `conv -> pool -> next conv` 和 `conv -> 1x1 head`

2. **权重生命周期管理**
   - 目标：从“bank + key”升级到真正的 layer/tile 级常驻
   - 减少 PS 干预和重复装载

3. **pointwise / reduce 双模后端**
   - 目标：让 `1x1 / FC / temporal fusion` 进入统一执行路径
   - 避免继续保留“空间卷积一套、后处理一套”的割裂结构

### 12.4 顶层 RTL 目前最大的问题不是功能，而是职责过度堆叠

当前：

- `gesture_project/innovation_npu/rtl/gestureflow_layer_chain_hp0_axil.sv`

同时承担：

1. AXI-Lite 寄存器映射
2. descriptor 重放
3. 多路 HP0 读仲裁
4. 权重/参数 bank 管理
5. hash
6. postprocess 管理
7. writer 启停

这在“第一版可跑通”阶段是合理的，但对后续继续提频、提吞吐、加 relay 会形成结构阻碍。  
后续应该拆成至少三层：

1. **control plane**
   - AXI-Lite
   - descriptor
   - 状态/计数器

2. **data mover plane**
   - RGB/tensor/weight/postprocess loader arbiter
   - writer

3. **compute plane**
   - stream engine
   - requant
   - relay / output bank

只有这样，后续继续做双 bank、预取、局部接力时才不会把一个顶层文件越改越重。

### 12.5 对“全部硬件代码都看过之后”的当前排序结论

按对 7020 长期最优路线的重要性排序，当前最值得推进的结构改造次序应是：

1. `gestureflow_requant_relu.sv`
   - 改成更窄、更深流水的时间复用 requant

2. `gestureflow_layer_chain_hp0_axil.sv`
   - 拆分 control / mover / compute

3. `gestureflow_output_bank.sv` + `gestureflow_hp0_tensor_writer.sv`
   - 从“最终写回 bank”升级成“relay + writeback 双用途 bank”

4. `gestureflow_mac_tile.sv`
   - 从纯空间卷积 tile 升级到稳定双模 `spatial + reduce`

5. `gestureflow_hp0_tensor_loader_banked.sv`
   - 增加 tile 预取协同、tile-valid / ROI 门控

6. `gestureflow_same4x4_cin_window.sv` + `gestureflow_conv4x4_cin_same_stream.sv`
   - 继续把 `3x3 / 4x4 / 1x1` 统一到更干净的数据流边界

### 12.6 这一节之后的执行纪律

后续再做结构修改时，必须同时满足：

1. 改动前先指出本轮要收的真实瓶颈来自哪份报告、哪个模块。
2. 改完后必须至少跑对应模块级回归，不允许只停在“代码写好了”。
3. 如果目标是提频，优先看 routed 最差路径有没有换位置，而不是只看 DRC 告警条数。
4. 任何“新并行度”都要先问一句：它是不是当前真正的吞吐瓶颈；如果不是，就先考虑时间复用和资源回收。

## 13. 2026-08-25 深夜补充：4 路时间复用 requant 已修正，证明“先收非主瓶颈宽并行”这条路线成立

### 13.1 这次不是回退优化，而是把时间复用版真正修到可用

在第 12 节之后，项目侧继续推进了：

目标没有变，仍然是把原来 `16 lane` 全并行的 requant 缩成 `4 lane` 时间复用，以减少 7020 上非主吞吐路径的 DSP/route 压力。

第一版时间复用实现最初确实写坏了，症状非常集中：

### 13.2 这次钉死的根因

通过把 `gestureflow_requant_relu.sv` 单独拉出来做隔离 Verilator 仿真，可以确认：

1. `requantize_lane()` 里的 LiteRT 数值公式本身没有错；
2. `multiplier / right_shift / zero_point` 捕获值也没错；
3. 真正出错的是第一版时间复用实现对 **packed 数组做变量索引写回** 的那层写法。

也就是说，这次问题不是“时间复用方向错了”，而是“当前 RTL 具体实现方式不稳”。这一点对之后继续做 `relay bank`、`dual-mode MAC`、`reduce backend` 很重要，因为这些结构都会大量碰到“分块处理 + 局部写回”的相同范式。

### 13.3 最终修法

当前已采用的稳态修法是：

1. 把 `pending_psum / pending_multiplier / pending_right_shift / pending_lane_enable` 改成 unpacked 数组寄存；
2. 每拍只在 `chunk_data_comb` 中计算当前 `4 lane chunk`；
3. 回写 `out_data` 时不再用旧的 packed 变量索引，而是用常量 lane 位置逐个写回；
4. 保持 `config_error` 的 sticky 语义不变。

这个修法的价值在于：

- 仍然保留 `4 lane` 时间复用的资源回收方向；
- 但把最容易在仿真和综合中埋坑的写法去掉了；
- 为后续继续把 requant 做成“窄并行 + 更深流水”的 7020 友好结构打下了正确基础。

## 14. 2026-08-25 深夜再补充：连续写回 `writer` 已从 4 向量 burst 扩到 8 向量，并重新压过 handoff 主线

### 14.1 这次改动解决的不是 MAC，而是 layer handoff 写回头开销

这次继续推进的模块是：

- `gesture_project/innovation_npu/rtl/gestureflow_hp0_tensor_writer.sv`

当前 `writer` 在连续 `16B vector` 写回模式下，原先固定一次只发 `4 vector = 8 beat`。  
对 7020 来说，这不是最重的瓶颈，但它确实会带来额外的：

- AW 事务头开销
- B 返回往返
- 写回状态机空拍

而这些开销不会给数值正确性带来任何收益。

所以这次做的不是“更宽算力”，而是把连续写回 burst 深度从 `4 vector` 提高到 `8 vector`，用更少的外部写事务完成同样的数据搬运。

### 14.2 当前已落地的 RTL 变化

这次对 `gestureflow_hp0_tensor_writer.sv` 做了三类修改：

1. 新增 `MAX_BURST_VECTORS` 参数，默认值改为 `8`
2. 把 `burst_vectors / burst_beats / burst_read_index / burst_beat_index` 全部改成按参数推导位宽
3. 把相关比较、索引、地址推进全部改成严格同宽写法，消除 Verilator 宽度告警

这一步的意义不只是“代码更整齐”，而是：

- 后续如果继续把 burst 深度做实验对比，不用再手工改一堆常量；
- 当前主线已经能在不碰主 MAC 路径的前提下，真实减少连续写回的事务数量；
- 不会因为位宽告警把后续仿真或综合风险藏起来。

### 14.3 这次还顺手修正了一条很关键的测试不一致

在重跑大链路时，发现：

- `gesture_project/innovation_npu/tests/tb_gestureflow_layer_chain_hp0_axil.sv`

## 15. 2026-08-25 片上 `relay bank` 第一版已打通，层间接力从“写 DDR 再读 DDR”前移到 bank 直读

这次新增的不是新的卷积核，而是层间数据搬运方式的第一版结构升级。当前已经通过的新回归是：

- `bash gesture_project/innovation_npu/tests/run_gestureflow_layer_chain_relay_axil.sh`
- 输出：`GESTUREFLOW_LAYER_CHAIN_RELAY_AXIL_PASS layer0=f49b1b48 layer1=893afa60 pixels=9216`

这条回归证明了三件事：

1. 第一层输出已经可以保存在双 bank 里的某一个 bank 上。
2. 第二层可以直接从片上 bank 读，不再先落 DDR 再回读。
3. relay 模式下，第二层运行期间 HP0 中间读写通道保持静默，没有出现额外的 DDR 往返事务。

对应的新增 / 修改模块是：

- `gesture_project/innovation_npu/rtl/gestureflow_output_bank.sv`
- `gesture_project/innovation_npu/rtl/gestureflow_output_bank_relay_loader.sv`
- `gesture_project/innovation_npu/rtl/gestureflow_layer_chain_hp0_axil.sv`

对应的控制入口是：

- `RELAY_CONTROL[0]`：启用 relay 模式
- `RELAY_CONTROL[1]`：选择 relay 读取的 bank
- `RELAY_CONTROL[2]`：选择当前层输出写入的 bank

这次还确认了一个容易埋坑的点：

- `relay_done` 只能表示输入流结束，不能直接当作整层完成；
- 真正的层结束仍然要等输出写回和哈希 drain 完成。

下一步如果继续沿这条线推进，最值得先试的是：

1. `pool -> head1x1` 的 relay。
2. `conv -> pool` 的 relay。
3. 只在这些高频链路上继续扩 bank 语义，不要回头去扩一套新的大 MAC。
