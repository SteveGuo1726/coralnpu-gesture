## 2. 先给结论

### 2.1 qwen 分析里可以直接保留的核心结论

这些判断与官方源码是一致的，可以继续作为后续路线依据：

- CoralNPU 不是固定功能的 `3x3` 卷积核，而是“轻量 `RISC-V` 标量控制前端 + `RVV` 向量后端 + 可选 `ZVT/VME` 矩阵扩展”的可编程结构。
- 当前默认参数下，向量主链是 `VLEN = 128 bit`、`instructionLanes = 4`、`NUM_MUL = 2`、`NUM_ALU = 2`、`NUM_LSU = 2`、`NUM_VRF = 32`。
- 官方源码中真实存在 `ZVT/VME` 相关 RTL，包括 `zvt.sv`、`zvt_ctrl.sv`、`zvt_acc.sv`、`zvt_pe_array.sv` 等文件。
- 官方 `TFLite Micro` 卷积优化主链对标准 `Conv2D` 的成熟特化，当前明显偏向 `4x4` 路径。
- 官方 `DepthwiseConv2D` 代码中，当前对 `3x3` 存在专门的中心区域复用优化。

### 2.2 qwen 分析里必须修正的地方

这些表述如果不修正，后续路线会被带偏：

- 不能把 `instructionLanes = 4` 直接写成“传统意义上已经充分证实的 4 发射超标量 CPU”。
- 不能把 `RVV 1.0` 写成“所有实现都已经完整、无保留地覆盖了全部能力”。
- 不能把 `VME` 写成“当前默认构建已经启用且系统级完全打通”。
- 不能把“软件里存在 `4x4 Conv2D` 专用优化”直接等价成“硬件本体就是固定的 `4x4` 卷积阵列”。
- 不能把理论并行度、理论 `GMAC/s` 或与商用芯片的纸面对比，写成项目当前已经得到的真实性能结论。

### 2.3 当前项目后续方向

当前最稳、也最符合官方源码真实结构的方向是：

1. 算法侧先继续提高精度，不再把纯 `3x3` 单分支当成唯一主线。
2. 官方仿真与硬件理解侧，要优先围绕官方真实可见的 `RVV` 与独立 `VME` 目标做验证，不再围绕旧 `7Z010` 妥协试验打转。
3. 未来硬件侧应按“双后端”思路规划：
   - 一个偏空间卷积的数据流后端，服务 `3x3 / 4x4 / 少量 depthwise`
   - 一个偏稠密矩阵的数据流后端，服务 `1x1 / MLP / FC / GRU`

## 3. 源码已证实的内容

### 3.1 默认参数和向量主链

`coralnpu/hdl/chisel/src/coralnpu/Parameters.scala` 直接给出：

- `itcmSizeKBytesDefault = 8`
- `dtcmSizeKBytesDefault = 32`
- `instructionLanes = 4`
- `rvvVlen = 128`
- `enableVme = false`

`coralnpu/hdl/verilog/rvv/inc/rvv_backend_define.svh` 直接给出：

- `ISSUE_LANE = 4`
- `NUM_VRF = 32`
- `NUM_LSU = 2`
- `NUM_ALU = 2`
- `NUM_MUL = 2`

因此当前最准确的说法是：

- 默认主链是 `RVV 128-bit` 向量执行后端。
- `VME` 不是默认普通构建的一部分。
- 当前公开主链首先应被理解为“可编程向量计算核心”，而不是已经完成产品化封装的固定卷积 NPU。

### 3.2 VME 是真实存在的，但不是默认普通构建

官方源码中，下面这些文件真实存在：

- `coralnpu/hdl/verilog/rvv/design/Zvt/zvt.sv`
- `coralnpu/hdl/verilog/rvv/design/Zvt/zvt_ctrl.sv`
- `coralnpu/hdl/verilog/rvv/design/Zvt/zvt_acc.sv`
- `coralnpu/hdl/verilog/rvv/design/Zvt/zvt_pe_array.sv`
- `coralnpu/hdl/verilog/rvv/design/Zvt/zvt_pe_block.sv`

官方构建规则也明确给出了独立的 `VME` 目标：

- `coralnpu/hdl/chisel/src/coralnpu/BUILD`
  - 包含 `--enableVme=True`
  - 包含 `vme_core_mini_axi_cc_library`
  - 包含 `-DZVT_ON`
- `coralnpu/tests/cocotb/BUILD`
  - 包含 `vme_core_mini_axi_model`
  - 也显式加入 `-DZVT_ON`

因此准确表述应是：

- `VME` 不是“没有”。
- `VME` 也不是“默认主链已经全开”。
- 官方已经提供了独立的 `VME` 生成目标和仿真目标，后续验证应该走这条路，而不是修改官方仓库硬开宏。

### 3.3 VME 当前还不能写成“系统级完全打通”

`coralnpu/hdl/verilog/rvv/design/RvvCore.sv` 中明确写着：

- `Tie-off VME LSU interfaces`
- `TODO: Support these`

并且相关 `uop_vme2lsu_*` 信号当前被 `dummy / tie-off` 处理。

这说明：

- `VME` 的 RTL 主体、控制器、累加器和阵列结构是存在的。
- 但当前公开源码里，`VME` 到系统级访存路径的整合不能直接假定已经完整成熟。

因此后续项目不能直接宣传：

- “官方矩阵引擎已经完全可用”
- “只要开宏就能拿到完整矩阵 NPU 性能”

### 3.4 当前公开软件卷积主链的真实偏向

`coralnpu/sw/opt/litert-micro/conv.cc` 中能直接看到：

- `Conv2D_4x4`
- `Conv_4x4_OCVectorized`
- 多处 `if (filter_height == 4 && filter_width == 4)` 的专门分流

因此当前公开软件主链对标准卷积的最成熟特化，是：

- `4x4 Conv2D`

`coralnpu/sw/opt/litert-micro/depthwise_conv.cc` 中能直接看到：

- `DepthwiseConvPerChannelPatchCenter3x3Reuse6`

因此当前公开软件主链对深度卷积的已知优势区，是：

- `3x3 depthwise`

这两条一起决定了后续算法设计不应再只围着“全网都是传统 `3x3 standard conv`”打转。

## 4. 对 qwen 分析需要降级或改写的内容

### 4.1 “4 发射超标量 CPU”要改成更稳妥表述

当前我们能从源码直接确认的，是：

- 有 `instructionLanes = 4`
- 有 `ISSUE_LANE = 4`

但只凭这两处参数，不宜在项目正式文档里直接写成：

- “已经完全证实是传统意义的 4 发射超标量 CPU”

更稳妥的写法是：

- 官方核心前后端存在 `4-lane` 级别的并行参数配置；
- 其本质仍应优先理解为“轻量控制前端配合向量/矩阵执行后端”的 NPU 架构，而不是把讨论重点放到 CPU 级超标量名词上。

### 4.2 “完整 RVV 1.0”暂时不要写死

项目正式文档里，当前更合适的表述是：

- `RVV` 向量后端，目标面向 `RVV 1.0` 体系；
- 但如果没有做系统性的指令覆盖验证，就不要把它写成“已经完整验证全部能力”。

### 4.3 “支持 INT8 / INT16 / INT32 / BF16”必须按配置说

`qwen-analysis.md` 把多精度支持写得过于绝对。

更准确的表述应是：

- 不同精度能力受具体宏配置和生成目标影响；
- 项目后续如果要对某种精度做算法或硬件决策，必须以实际构建目标、实际仿真和实际可运行路径为准。

### 4.4 “理论性能”和“项目实测”必须分开

像：

- 理论 `GMAC/s`
- 与商用芯片的理论对比
- 扩到 `VLEN=512`
- 直接把 `NUM_MUL` 改成 4
- 直接把 `NUM_ACC` 扩到 32

这些都只能算建议探索，不是当前项目已经证实的能力。

特别是下面这些动作，当前都不能直接作为正式执行项：

- 修改官方 `coralnpu/` 仓库来扩大参数
- 把理论参数扩展直接写成“后续一定照做”
- 把纸面并行度直接等价成整网性能收益

原因很直接：

- 用户已经明确要求 `coralnpu/` 只读。
- 当前项目还没有完成对应的独立仿真、软件调用链验证和算法映射验证。

## 5. 项目已实测证实的内容

### 5.1 当前静态手势识别的真实最优线

当前项目已经保留并实测的静态结果里，最重要的是三条：

1. 纯卷积保底线  
   - 报告：`gesture_project/reports/static_cnn_regularized_3x3_i96_e70_hagrid6_sample_wsl_retrain_20260707_keras_eval_20260728.json`
   - 当前测试准确率约 `79.24%`
   - 价值：结构简单、部署直接、仍适合作为空间卷积保底映射对象

2. 关键点单分支  
   - 报告：`gesture_project/reports/landmark_static_mlp_mp21_full_20260728_eval.json`
   - 当前测试准确率约 `87.07%`
   - 价值：低算力、低输入带宽、天然适合后续稠密矩阵后端

3. 当前静态最高系统线  
   - 报告：`gesture_project/reports/repvgg3x3_landmark_geom_fusion_20260731.json`
   - 验证集准确率 `94.27%`
   - 测试集准确率 `94.62%`
   - 结构：`RepVGG` 图像分支 + 关键点 `MLP` 分支的加权融合

另外还有一条值得保留的图像单分支结果：

- `gesture_project/models/repvgg_3x3_i96_hagrid6_tuned_20260731`
- 其融合报告中记录的图像单分支测试准确率约 `89.47%`

这组结果说明：

- 当前整体静态最优路线，已经不是“单一图像 CNN”。
- 以后算法优化不能只追着纯 `3x3` 主线走。
- 图像分支和关键点分支必须作为两个正式对象共同考虑。

### 5.2 当前训练式融合头并没有超过简单加权融合

`gesture_project/reports/repvgg3x3_landmark_trainable_fusion_20260731.json` 中当前最优候选为：

- `hidden = 64`
- 验证集准确率约 `93.24%`
- 测试集准确率约 `93.87%`

它低于当前简单加权融合的 `94.62%`。

因此当前更稳的结论不是“立刻上更复杂的融合头”，而是：

- 继续优化图像分支训练；
- 继续优化关键点分支输入特征与清洗；
- 再考虑更强但仍可部署的融合方式。

## 6. 当前正式后续路线

## 6.1 算法侧

### 静态手势

当前正式保留三条线：

1. `3x3` 纯卷积保底线  
   用于空间卷积硬件的保底映射，不再把它当成系统精度上限。

2. `RepVGG` 图像线  
   这是当前更强、且部署后可折叠成单路卷积的图像主候选。

3. 图像分支 + 关键点分支的系统融合线  
   这是当前真实最高精度路线，后续要作为教师系统和总体上限。

下一步算法优化建议：

- 继续把图像分支做成“高精度但仍然卷积友好”的结构；
- 控制性探索“主体偏 `4x4`、局部保留 `3x3` 表达能力”的混合卷积结构；
- 不再盲目回到 `1x1 pointwise` 占主导的 `MobileNet` 风格；
- 继续保留关键点支路，因为它已经证明与图像分支存在显著互补。

### 动态手势

当前更合理的主线优先级仍然是：

1. `landmark sequence + GRU`
2. `landmark sequence + TCN`
3. `逐帧强分类器 + 时间平滑 / 迟滞`

原因不是“听起来先进”，而是它们与当前已知强项匹配：

- 关键点已经被当前项目实测证明有效；
- 这些结构更容易对接未来稠密矩阵后端；
- 不会过早被单一空间卷积思路绑死。

## 6.2 官方仿真与项目侧验证

后续验证顺序应明确为：

1. 继续使用项目已经跑通的官方普通卷积和深度卷积仿真入口，做周期与行为对照。
2. 在项目工作树中补走官方 `VME` 独立目标和专项测试。
3. 先确认 `VME` 的实际可运行边界，再决定是否把更多算法主干转向明显更矩阵友好的结构。
4. 所有项目侧扩展，都放到 `gesture_project/` 的工作树或新实验目录里，不修改官方 `coralnpu/`。

这里特别强调：

- 不能因为看见 `ZVT` RTL 存在，就默认全网都该立刻改成“纯 `4x4` 矩阵主线”。
- 也不能因为过去做过很多 `3x3` 试验，就忽略官方当前公开软件路径对 `4x4` 的明显偏向。

正确做法是：

- 用官方可运行入口，逐步把“结构适配性”和“周期收益”都做成可验证事实。

## 6.3 未来硬件改进方向

未来正式硬件规划，建议用“双后端”来统一：

### 空间卷积后端

主要服务：

- `3x3 standard conv`
- `4x4 standard conv`
- 必要的 `3x3 depthwise`

重点能力：

- 行缓冲
- 滑窗复用
- 权重驻留
- 片上部分和累加
- `requant / ReLU` 融合

### 稠密矩阵后端

主要服务：

- `1x1`
- `FC`
- `MLP`
- `GRU gate`
- 融合头

重点能力：

- 小 `tile` 矩阵乘
- `INT8` 输入
- `INT32` 部分和驻留
- 小批量序列推理
- 片上权重复用

这样规划的原因是：

- 当前图像分支和关键点分支的计算形态已经出现明显分裂；
- 单一路线硬件无法同时高效覆盖这两类负载；
- 这比继续围绕旧 `3x3` 局部技巧打补丁，更符合 CoralNPU 的长期价值。

## 7. 当前明确不再采用的误导性说法

后续文档里不要再写：

- “CoralNPU 本体就是 `3x3` 卷积核”
- “`4x4` 软件路径已经证明硬件本体就是 `4x4` 卷积阵列”
- “把 `-DZVT_ON` 打开就等于矩阵引擎完整可用”
- “理论 `GMAC/s` 就代表项目当前整网性能”
- “当前整体最佳算法就是单一纯卷积模型”

## 8. 当前一句话总路线

```text
官方 CoralNPU 当前应被理解为“RVV 主链 + 独立 VME 方向”的可编程轻量 NPU；
项目侧则以“高精度静态双分支、后续动态关键点序列、未来双后端硬件协同”为正式主线，
在不修改官方仓库的前提下继续做真实验证和定向优化。
```
