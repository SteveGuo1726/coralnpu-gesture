### 2. ⚠️ 本机 agent 环境的 git 陷阱（重要，写进 sync_repo.sh 头部）

1. **git 的 ref 锁写入被拦**：`git fetch` 报 `* [new branch] main -> origin/main`，
   但 `.git/refs/remotes/` 下**没有文件**、`git rev-parse origin/main` 说 "not a commit"。
   手动往 `.git/refs/...` 写文件是**正常**的 ⇒ 是 lockfile+rename 流程被拦。
   **后果**：连续两次 commit 会让本地分支**静默分叉**。
   **对策**：每次操作后显式 `git fetch && git rev-parse refs/remotes/origin/main` 确认。
2. **"提交成功"不可信**：出现过 `git commit` 报成功、但提交里**没有**实际改动
   （`--stat` 只有别的文件）。**对策**：提交后 `git show --stat HEAD`，
   并从远端 `git show refs/remotes/origin/main:<path>` 回读关键文件确认。
3. **分叉修复姿势**（保留工作树里真正想要的改动）：
   `cp <文件> /tmp/keep` → `git fetch` → `git reset --hard refs/remotes/origin/main`
   → `cp /tmp/keep <原路径>` → `git add` → `commit` → `push`。
   **不要 merge/rebase**，直接以远端为基线重做更干净。
4. **`git reset --soft` 会连带把工作树里的旧文件差异一起提交**（曾因此误回退了
   `sync_repo.sh` 的 43 行改进，后来专门补了一个提交修复）。
5. **永远只有一端 commit** —— Windows 端无推送能力，以 Ubuntu 为提交端。

## 【第 4 次构建失败】DWC3 host-only 链接失败 —— 还是我配错了（00:33）

`petalinux-build` 在 `linux-xlnx do_compile` 失败：

```
aarch64-xilinx-linux-ld.bfd: drivers/usb/dwc3/core.o: in function `dwc3_remove':
core.c:(.text+0x580): undefined reference to `dwc3_gadget_exit_hibernation'
core.c:(.text+0x86c): undefined reference to `dwc3_gadget_exit_hibernation'
make[1]: *** [scripts/Makefile.vmlinux:34: vmlinux] Error 1
```

### 根因（源码级确证）
`kernel_uvc.cfg` 里我写了：
```
CONFIG_USB_DWC3_DUAL_ROLE=n
CONFIG_USB_DWC3_HOST=y
```
生成的 `.config` 确认：
```
CONFIG_USB_DWC3_HOST=y
# CONFIG_USB_DWC3_GADGET is not set
# CONFIG_USB_DWC3_DUAL_ROLE is not set
```

而 Xilinx 内核（6.1.30）的 `core.c` **无条件**调用 gadget 专有函数：
- `drivers/usb/dwc3/core.c:2104`（`dwc3_remove` 内）
- `drivers/usb/dwc3/core.c:2399`（`dwc3_suspend` 内）
- 两处都在 `#ifdef CONFIG_PM_SLEEP` 内，**没有** `CONFIG_USB_DWC3_GADGET` 守卫

定义在 **`drivers/usb/dwc3/gadget_hibernation.c:399`**（gadget 专有文件），声明在 `gadget.h:139`。
host-only ⇒ 该文件不参与编译 ⇒ 符号未定义 ⇒ vmlinux 链接失败。

`drivers/usb/dwc3/Kconfig` 的 `USB_DWC3_HOST` help 原文就写着
*"Select this when you want to use DWC3 in host mode only, thereby the gadget feature will be regressed."*
—— 这个模式本身就会退化 gadget 特性。而 Kconfig 的 mode choice 默认值：
```
default USB_DWC3_DUAL_ROLE if (USB && USB_GADGET)
```
Xilinx defconfig 只写 `CONFIG_USB_DWC3=y`（即默认 DUAL_ROLE=y），**并不用 host-only**。

### 正确做法
**DUAL_ROLE + 设备树 `dr_mode="host"`**。host 行为由设备树决定，不是由 Kconfig 模式决定。
ZCU104 板级 DTS（`{BOARD zcu104-revc}`）已经有 `dr_mode = "host"`，所以 dual-role 驱动照样把控制器跑成 host。

### 修正
`kernel_uvc.cfg` 改为：
```
CONFIG_USB_DWC3=y
CONFIG_USB_DWC3_DUAL_ROLE=y
```
（去掉 `CONFIG_USB_DWC3_HOST=y`、`CONFIG_USB_DWC3_DUAL_ROLE=n`；去掉多余的 `CONFIG_USB_XHCI_PCI=n` override）
原理写进 fragment 头部注释防回退。

**验证**：重建后 `.config` 变为
```
# CONFIG_USB_DWC3_HOST is not set
CONFIG_USB_DWC3_DUAL_ROLE=y
```
已提交推送 `5966654`。

### 教训（第 3 次同类失误）
这已经是**第三次**因为"按直觉写配置、没先查源码/归属"而失败：
1. `PARALLEL_MAKE` 填 `-j8`（应为纯数字，生成逻辑自己加 `-j `）
2. `package-management` 当包启用（实为 Image Feature）
3. `CONFIG_USB_DWC3_HOST=y`（应保持 DUAL_ROLE）

共同模式：**PetaLinux/Kconfig 的某些符号语义与字面直觉不符**。以后动任何 Kconfig/配置符号前，
先做两件事：① `grep` 生成逻辑或源码里的消费点；② 确认它是 recipe / image feature / kernel config 中的哪一类。

### 三、设备树新增 reserved-memory（V0 校验通过）
`plnx/system-user.dtsi` → `reserved-memory { npu-buffers@70000000 { reg = <0x0 0x70000000 0x0 0x1000000>; no-map; } }`

`no-map` 是关键：不加就还是 System RAM，`devmem_is_allowed()` 会拦掉；加了则被 `memblock_remove` 摘出 RAM 映射 → `/dev/mem` 可 map 且内核不会占用。

同时把 `CONFIG_SUBSYSTEM_EXTRA_BOOTARGS` 设为 `"rw"`（开发期方便），生成结果 `... root=/dev/mmcblk0p2 ro rootwait rw`（末尾 rw 生效）。

**V0 校验全过**：reserved-memory 在 / bootargs 含 `clk_ignore_unused` 且末尾 rw / `dr_mode="host"` 回归无损 / memory 节点 `0x0–0x7FF00000` 无冲突 / rootfs 含 `v4l-utils 1.23.0`(v4l2-ctl) + `usbutils 014`(lsusb) + `libv4l`。

### 二、顺带纠正一个易误读点（重要）
**融合了池化的层，硬件 `GF_OUTPUT_FNV1A` 报的不是存进 DDR 的池化张量。**
conv1 跑完后它读 `GF_BODY2_OUTPUT_FNV1A = GF_POOL_INPUT_FNV1A = 0x7E276C7B`，
即**池化前**卷积输出的 FNV；而 `gf_pool_output` 是 `0x33B1A130`。
⇒ 裸机版那处检查实际在查 MAC 输出流，**池化结果从未被验证过**。

### 三、升级：中间 6 个阶段改为字节级 memcmp
原来只查 DMA 写入字节数 → 现在逐张量 `memcmp` 对 golden。
实现在 `gf_npu.c` 的 `verify_tensor()`：

- **只在 `stats != NULL` 时执行**（`gf_npu_probe`）。实时摄像头循环传 NULL 走快速路径 ——
  否则每帧对非缓存内存做 ~0.6 MB 的 memcmp+FNV1A 会**污染 V4 要测的 CPU 侧开销**。
- 校验耗时单独累计进 `cpu_checks_ms`，报告里**从 CPU 开销中扣除**，保证与裸机 10.04 ms 同口径。
- 失败时打印**首个差异字节偏移 + 两侧值 + 两侧 FNV**，必须可定位。
- 唯一缺 golden 的是 head1x1 的 12×12×64 输出，只留软件 FNV 基线。
- 副作用：二进制 205 KB → 516 KB（golden 数组终于被引用，链接器不再丢弃）。

### 二、⚠️ 一次误判，代价不小，值得记牢
**现象**：`gf_npu.c` 里有 `Widen the reserved-memory node`，但 `strings` 在镜像 ELF 里搜不到。
**当时的错误结论**：`file://` 的 SRC_URI 不带内容哈希 ⇒ sstate 短路了 `do_compile`
⇒ 镜像里是旧代码。还围绕它编了一整套"证据"（85 字节的 `log.do_compile`、三次构建日志字节数相同）。
**真正原因（已证实）**：那句 `fprintf` 在
```c
if (bytes_needed > (size_t)GF_BUF_SIZE)   /* ~578 KB > 16 MiB，两边都是编译期常量 */
```
条件**恒假**，GCC 做了死代码消除，把整个分支**连字符串一起删掉**。**这是正确且期望的优化。**
**证实方式**：在 Yocto WORKDIR 里用完全相同的 `--sysroot` 和命令行手工编译，
返回码 0，字符串存活表显示"运行期条件保护的串全在，只有两个编译期常量保护的串不在"。

**⇒ 挑回归探针字符串时，条件必须是运行期才能确定的**（依赖读到的寄存器 / memcmp 结果 /
V4L2 返回值），否则它会凭空消失，看起来像"代码没进去"。
