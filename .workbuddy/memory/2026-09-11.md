### 摸清的关键技术事实（下次省事）
- **ZynqMP PS 从口使能属性是 `PSU__USE__S_AXI_GP0..GP6`**，映射到物理接口
  HPC0/HPC1/HP0..HP3：`GP0 → S_AXI_HPC0_FPD`、`GP1 → S_AXI_HPC1_FPD`（已实证）。
  板卡预置只启用 PS **主**口（M_AXI_HPM0/HPM1_FPD），**不会**启用从口，必须显式开 GP0。
- **`set_property CONFIG.X` 对不存在的属性不报错**（静默忽略）→ 不能用 OK/FAIL 判定属性是否存在，
  必须靠 dump 实际引脚验证。
- PS 从口的地址段路径是 `/zynq_ultra_ps_e_0/SAXIGP0/HPC0_DDR_LOW`（不是 `.../S_AXI_HPC0_FPD/...`）。
- **打包 IP 时 `aclk` 的 `FREQ_HZ` 会被 Vivado 推断成固定 80MHz**，导致任何非 80MHz 的
  pl_clk0 都 `validate_bd_design` 失败。修法：打包后用
  `ipx::get_bus_parameters FREQ_HZ` + `set_property value`（并设 `value_resolve_type user`）
  钉成目标频率。**这是阶段 1 提频的前置修复。**
- `proc_sys_reset` 的 `C_EXT_RESET_HIGH` 在 v5.0 是**只读**（实测=1，active-high），
  而 `pl_resetn0` 是 active-low → 必须插 `util_vector_logic` 反相。
- PS 主口的 aclk 引脚名：`maxihpm0_fpd_aclk` / `maxihpm1_fpd_aclk`；从口：`saxihpc0_fpd_aclk`，
  都要接 pl_clk0。
- 软件端口**极小**：`XTime` 走 BSP 的 `COUNTS_PER_SECOND`（无硬编码 tick），
  只差 AXI-Lite 基地址。已给 7020 的 `gestureflow_hagrid18_dmp_main.c` 的
  `GF_BASE`/`PROBE_BASE` 加 `#ifndef` 守卫，ZCU104 侧用 `-DGF_BASE=0xA0000000U` 覆盖，
  零重复代码且不动 7020 语义。PROBE_BASE 仍 0xFFFF0000（ZynqMP OCM 顶部同样适用）。
- 地址约定：NPU AXI-Lite 在 `0xA0000000`（MPSoC PL 区），NPU 主口映射 DDR_LOW
  （0x00000000 range 0x80000000）。
- **ZCU104 板卡当前未连接**（FTDI VID_0403&PID_6011 计数 0，无 hw_server）→ 板级验证待硬件。

### 根因锁定：`update_compile_order` 顺序错误导致源码被 AutoDisabled（20:00）
Module Reference 版 BD `BD_ONLY_PASS` 后，完整构建报出**新的、更靠后**的错误：
```
ERROR: [Synth 8-439] module 'system_wrapper' not found   （RTL Elaboration 阶段）
```
关键信号：**困扰 6 轮的 `.Xil/.../realtime/tmp` 错误彻底消失了** → 「自打包 IP 是根因」
的结论成立。

**真正原因（读 `.xpr` 得到的确凿证据）**：工程文件里 `sources_1` 源集中，
21 个 RTL 里有 16 个、以及 BD 的 `system.bd`、以及 wrapper
`$PPRDIR/project_local_gestureflow/system_wrapper.v` **全都被写了
`<Attr Name="AutoDisabled" Val="1"/>`** → 它们被排除出编译顺序，综合自然找不到 top。

为什么会被 AutoDisabled：**`update_compile_order` 在没有设定 top 的情况下运行**。
它的语义是"从当前 top 出发、把够不到的源文件全部标记 AutoDisabled"，而我把
它放在了 `set_property top system_wrapper` **之前**（脚本里有两处
`update_compile_order`：一处加完 RTL 就跑、一处加完 wrapper 就跑，top 都是后设的）。
这些 AutoDisabled 标志会被持久化进 `.xpr`，之后 `synth_design` 就只看到残缺源集。

**对照已验证的 7020 工程**：`gestureflow_hagrid18_7020_v1` 的 wrapper 位于
`$PSRCDIR/sources_1/imports/hdl/system_wrapper.v`，**没有** AutoDisabled 标记 ——
说明正常状态就该是启用。

**修法（顺序是本质）**：
1. **删掉加完 RTL 后那次 `update_compile_order`**（top 未定时运行只会造成误禁用）。
2. 注册 wrapper 后：**先 `set_property top system_wrapper [current_fileset]`，
   再 `update_compile_order -fileset sources_1`**。
3. 加**自诊断 + 强制恢复网**：遍历 `sources_1`，凡 `IS_ENABLED == 0` 的
   `set_property IS_ENABLED 1` 恢复，并打印 `AUTO_DISABLED_FORCED`。注意
   **恢复后不能再跑 `update_compile_order`**（会重新禁用）。

**顺带确认的一个正确性事实**：ZCU104 的 wrapper 是 `module system_wrapper ();`
**无端口**，这是**对的** —— Zynq-7000 的 DDR 走 fabric（所以 7020 的 wrapper 有
`DDR_addr/DDR_ba/...`），而 **ZynqMP 的 DDR/固定 IO 是 PS 专用引脚，不占 fabric 端口**。

**教训（跨项目可复用）**：Vivado 脚本化流程里 `update_compile_order` **必须在 top
确定之后调用**；用 `add_files` + `make_wrapper` 时尤其容易踩。判断源集是否健全
可以直接读 `.xpr` 里的 `AutoDisabled` 属性，比等综合报错快得多。

**坑1：`APU L2 cache is held in reset`**

（出处：meta-xilinx `README.booting.zynqmp.md`「Booting from JTAG」+ Xilinx 社区同错案例）

**坑2：`XIL_EXCEPTION_ID_DATA_ABORT_INT` 在 AArch64 不存在**

`XIL_EXCEPTION_ID_SYNC_INT`（同步异常，含 data/prefetch abort）+
`XIL_EXCEPTION_ID_SERROR_ABORT_INT`。
已在 `gestureflow_hagrid18_dmp_main.c` 用 `#if defined(__aarch64__)` 加保护，
**7020 路径不受影响**（已同步回仓库）。

**坑3（工具链）**：Vitis 2023.2 的 `app build -name X` 在 xsct 批处理里**无限挂起**
（无输出、无进程、无报错）。改用 7020 验证过的做法：**直接 `aarch64-none-elf-gcc` 编译**，
配合 `app create` 生成的 `lscript.ld`。不需要 `Xilinx.spec`（aarch64 没有这个 spec）。

**A. 正规（需 sudo，推荐，一次到位）**
```bash

```

**B. 免 sudo（本次采用，已验证）**
`localedef` 可以把 locale 生成到**任意目录**，再用 `LOCPATH` 指过去：
```bash
mkdir -p ~/.locales
localedef -i en_US -f UTF-8 ~/.locales/en_US.UTF-8
export LOCPATH=~/.locales
```
实测验证（写了个 C++ 小程序测 `std::locale("en_US.UTF-8")`）：
```
不带 LOCPATH : FAIL: locale::facet::_S_create_c_locale name not valid
带 LOCPATH   : OK: en_US.UTF-8 可用
```
已把 `ensure_locale()` 加进 `plnx_driver.sh`，每个 stage 在 `source settings.sh` 之后调用，
自动生成并导出 `LOCPATH` / `LC_ALL` / `LANG`。

### 通用教训（跨项目）
1. **WSL 上的 WSL 发行版默认只有 C.UTF-8**，而很多 Xilinx/AMD 工具硬编码 `LC_ALL=en_US.UTF-8`。
   症状不是"警告"而是**C++ 工具 core dump**，很容易误判成工具坏了。
2. **判断小技巧**：写个 20 行 C++ 测 `std::locale("<name>")`，能立刻区分
   "locale 缺失" 和 "工具真有问题"。
3. **`LOCPATH` 是个好东西**：任何需要额外 locale 但拿不到 root 的场合都能用。
4. 排查时**先 grep 工具链里的硬编码导出**（`grep -rn 'LC_ALL' tools/`），
   比反复试环境变量快得多。

## 【第二个 locale 坑】BitBake 因 setlocale 警告误判 gcc 版本而 fatal（23:45）

locale 修好后工程建成功（`MACHINE_NAME=zcu104-revc` 已确认写入 `{BOARD zcu104-revc}`），
但 `petalinux-build` 秒退：

```
INFO: bitbake petalinux-image-minimal
ERROR: Can't get compiler version from gcc  --version output
BUILD_RC=255
```

### 定位过程（这次全程有依据）
1. `gcc --version` 在各环境下都正常 → 排除 gcc 本身
2. 去源码找报错：`poky/meta/lib/oe/utils.py:430 / :456`
   ```python
   output = subprocess.check_output("%s --version" % compiler,
             shell=True, env=env, stderr=subprocess.STDOUT).decode("utf-8")
   match = re.match(r".* (\d+\.\d+)\.\d+.*", output.split('\n')[0])   # ← 只看第一行
   if not match: bb.fatal("Can't get compiler version from %s --version output" % compiler)
   ```
3. 触发点：`sanity.bbclass:489` → `check_gcc_version` → `get_host_compiler_version`
4. `BUILD_CC = "${CCACHE}${BUILD_PREFIX}gcc ${BUILD_CC_ARCH}"`（`bitbake.conf:570`，
   `CCACHE=""`、`BUILD_PREFIX=""`、`BUILD_CC_ARCH=""`）⇒ 实际命令是 **`gcc  --version`**（双空格）
5. `shell=True` ⇒ 走 `/bin/sh`；`env=os.environ.copy()` ⇒ 用会话环境

### 精确复现（决定性证据）
写了个探针，逐个组合测 `/bin/sh -c 'gcc  --version'` + `stderr→stdout` + 取第一行：
```
A: 无 locale 变量                     → OK
B: 仅 LOCPATH                         → OK
C: LOCPATH + LC_ALL=en_US.UTF-8       → OK
D: 仅 LC_ALL=en_US.UTF-8（无 LOCPATH） → FAIL
   first line = "/bin/sh: warning: setlocale: LC_ALL: cannot change locale (en_US.UTF-8)"
E: LC_ALL=C.UTF-8                     → OK
```
**⇒ 根因：`LC_ALL=en_US.UTF-8` 但 locale 不可得时，`/bin/sh` 会往 stderr 打一行 setlocale 警告；
BitBake 把它合并进 stdout 且只检查第一行 → 正则匹配到警告文本 → bb.fatal。**

**⇒ 结论：`LOCPATH` 的免 sudo 修法不够彻底**（PetaLinux/BitBake 的调用链里有些 shell 拿不到
LOCPATH，例如日志里 `Starting bitbake server` 之前就出现过 `/bin/bash: warning: setlocale: ...`）。
**正规修法：系统级生成 en_US.UTF-8（需 sudo）。**

### 处置
让用户执行一次（`00_host_setup.sh` 里已加 `locale-gen en_US.UTF-8`）：
```bash
sudo bash ~/coralnpu-gesture/gesture_project/innovation_npu/board_zcu104/plnx/00_host_setup.sh
```

### 通用教训（很重要，跨项目）
1. **BitBake 的 `_get_host_compiler_version` 用 `stderr=STDOUT` + 只解析第一行**，
   任何通往 stderr 的一行噪声（locale 警告、shell 警告、deprecation 提示）都会让它误判成
   "gcc 版本解析失败"。看到 `Can't get compiler version from ... --version output` 时，
   **先怀疑 stderr 噪声，而不是 gcc**。
2. 排查手法有效：**先在源码里 grep 到报错字符串**，读它的解析逻辑，
   再按逻辑写出最小复现探针——比反复试参数快得多。
3. 这类"环境噪声污染 stdout 解析"的坑，`LC_ALL` 必须指向**真实存在**的 locale；
   半吊子的 LOCPATH 只在部分进程生效。

```
  .../meta-petalinux/recipes-core/images/petalinux-image-minimal.bb RDEPENDS on or
  otherwise requires it)
ERROR: Required build target 'petalinux-image-minimal' has no buildable providers.
```

### 根因
`rootfs_config` 里其实是**两个不同符号、不同段**：
```
4069:# CONFIG_imagefeature-ssh-server-dropbear is not set
4070:CONFIG_imagefeature-ssh-server-openssh=y
4071:CONFIG_imagefeature-hwcodecs=y
4072:# CONFIG_imagefeature-package-management is not set   ← Image Feature（正确位置）
4073:# CONFIG_imagefeature-debug-tweaks is not set
4074:# CONFIG_imagefeature-empty-root-password is not set
...
4079-4081:# user packages
4082:# CONFIG_gpio-demo is not set
4083:CONFIG_package-management=y                          ← 我错当成"包"启用的
```

我把 `CONFIG_package-management` 写进了 `project-spec/meta-user/conf/user-rootfsconfig`
（直接抄的 Vitis 教程包清单）。**PetaLinux 会把 user-rootfsconfig 里的条目当 recipe
塞进 `IMAGE_INSTALL`**，而 `package-management` 不是 recipe → `Nothing RPROVIDES`。

**教训：Vitis 教程那份清单混了"image features"和"真实包"，抄的时候必须逐项确认归属。**

### 修正（已落地）
1. 从 `user-rootfsconfig` 删掉 `CONFIG_package-management`（原文件已备份为 `.bak`）
2. `rootfs_config` 里 `CONFIG_package-management` 置为 not set
3. 打开**正确**的 `CONFIG_imagefeature-package-management=y`
4. 顺带打开 `CONFIG_imagefeature-empty-root-password=y`（串口调试免密码，避免登录不了）

验证通过的真实包：`CONFIG_dnf`、`CONFIG_e2fsprogs-resize2fs`、`CONFIG_parted`、
`CONFIG_usbutils`、`CONFIG_packagegroup-petalinux-v4lutils` 全部 =y ✓

### 判断方法（可复用）
遇到 `Nothing RPROVIDES 'X'`，先分清 X 是 recipe 还是 feature：
- recipe 名一般能在 `components/yocto/layers/*/recipes-*/*/*.bb` 里找到
- 若是 IMAGE_FEATURE，正确写法是 `CONFIG_imagefeature-X`，且它不在 user-rootfsconfig 里
